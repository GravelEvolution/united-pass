# ADR-0007: Phase 5 identity/workforce real API seam

- Status: Accepted
- Date: 2026-08-11
- Depends on: ADR-0006, backend ADR-0011

## Context

Phase 5 replaces the Mock-only user, employee and department administration
surfaces with the authoritative backend management plane. The frontend must
not recreate identity linking, authorization or pagination rules in browser
state.

## Decision

### 1. Server-side directory queries

User and employee search, filters, sort and cursor pagination are URL-driven
and forwarded to the backend. The browser never downloads a complete
directory for local filtering. Department search is also server-side and is
bounded to 100 rows until the product introduces a cursor UI.

Opaque cursors are treated as untrusted input and are sent only with the
current query state. The backend signs and binds them to that state; the
frontend does not decode them.

### 2. Runtime validation at the trust boundary

Every Phase 5 response is narrowed by a fail-closed runtime validator before
it reaches a page or component. This includes capabilities, cursor pages,
nested user detail, employee profiles and department detail. A TypeScript
annotation alone is not considered response validation.

### 3. Stable identity linking

Employee linking submits an explicit existing `userId`. Email, display name,
phone, domain and provider subject are display/search facts only. The UI does
not offer an implicit merge or a second employee-account creation path.

### 4. Target-bound high-risk operations

User disable, bulk user-session revocation and employee offboarding reuse the
password/TOTP/passkey reauthentication flow. The requested grant is bound to
the exact action and target `userId`, then sent in
`X-Reauthentication-Token` for that one mutation. It is never cached or
reused for another target.

All browser mutations use the shared same-origin HTTP client and CSRF
contract. Targeted single-session revocation, user enable, profile updates and
department changes remain capability-checked mutations but do not consume a
step-up grant under the Phase 5 backend contract.

### 5. Capability checks are presentation only

Pages and controls use `/api/v1/me/permissions` to hide or disable unavailable
actions. These checks improve usability but confer no authority. The backend
authenticates, authorizes, validates ownership and audits every request.

### 6. Durable cleanup wording

An offboarding or disable response may report `cleanupPending`. The UI says
that authoritative access denial has started and local session cleanup is
converging; it never claims that all ZITADEL sessions have already been
revoked. Provider-side revocation remains the backend's explicitly audited
best-effort boundary.

## Consequences

- P5 pages use real queries and browser commands in non-Mock mode.
- URL search and cursors survive refresh and browser navigation.
- Malformed responses fail closed instead of partially rendering.
- Mock implementations remain only as development/test fixtures and must
  satisfy the same data-source contract.
- Authorization logic, cursor signatures, hierarchy safety and identity
  uniqueness remain backend responsibilities.
