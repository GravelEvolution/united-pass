# ADR-0004: API 客户端、浏览器会话与错误处理边界

- Status: Accepted
- Date: 2026-08-05
- Owners: United Pass frontend team

## Context

United Pass 前端目前通过 `UnitedPassDataSource` 接口和 `mockUnitedPassDataSource` 实现提供页面数据。OAuth 应用创建、授权确认状态机和账号中心授权应用页面已完成，Mock 数据结构趋于稳定。

下一步需要替换 Mock 为真实后端 API。`docs/api-contracts.md` 已定义了路径、分页模型和错误响应草案，但在实际接入前需要确定：

1. HTTP 客户端放在哪里、如何组织
2. 浏览器会话如何传递（Cookie、CSRF）
3. HTTP 状态码如何统一归一化为前端可消费的错误类型
4. 后端字段错误如何映射到 Semi Design Form
5. Cursor Pagination 如何映射到 Semi Design Table
6. 重认证 Challenge 如何在 UI 层表示
7. OpenAPI 生成的客户端最终放在哪里

此外，数据源接口已拆分为 `UnitedPassQueries`（只读查询）和 `UnitedPassCommands`（写操作），以便 Mock 和真实后端实现相同的读写合同。

## Decision

### 1. Server/Browser 双 HTTP 客户端架构

Server Component 和浏览器端的运行环境存在根本差异：

- **Server Component** 中没有 `document.cookie`，`credentials: "same-origin"` 不会自动转发用户当前请求的 Cookie。必须通过 `next/headers` 的 `cookies()` 读取会话 Cookie，再显式传递给后端 API。
- **浏览器端** 的写操作需要 CSRF Token，而 Server Component 发出的服务端请求不需要 CSRF（请求不经过浏览器）。
- 服务端请求不应复用依赖浏览器全局对象（`document`、`window`）的实现。

因此，HTTP 客户端明确拆分为两个运行环境：

```
src/lib/api/
├── united-pass-data-source.ts       # 已实现：数据源接口（Queries + Commands）
├── api-error.ts                     # 已实现：错误归一化与类型守卫
├── browser/
│   ├── browser-http-client.ts       # 待实现：浏览器端 fetch 封装
│   └── browser-commands.ts          # 待实现：浏览器端 Mutation 调用
├── server/
│   ├── server-http-client.ts        # 待实现：服务端 fetch 封装
│   ├── server-queries.ts            # 待实现：服务端 Query 实现
│   └── server-session.ts            # 待实现：服务端会话读取
├── generated/                       # 待实现：OpenAPI 生成代码
└── api-contracts.md → docs/         # 已有：API 草案
```

#### browser-http-client.ts 职责

- 封装 `fetch`，统一设置 `credentials: "same-origin"` 和 `Content-Type`
- 从 `document.cookie` 读取非 HttpOnly 的 CSRF Token，在写操作时通过 `X-CSRF-Token` 请求头发送
- 解析响应体，处理非 2xx 状态码
- 返回类型化结果，不泄漏 `Response` 对象到上层

#### server-http-client.ts 职责

- 封装 `fetch`，不设置 `credentials`（服务端没有浏览器凭据概念）
- 通过 `next/headers` 的 `cookies()` 读取用户会话 Cookie，显式作为 `Cookie` 请求头发送给后端
- 不读取或发送 CSRF Token（服务端到后端的请求不需要 CSRF 保护）
- 解析响应体，处理非 2xx 状态码
- 返回类型化结果，不泄漏 `Response` 对象到上层

#### 数据流

- **Server Component** → `server-queries.ts` → `server-http-client.ts` → 后端 API
- **Client Component** → `browser-commands.ts` → `browser-http-client.ts` → 后端 API
- 页面只依赖 `UnitedPassDataSource` 接口（或其子接口 `UnitedPassQueries` / `UnitedPassCommands`），不直接导入 HTTP 客户端

### 2. 浏览器会话

- 会话使用 `Secure; HttpOnly; SameSite=Lax` Cookie，由后端在 `POST /api/v1/auth/sessions` 后设置
- 前端不持有、不存储 Access Token、Refresh Token 或 ID Token
- 浏览器端 API 请求使用 `credentials: "same-origin"`，浏览器自动携带会话 Cookie
- 服务端 API 请求通过 `cookies()` 读取会话 Cookie，显式转发给后端
- CSRF Token 通过后端下发的非 HttpOnly Cookie 读取，仅在浏览器端写操作时发送
- `server-session.ts` 在 Server Component 中读取会话状态，用于决定是否重定向到 `/login`

### 2.1 管理端预渲染权限门禁

管理端页面采用三层授权边界：

1. `src/proxy.ts` 仅匹配 `/admin/:path*`，在 React 路由开始渲染前把
   `up_session` 转发给 `GET /api/v1/me/permissions`。未登录请求跳转
   `/login`，全部管理能力为 `false` 的请求跳转 `/account`，上游故障或
   malformed 响应返回不可缓存的 `503`，不得放行。
2. 管理端共享 Server Layout 再次读取权限并执行相同的 fail-closed 入口检查，
   防止未来 matcher 或路由结构调整后只剩 Proxy 单点保护。
3. 后端每个 `/api/v1/admin/*` Handler 继续独立认证和授权；Proxy 与前端
   capability 只负责预过滤和避免未授权页面内容进入流式响应，不是数据安全边界。

Proxy 不缓存用户权限，也不转发 CSRF Cookie、Access Token 或其他凭据。它只转发
当前 HttpOnly Session Cookie；最终数据和 Mutation 授权始终由后端决定。

### 3. 错误处理边界

`api-error.ts` 定义统一的错误类型（**已实现**）：

```ts
type ApiErrorKind =
  | "network"
  | "unauthorized"       // 401
  | "forbidden"          // 403
  | "not_found"          // 404
  | "conflict"           // 409
  | "validation"         // 422
  | "rate_limited"       // 429
  | "reauthentication_required" // 后端要求重新验证身份
  | "server_error";      // 5xx

type FieldError = {
  field: string;
  message: string;
};

type ReauthenticationChallenge = {
  methods: ReadonlyArray<"password" | "totp" | "passkey">;
  requestId: string;
};

type ApiError = {
  kind: ApiErrorKind;
  message: string;          // 可安全展示给用户
  requestId?: string;       // 后端追踪 ID
  fieldErrors?: FieldError[];
  retryAfter?: number;      // 429 时的重试等待秒数
  challenge?: ReauthenticationChallenge; // 重认证 Challenge
};
```

`isApiError` 类型守卫完整验证 `kind`（必须为合法 `ApiErrorKind`）、`message`（必须为字符串），以及所有可选字段的结构。

映射规则：
- 401 → `unauthorized`：重定向到 `/login`，保留 `requestId` 参数
- 403 → `forbidden`：展示权限不足提示，不重定向
- 404 → `not_found`：展示 notFound() 或空状态
- 409 → `conflict`：展示资源冲突提示（如邮箱已存在）
- 422 → `validation`：将 `fieldErrors` 映射到 Semi Form 的 `validateStatus` 和错误文案
- 429 → `rate_limited`：展示限速提示，读取 `Retry-After` 头
- 后端返回 `code: "session.reauthentication_required"` → `reauthentication_required`：触发重认证流程
- 5xx → `server_error`：展示通用错误页面，不暴露内部信息

### 4. 字段错误映射到 Semi Form

后端 422 响应的 `fieldErrors` 对象按字段名映射到 Semi Design Form：

```tsx
// 后端返回: { "redirectUri": "该重定向地址未登记。" }
// 前端映射:
formApi.setError("redirectUri", {
  text: apiError.fieldErrors?.find(e => e.field === "redirectUri")?.message
});
```

Semi Form 的 `validateStatus` 设为 `"error"`，错误文案显示在字段下方。

对于非字段级错误（如凭据错误、限速），使用 `Toast` 或页面级错误提示。

### 5. Cursor Pagination 映射到 Semi Table

后端使用 Cursor Pagination：

```json
{
  "items": [],
  "page": { "nextCursor": "opaque_cursor_or_null", "hasMore": false }
}
```

后端响应**不包含** `total` 或 `estimatedTotal`。前端不展示虚假的总页数。

映射策略：
- `dataSource` 使用当前页 `items`
- 使用上一页/下一页分页模式，不展示总页数
- 前端维护 Cursor 栈以支持后退导航
- 当 `hasMore` 为 `true` 时，下一页请求携带 `?page[cursor]=nextCursor`
- 搜索、排序变更时重置 Cursor 栈，从第一页重新加载
- 对于审计日志、大用户列表等场景，Cursor Pagination 比页码分页更适合

如果产品要求展示总条数，后端需额外提供精确或估算的 `total`，前端才使用页码分页 UI。当前不计划添加此字段。

### 6. 重认证 Challenge

后端在需要更强身份验证的操作（如密钥轮换、会话撤销、策略发布）时返回：

```json
{
  "error": {
    "code": "session.reauthentication_required",
    "message": "请重新验证身份后继续。",
    "challenge": {
      "methods": ["password", "totp"],
      "requestId": "reauth_01..."
    }
  }
}
```

前端表示：
- `ApiError.kind` 设为 `reauthentication_required`
- Client Component 收到此错误后打开重认证 Modal
- Modal 展示可用的验证方式（密码、TOTP、Passkey）
- 验证成功后自动重试原始请求
- `challenge.requestId` 用于关联重认证流程与原始操作

### 7. OpenAPI 客户端放置

当后端 OpenAPI 规范可用时：
- 生成的类型和客户端放在 `src/lib/api/generated/`
- `browser-commands.ts` 和 `server-queries.ts` 内部调用生成的客户端，但对外仍暴露 `UnitedPassDataSource` 接口
- 页面不直接导入 `generated/` 下的代码
- 手写的传输类型逐步替换为生成类型
- 生成代码不手动编辑；变更时先更新 OpenAPI 规范再重新生成

## Alternatives Considered

- **在页面中直接调用 fetch**：简单直接，但会将 URL 构造、错误处理和 Cookie 逻辑扩散到每个页面，替换成本高
- **使用 axios 或 got 等第三方 HTTP 库**：增加依赖且不提供比 fetch 更多的能力；fetch 已满足需求
- **使用单一通用 http-client.ts**：服务端和浏览器端环境差异大（Cookie 传递、CSRF、全局对象），共用实现会导致条件分支过多且容易出错
- **在 Next.js Route Handler 中实现 BFF 层**：增加了一层间接调用，但当前不需要端到端网络转换或服务端密钥注入
- **使用 React Server Actions 替代 API 层**：适合内部工具，但 OAuth/OIDC 流程需要标准 HTTP 重定向和 Cookie 语义，不适合 Server Actions
- **只在管理端共享 Layout 中重定向**：Next.js 可并行、流式渲染 Layout 与子页面；重定向指令产生前，子页面内容可能已经进入 `200` 响应，因此不能独立承担渲染前预过滤
- **在 Cursor Pagination 响应中添加 estimatedTotal**：增加了后端复杂度且估算值可能误导用户；审计日志等场景更适合纯 Cursor 模式

## Consequences

- 页面只依赖 `UnitedPassDataSource` 接口（或其子接口），Mock 和真实 API 实现可互换
- Server Component 和 Client Component 使用各自环境的 HTTP 客户端，不会因环境差异产生运行时错误
- 错误处理集中在一处，不会在每个页面重复
- CSRF Token 的读取和注入仅在浏览器端进行，对服务端透明
- 重认证流程有统一的 UI 表示，不会散落在各组件中
- 当 OpenAPI 合同可用时，生成代码隔离在 `generated/` 下，不影响接口边界
- 前端不持有任何 Token，降低了凭据泄露风险
- Cursor Pagination 使用 Cursor 栈管理，不展示虚假总页数
- 未授权管理请求在 React 渲染前被拒绝，不再把后台页面内容写入流式响应
- 每次管理页面请求增加一次不可缓存的权限摘要查询；这是阻止预渲染泄漏的明确延迟成本，后端逐接口授权仍保持不变
