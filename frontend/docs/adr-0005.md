# ADR-0005: Application、OAuth Client 与 Grant Profile 模型

- Status: Accepted
- Date: 2026-08-05
- Owners: United Pass frontend team

## Context

当前前端将 OAuth Application 和 OAuth Client 混为同一实体。`OAuthApplicationDetail` 直接包含 `clientId`、`clientType`、`redirectUris`、`clientSecrets`，即一个应用只能有一个 Client。这在实际产品中行不通：

- 一个产品应用通常需要 Web、iOS、Android、Server-to-server 等多个 Client
- 不同 Client 有不同的 Grant Type、Redirect URI 和认证方式
- Client Credentials Grant 不需要 Redirect URI、openid Scope 或用户 Consent
- 当前 `ApplicationKind`（"internal" | "public-app" | "hybrid"）描述的是应用的受众范围，但 "public-app" 容易与 OAuth 的 "public client" 混淆

后端尚未实现，现在是修改模型的最低成本时机。

### 现有问题清单

1. 创建表单强制所有应用选择 `openid` Scope 并填写至少一个 Redirect URI，不适合机器对机器 Client
2. 创建表单只有一个 Client Type 选项（Public / Confidential），缺少 Grant Type 和 Token Endpoint Auth Method
3. `consentRequired` 只是一个 Checkbox，任何管理员都能关闭 Consent 页面
4. 应用列表展示的是 Client 级别的字段（`clientType`），而非应用级别的字段

## Decision

### 1. 拆分 Application 与 OAuth Client

Application 是产品级实体，描述应用本身的属性。OAuth Client 是应用下的认证配置单元，一个 Application 可以有多个 Client。

```ts
type Application = {
  applicationId: string;
  name: string;
  description: string;
  logoUrl: string | null;
  audience: ApplicationAudience;
  ownerId: string;
  ownerName: string;
  status: "active" | "disabled";
  createdAt: string;
  updatedAt: string;
};
```

```ts
type OAuthClient = {
  clientId: string;
  applicationId: string;
  name: string;
  clientType: "public" | "confidential";
  grantTypes: OAuthGrantType[];
  tokenEndpointAuthMethod: TokenEndpointAuthMethod;
  redirectUris: RedirectUriEntry[];
  logoutUri: string | null;
  allowedScopes: AllowedScope[];
  consentMode: ConsentMode;
  status: "active" | "disabled";
  clientSecrets: ClientSecretRecord[];
  createdAt: string;
  updatedAt: string;
};
```

### 2. ApplicationAudience 替代 ApplicationKind

将 `ApplicationKind` 重命名为 `ApplicationAudience`，避免 "public-app" 与 OAuth "public client" 混淆：

```ts
type ApplicationAudience = "internal" | "external" | "hybrid";
```

- `internal`：仅组织内部使用
- `external`：面向所有用户开放授权
- `hybrid`：同时支持内部和外部使用场景

### 3. Grant Type 与 Client Profile

```ts
type OAuthGrantType =
  | "authorization_code"
  | "refresh_token"
  | "client_credentials";
```

```ts
type TokenEndpointAuthMethod =
  | "client_secret_post"
  | "client_secret_basic"
  | "none"
  | "private_key_jwt";
```

创建流程先让管理员选择 Client 用途（Client Profile），自动限定配置：

| Profile | Grant Types | Redirect URI | openid | Consent | Secret |
|---------|------------|--------------|--------|---------|--------|
| Web 服务端 | authorization_code, refresh_token | 需要 | 可选 | 通常需要 | 有 |
| SPA / 移动端 | authorization_code, refresh_token | 需要 | 可选 | 通常需要 | 无（PKCE） |
| 服务账号 | client_credentials | 不需要 | 不允许 | 不适用 | 有 |

```ts
type ClientProfile =
  | "web_server"
  | "spa_mobile"
  | "server_to_server";
```

选择 Profile 后，表单自动设置 Grant Types 和 Token Endpoint Auth Method，管理员可在此基础上微调。

### 4. ConsentMode 替代布尔值

```ts
type ConsentMode =
  | "always"
  | "first_authorization";
```

- `always`：每次授权都显示确认页（默认）
- `first_authorization`：首次授权显示确认页，后续自动通过

> **MVP 变更**：`trusted_first_party` 暂不支持。该模式需要后端信任策略、`application.trust.manage` 权限和重认证才能安全使用，将在后端实现信任策略后再加入类型和表单。

前端不自行决定是否跳过 Consent，仅传递 `consentMode` 给后端，由后端根据应用受众、Scope 敏感度和用户权限决定是否强制确认。

### 5. 路由结构

```
/admin/applications                          # 应用列表
/admin/applications/new                      # 创建应用
/admin/applications/[applicationId]          # 应用详情（含 Client 列表 Tab）
/admin/applications/[applicationId]/clients/[clientId]  # Client 详情
```

应用详情页的 Tab 调整为：

- 基本信息（Application 级）
- OAuth Clients（Client 列表与配置）
- 授权记录
- 审计日志
- 危险操作

### 6. 创建流程

创建分为两步：

1. **创建 Application**：名称、说明、Logo、受众、负责人
2. **创建第一个 OAuth Client**：选择 Client Profile、填写 Redirect URI、选择 Scope、设置 Consent Mode

创建成功后跳转到应用详情页，管理员可以在详情页继续添加更多 Client。

## Alternatives Considered

- **保持 Application = Client 的一对一模型**：简单但不现实。一个产品通常需要 Web + 移动端 + 服务端至少三个 Client，强行拆成三个"应用"会导致应用列表混乱
- **将 Client 嵌入 Application 详情但不独立路由**：可行但不利于后续 Client 级别的审计、密钥轮换和权限管理
- **使用动态 Client Registration 协议（RFC 7591）**：后端尚未实现，过早引入协议级抽象增加复杂度
- **不引入 Client Profile**：直接让管理员手动选择 Grant Types。可行但容易配错（如 Confidential Client 忘记加 refresh_token）

## Consequences

- Application 列表只展示应用级字段（名称、受众、状态），不再暴露 Client 级细节
- 应用详情页需要重构为多 Client 布局
- 创建表单拆为两步，但仍然在一个页面内完成
- Client Secret 只在 Client 级别管理，不在 Application 级别
- `ApplicationCreateInput` 拆分为 `ApplicationCreateInput` 和 `OAuthClientCreateInput`
- Grant Profile 是前端便利层，后端仍以 `grantTypes` 数组为准
- ConsentMode 是声明性的，后端保留强制确认的权力
- 前端权限检查需要细化到 Client 级别（如 `application.client.create`）

- ✅ MVP 移除 `trusted_first_party` 同意模式，待后端实现信任策略后再加回
- ✅ `openidAllowed` 和 `openidRequired` 已拆分，MVP 中所有 Profile 的 `openidRequired` 均为 `false`，管理员可按需选择
- 后端确认 Client Profile 是否需要存储为枚举，还是仅作为创建时的便利选项
- 确认 `private_key_jwt` 认证方式是否在 MVP 范围内
- 确认 Client 数量上限和权限粒度
- 评估是否需要 Client 级别的独立审计日志
- 确认 ConsentMode 的后端验证规则和审计事件格式
