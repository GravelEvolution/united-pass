# ADR-0008: Phase 6 Feishu Provider real API seam

- Status: Accepted
- Date: 2026-08-11
- Depends on: ADR-0007, backend ADR-0012

## Context

Phase 6 replaces the Provider administration mock seam with a real backend and
adds an optional Feishu login entry. Identity matching, OAuth state, credentials,
directory reconciliation and authorization remain server responsibilities.

## Decision

### 1. Server and client boundaries

Provider list/detail/history/conflict queries run through Server Components and
the server HTTP client. Enable/disable, sync, resolve and ignore run through the
shared browser command client, which supplies same-origin credentials and CSRF.
Every untrusted response is narrowed by a Phase 6 runtime validator.

The login page fetches the public Provider list on the server. When Feishu is
effectively enabled it renders a normal link to the backend authorization
endpoint; the browser never receives or exchanges App Secret, authorization
code or Provider access token.

### 2. Explicit identity linking

Conflict rows may show an email/name candidate, but the UI labels them as
suggestions. Resolution submits an explicit stable `userId` and obtains a
single-use reauthentication grant bound to `provider.identity.link` and the
exact `conflictId`. The UI never calls resolve automatically.

### 3. Provider state and long-running jobs

Enable/disable consume grants bound to `provider.enable` or `provider.disable`
and the exact `providerId`. The secret is represented only as the boolean
`secretConfigured`; no input or readback seam exists for secret material.

Directory synchronization returns a `pending` job with HTTP 202. The UI reports
that it was queued and renders `pending`/`running`/`success`/`partial`/`failed`
history, including nullable completion time. It does not claim immediate
completion or infer local employee changes from Provider counters.

### 4. Login failure disclosure

The backend redirects with one of two safe display codes: a generic Provider
failure or an unlinked identity that requires administrator handling. The login
page does not display Provider response text, tenant keys, subjects or candidate
account data.

### 5. Capability checks

`providerRead` and `providerManage` control navigation and action presentation
only. The backend independently authenticates, authorizes, checks CSRF,
consumes reauthentication grants and audits mutations.

## Consequences

- P6 Provider and public-login seams use real HTTP when mock mode is disabled.
- Mock Provider records remain development/test fixtures satisfying the same
  contract, not production fallback.
- Secrets and Provider tokens never cross the Server/Client Component boundary.
- Identity suggestions cannot become links without an explicit administrator
  selection and target-bound step-up.
