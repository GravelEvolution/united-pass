# ADR-0002: Identity Provider 管理边界与飞书规划

- Status: Accepted
- Date: 2026-08-05
- Owners: United Pass frontend team

## Context

管理后台需要统一查看外部身份 Provider，并将飞书作为未来首个厂商接入目标。当前没有后端 Provider 合同、服务端密钥管理、回调校验或账户关联流程，因此界面不能暗示飞书登录已经可用，也不能在浏览器中实现协议交换。

## Decision

1. 新增 `/admin/providers` 作为 Provider 清单入口，与 OAuth 应用管理保持独立。
2. Provider 只展示非敏感元数据、启用状态、登录可用性和关联用户数量；客户端密钥、供应商令牌与回调凭据不进入前端数据模型。
3. 飞书以 `planned` Mock 记录出现，`loginEnabled` 固定为 `false`，待后端合同和安全评审完成后再实现配置与登录流程。
4. 未来 Provider 登录和账户关联由后端处理。前端只承载受控配置、状态和明确确认，不负责凭据交换或安全决策。
5. 外部主体必须关联到既有稳定 `userId`。不得仅凭邮箱、手机号或组织域自动合并账户，也不得从 Provider 属性直接推导员工或管理权限。

## Alternatives Considered

- 将 Provider 放入 OAuth 应用列表：两者都涉及 OAuth，但一个是外部身份来源，一个是 United Pass 对外提供的客户端，生命周期、密钥归属和风险不同。
- 立即制作可编辑飞书配置表单：缺少后端合同和密钥托管方案，容易形成不可用或不安全的伪实现。
- 在前端直接调用厂商令牌接口：会暴露客户端凭据并把协议安全责任错误地放到浏览器。

## Consequences

- 管理员可以评审 Provider 信息架构，同时界面清晰表达飞书尚未启用。
- 真实实现需要新增服务端密钥管理、回调校验、重认证、审计、冲突处理和账户恢复设计。
- Provider 权限与应用、员工和策略权限保持独立，后端仍是唯一授权边界。

## Follow-up

- 与后端及安全团队确认飞书开放平台的协议、回调、密钥轮换与错误合同。
- 设计显式账户关联、冲突解决、解绑、恢复和停用影响说明。
- 接入前补齐允许与拒绝路径、重放防护和权限回归测试。
