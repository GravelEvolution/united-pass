# ADR-0006: Frontend、API、OAuth endpoints 与 Cookie 部署拓扑

- Status: Proposed
- Date: 2026-08-05
- Owners: United Pass frontend team

## Context

当前前端存在三套不同的 Cookie 命名：

```text
浏览器 CSRF Cookie：csrf_token        (browser-http-client.ts)
服务端 Session Cookie：session         (server-session.ts)
法律文件 Cookie：ms_session / ms_csrf_token  (privacy-sections.ts)
```

浏览器 API 使用同源 `/api/v1`，服务端 API 默认使用 `http://localhost:8080/api/v1`。

在 Go 后端开工前，必须统一 Cookie 名称、部署拓扑和 CSRF 约定，否则后端联调时会出现 Cookie 不匹配、CSRF 校验失败、法律文件描述与实际不符等问题。

## Decision

### 1. 统一 Cookie 命名

```ts
SESSION_COOKIE_NAME = "up_session";
CSRF_COOKIE_NAME = "up_csrf";
CSRF_HEADER_NAME = "X-CSRF-Token";
```

所有代码、法律文件和后端配置统一使用以上名称。法律文件中的 `ms_session` / `ms_csrf_token` 必须同步更新为 `up_session` / `up_csrf`。

### 2. 反向代理拓扑

生产环境使用单一域名，通过路径前缀反向代理到不同后端：

```text
浏览器请求：
  https://pass.example.com/api/v1/*     → Go backend (REST API)
  https://pass.example.com/oauth2/*     → OAuth/OIDC provider (ZITADEL or Go)
  https://pass.example.com/.well-known/* → OAuth/OIDC provider
  https://pass.example.com/*           → Next.js frontend (SSR + assets)
```

这样所有 Cookie 都在同一站点下，不需要跨域 Cookie 配置。

### 3. Cookie 属性

| Cookie | Domain | Path | HttpOnly | Secure | SameSite |
|--------|--------|------|----------|--------|----------|
| `up_session` | `.example.com` 或同源 | `/` | `true` | `true`（生产） | `Lax` |
| `up_csrf` | 同源 | `/` | `false`（前端需读取） | `true`（生产） | `Lax` |

- `up_session` 是 HttpOnly Cookie，前端 JavaScript 无法读取，由后端 Set-Cookie 设置。
- `up_csrf` 不是 HttpOnly，前端 JavaScript 读取后通过 `X-CSRF-Token` 请求头发送。
- `SameSite=Lax` 允许 OAuth 回调跳转携带 Cookie，同时防止跨站 POST 的 CSRF。
- 本地开发 HTTP 下 `Secure=false`；生产环境必须 `Secure=true`。

### 4. API Base URL 环境变量

```text
# 浏览器端（同源）
NEXT_PUBLIC_API_BASE_URL=/api/v1

# 服务端端（反向代理或直连后端）
API_BASE_URL=http://localhost:8080/api/v1     # 本地开发
API_BASE_URL=http://go-backend:8080/api/v1    # Docker/容器
API_BASE_URL=/api/v1                           # 同进程反向代理
```

### 5. Server-to-Backend 请求

服务端渲染时，Next.js Server Component 通过 `next/headers` 的 `cookies()` 读取 `up_session`，以 `Cookie` 请求头转发给后端：

```ts
headers["Cookie"] = `up_session=${sessionCookie.value}`;
```

服务端到后端的请求不需要 CSRF Token（CSRF 防护仅适用于浏览器发起的请求）。

服务端请求必须使用 `cache: "no-store"` 避免缓存包含用户数据的响应。

### 6. Browser-to-API 请求

浏览器端通过 `fetch` 同源调用 `/api/v1/*`：

- GET 请求：`credentials: "same-origin"`
- 写操作（POST/PUT/PATCH/DELETE）：附加 `X-CSRF-Token` 请求头
- FormData 请求（如头像上传）：不设置 `Content-Type`，由浏览器自动添加 boundary

### 7. OAuth 回调域名

OAuth 回调地址必须使用与前端相同的域名：

```text
https://pass.example.com/oauth2/callback
```

回调由后端处理，不在前端路由中暴露。后端校验 `state`、`nonce`、精确回调地址后，设置 `up_session` Cookie 并 303 重定向到前端。

## Alternatives Considered

### 跨域部署（前端和后端不同域名）

- 优点：前后端可独立部署和扩缩容
- 缺点：需要 CORS 配置；Cookie 需要 `SameSite=None; Secure`，在部分浏览器中被阻止；CSRF 防护更复杂
- 不选：增加复杂度且无明确收益

### 前端内嵌 API（Next.js API Routes 转发）

- 优点：前端和后端完全同源，无 CORS
- 缺点：增加一层转发，延迟和运维成本上升；Next.js API Route 不适合高频请求
- 不选：反向代理已解决同源问题，不需要额外转发层

## Consequences

- 法律文件（隐私政策）中的 Cookie 名称必须更新为 `up_session` / `up_csrf`
- `server-session.ts` 中的 `SESSION_COOKIE_NAME` 从 `"session"` 改为 `"up_session"`
- `browser-http-client.ts` 中的 Cookie 读取正则从 `csrf_token` 改为 `up_csrf`
- 新增 `CSRF_COOKIE_NAME` 和 `CSRF_HEADER_NAME` 常量
- 后端必须按统一名称设置和读取 Cookie
- 本地开发需要配置反向代理或使用 Next.js rewrites 将 `/api/v1/*` 代理到 `localhost:8080`
- 所有 Cookie 在同一域名下，不需要跨域配置

## Implementation Notes

- Cookie 常量：`src/lib/api/constants.ts`（新增）
- 服务端 Session：`src/lib/api/server/server-session.ts`（更新常量）
- 浏览器 HTTP 客户端：`src/lib/api/browser/browser-http-client.ts`（更新 CSRF Cookie 名）
- 法律文件：`src/features/legal/data/privacy-sections.ts`（更新 Cookie 名称）
- 环境变量示例：`.env.example`（新增或更新）
- Next.js rewrites（本地开发代理）：`next.config.ts`

## Follow-up

- 后端确认 Cookie Domain 是否需要包含子域名（`.example.com` vs `pass.example.com`）
- 后端确认 Session 过期策略和滑动续期
- 后端确认 CSRF Token 的生成和校验方式（HMAC-based vs random + server state）
- 评估是否需要在法律文件生效前完成 Cookie 名称同步
- 后端实现重认证挑战时，确认是否需要额外的 Challenge Cookie
