# ADR-0003: 头像上传校验与安全预览

- Status: Accepted
- Date: 2026-08-05
- Owners: United Pass frontend team

## Context

账户中心原先允许用户填写头像 URL，会触发浏览器向外部图片服务发起请求，可能泄露网络信息并引入不受控内容。直接预览用户选择的原始文件也会保留元数据，并让格式声明与真实内容不一致的文件过早进入展示链路。

当前阶段没有头像上传后端，仅需要安全、可替换的 Mock 交互。任何浏览器校验都不能替代服务端的文件安全处理。

## Decision

1. 移除用户可编辑的头像 URL，仅提供本地文件选择。
2. 只接受 PNG、JPEG、WebP，最大 2 MiB；SVG、GIF 和其他格式全部拒绝。
3. 在解码前比对声明 MIME 与真实文件签名，并读取图片头限制宽高、总像素和异常结构；现有头像只接受 `/api/v1/media/avatars/` 下的同源受控路径。
4. 使用 `createImageBitmap` 解码并校验解码尺寸与文件头一致，再绘制到最大边长 1024 像素的 Canvas，重新编码为 WebP 预览。页面不直接展示原始文件，不上传原文件，也不写入浏览器存储。
5. 使用 Semi Design Button 触发隐藏的原生文件选择器。当前不使用 Semi Upload 的默认文件生命周期，避免组件在项目安全校验和重新编码前生成或展示原始文件预览。
6. 真实 API 必须在服务端重新执行大小、签名、解码、尺寸和像素限制，剥离元数据、重新编码，并从同源或受控媒体域提供结果。前端结果不构成信任证明。

## Alternatives Considered

- 保留 HTTPS 头像 URL：实现简单，但无法阻止外部请求跟踪，也无法控制远端内容变化。
- 使用原始文件的 Object URL 或 Data URL 直接预览：响应快，但会绕过重新编码和元数据清理边界。
- 只校验扩展名或浏览器 MIME：两者都由文件提供方影响，不能确认真实内容。
- 直接采用 Semi Upload 默认流程：能统一上传视觉，但当前 Mock 需要保证原文件在安全处理完成前不进入预览和网络流程；后续可在确认自定义生命周期后重新评估。

## Consequences

- 头像预览不再发起用户指定的外部请求，也不会保留原文件元数据或动画帧。
- 老旧且缺少 `createImageBitmap` 或 WebP Canvas 编码能力的浏览器会收到明确拒绝提示。
- 大图片解码和重新编码会消耗短时 CPU；文件字节、尺寸与像素限制降低资源滥用风险，但服务端仍须有独立的超时、内存和解码隔离措施。
- Mock 刷新后恢复，不能被误认为头像已上传成功。

## Implementation Notes

- 文件校验与重新编码：`src/features/account/utils/avatar-file.ts`
- 账户资料交互：`src/features/account/components/account-overview.tsx`
- 真实 API 草案：`POST /api/v1/me/avatar`，见 `docs/api-contracts.md`

## Follow-up

- 后端实现隔离的图片解码、重编码、存储和媒体域策略。
- 增加 PNG、JPEG、WebP 有效样本以及伪造 MIME、超尺寸、损坏头和解码失败的自动化测试。
- 评估头像裁剪、方向处理、配额和旧头像清理策略。
