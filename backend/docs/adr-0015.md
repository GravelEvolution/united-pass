# ADR-0015: Production account lifecycle and final Mock-seam replacement

- Status: Accepted
- Date: 2026-08-16
- Owners: United Pass backend team
- Depends on: ADR-0002, ADR-0007, ADR-0008, ADR-0009, ADR-0011, ADR-0014

## Context

The frontend freeze originally contained product prototypes for public
registration, password recovery, email verification, profile/avatar/contact
changes, the administration dashboard and parts of OAuth application/client
management. A production data-source mode must not silently execute a Mock
mutation or navigate as though a server session or durable write exists.

Credentials and verification codes remain ZITADEL-owned, while stable user
identity, explicit provider links, personas and profile data remain United
Pass-owned. Completing these seams therefore requires cross-store settlement
rules instead of recreating identity-provider credential logic in Go.

## Decision

### Public account lifecycle

`POST /api/v1/registrations` creates a ZITADEL human user first, then creates
the pending stable United Pass user, Consumer Persona and exact
`(provider, provider_tenant_id, provider_subject)` link in one PostgreSQL
transaction. A local failure compensates by deleting the provider user. The
pending user cannot authenticate until the provider confirms the exact email
and PostgreSQL activates the same linked user.

Registration verification and password-reset links carry encrypted,
short-lived local capabilities containing only version, purpose, stable
`userId` and expiry. They contain no email, provider subject, password or
verification code. Provider codes remain provider-generated and
provider-validated. Password-reset lookup requires an active, locally verified
user behind an explicit identity link, while the public request response is
always the same `202` after validation and rate limiting.

A successful password reset reuses the security-state mutation ledger. It
records the provider outcome, advances the user's security epoch and revokes
older sessions before returning success. Ambiguous provider outcomes or local
settlement failures return an explicit degraded error and remain recoverable;
they never report a false success.

### Profile, avatar and verified contacts

`PATCH /api/v1/me` changes only display name and nickname. Avatar upload is a
separate multipart endpoint: the server caps bytes and decoded pixels, accepts
only PNG/JPEG/WebP signatures, decodes, resizes when necessary, strips metadata
by re-encoding PNG and stores the controlled bytes under a random media ID.
Public avatar URLs contain no user ID and serve only sanitized PNG with
`nosniff`, ETag and immutable caching.

Email and phone changes use a durable, hashed opaque request capability bound
to both stable user and current session. Creating a new request supersedes the
prior active request of the same kind. Verification uses a short claim lease so
only one provider call is live; invalid codes consume one of five attempts,
infrastructure failures do not. After provider verification, PostgreSQL mirrors
the exact value and terminally clears the stored contact value in one
transaction. Provider readback repairs the provider-committed/response-lost
boundary.

### Dashboard and frontend data-source boundary

The dashboard is a PostgreSQL read model. `user.read` independently unlocks
user and employee counts, `application.read` application counts, and
`audit.read` the 30-day denied count plus three already-redacted recent events.
An unrelated administration capability may render the overview shell but does
not reveal unauthorized aggregates.

Every production `UnitedPassQueries` and `UnitedPassCommands` seam now has a
real HTTP implementation. `NEXT_PUBLIC_USE_MOCK=true` remains an explicit
development/test fixture choice only; there is no production fallback.
Credential-bearing login, registration, email verification and password
recovery always use the real API so a fixture can never manufacture an
authenticated state. Recovery Codes remain provider-deferred and expose no
fake generate/rotate action.

## Alternatives Considered

- Store passwords or verification codes locally: rejected because ZITADEL is
  the credential authority and duplicate credential stores enlarge the attack
  surface.
- Resolve users by email during reset or activation: rejected because email is
  mutable and cannot replace an explicit provider identity link.
- Mark a local user active before provider email verification: rejected because
  it creates an authentication/account-recovery race and an unverified identity.
- Store avatars exactly as uploaded or accept external URLs: rejected because
  active formats, metadata, content-type confusion and third-party tracking
  would cross the controlled media boundary.
- Return all dashboard aggregates after one broad “admin” check: rejected
  because it leaks independently protected user, application and audit data.
- Keep incomplete production methods backed by Mock: rejected because success
  would not represent durable server state.

## Consequences

- Migration v12 adds sanitized avatar storage and durable contact-change
  requests.
- Public lifecycle endpoints require PostgreSQL, Redis rate limiting,
  encryption, ZITADEL management access and a configured public origin.
- Redis construction failure aborts startup; a process must not run with
  credential endpoints whose required fail-closed limiter was not constructed.
- Rate limiting uses the transport peer because no trusted-proxy configuration
  exists. Original client IP attribution requires a future explicit proxy
  allow-list; caller-controlled forwarding headers are never trusted.
- The frontend Mock data source remains useful for deterministic component and
  unit tests but is not a production security or persistence implementation.

## Security Considerations

- Logged-out credential endpoints require `application/json`, an exact
  same-origin `Origin` and non-cross-site Fetch Metadata. Login CSRF cannot use
  the session-bound double-submit token because no session exists yet.
- Raw lifecycle capabilities, contact request IDs, passwords and codes are not
  logged or stored. Redis keys receive only hashed identifiers/capabilities.
- Pending users cannot authenticate; password reset does not reveal account
  existence; contact requests cannot move between users or sessions.
- Provider calls have bounded deadlines. Cross-store settlement is explicit,
  retryable and covered by provider readback or compensation.
- Server shutdown returns joined HTTP/Redis/provider close errors so failed
  teardown is observable instead of being reported as successful.
