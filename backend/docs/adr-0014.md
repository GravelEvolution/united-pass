# ADR-0014: Launch privacy rights and controlled legal publication

- Status: Accepted
- Date: 2026-08-11
- Depends on: ADR-0002, ADR-0007, ADR-0013

## Context

Phase 8 is the production-launch closure. The existing legal text is still a
draft and its review files are not a legal opinion or approval. A deployment
must therefore not make those pages appear effective. Users also need working
personal-data export and account-deletion rights without exposing credentials,
creating cross-user downloads, or turning provider/local failures into partial
untracked deletion.

## Decision

### Controlled legal publication

The exact bytes of the frontend legal data modules are pinned by SHA-256 in a
backend allow-list and the frontend manifest. `cmd/legal-publish` is the only
publication writer. It requires an existing operator, approval reference,
approver, effective time and explicit `--confirm-approved`. PostgreSQL stores
that immutable tuple and the audit event. A version/digest mismatch is rejected.

`GET /api/v1/legal-documents` exposes only the current document identity and
effective/scheduled status; it omits approver and ticket information. The
frontend displays an effective date only when backend version and digest match
its own manifest. Missing/unreachable/mismatched state remains “暂未生效”. Code
deployment and AI review can never activate a document.

### Personal-data export

`account.data_export` step-up is bound to the current stable user ID. A durable
worker builds a fixed JSON document containing the requester's profile,
personas, identity links, optional employee profile, OAuth grants and pending
deletion state. A provider-directory snapshot is included only when an exact
provider/tenant/subject identity link binds it to the requester. It never reads passwords, MFA material, tokens, provider
sessions, secrets or unrelated audit records. The URL is owner-bound and
anti-enumerating. Bytes expire after 15 minutes and are physically cleared by
the worker; terminal job metadata is pruned after 30 days. The canonical
security event remains the longer-lived request proof.

### Delayed account deletion

`account.delete` step-up starts a 30-day cooling period. Only a pending request
before `execute_after` can be cancelled. After the deadline a durable worker:

1. deletes the provider user (provider not-found is already converged);
2. persists `provider_deleted` proof;
3. purges local Redis sessions, retrying if Redis is unavailable;
4. transactionally removes identity links, personas, employee profile, grants,
   exactly linked provider-directory staging rows/conflicts, password intents
   and export artifacts, then disables and anonymises the
   stable user row and commits the completion audit.

Provider deletion is never repeated after its proof is durable. Stale work is
reclaimed; transient failures retry at a bounded cadence and become explicit
`failed` after ten provider attempts. Stable user IDs and minimal security
events remain to preserve referential and security-audit integrity; they are
not presented as an active profile.

## Consequences

- Migration v11 adds legal publication, data-export and deletion state.
- Production deletion requires the ZITADEL adapter plus PostgreSQL and Redis.
- A completed user is disabled and its security epoch is incremented, so any
  session artifact missed outside the worker's normal path still fails closed.
- Substantive retention/legal obligations remain subject to external legal
  approval. This ADR records technical behavior, not legal sufficiency.
