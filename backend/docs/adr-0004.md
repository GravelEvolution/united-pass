# ADR-0004: OAuth Application and Client Management Architecture

- Status: Accepted
- Date: 2026-08-06
- Owners: United Pass backend team

Phase 2 is the OAuth **management plane**: Application and OAuth Client
metadata, lifecycle, provisioning orchestration, permissions, audit, and
secret handling. It is NOT the OAuth **protocol execution plane**: no
`/oauth/authorize`, authorization codes, token endpoint, refresh tokens,
consent execution, grant persistence, PKCE verification, JWKS, discovery,
or dynamic client registration (Phase 3+).

ZITADEL v2.71.0 continues to own OAuth/OIDC protocol behavior. The Go
backend owns local metadata, the management API, authorization, audit,
provider provisioning orchestration, provider ID mapping, one-time secret
delivery, and lifecycle/consistency.

## Context

The frozen frontend contract (`../frontend/docs/api-contracts.md`,
`adr-0005.md`, `src/features/applications/types.ts`) separates Application
and OAuth Client, defines three Client Profiles
(`web_server`, `spa_mobile`, `server_to_server`), cursor pagination,
field-error envelopes, permission identifiers
(`application.read` / `application.manage` / `application.secret.rotate`),
and requires reauthentication for high-risk operations.

All ZITADEL API facts below were verified against the pinned SDK
(`github.com/zitadel/zitadel-go/v3 v3.29.2`, Management API v1 generated
code) and the local real v2.71.0 instance, not from memory.

## Contract Gap Review

Gaps found while reading the frozen contract, and their resolutions:

### G1. `ownerName` input vs stable ownership

`ApplicationCreateInput` / `ApplicationUpdateInput` carry `ownerName`
(display text). Ownership must never be resolved from a display name.

**Resolution (security contract fix):** inputs switch to `ownerId` (stable
United Pass user ID). Responses carry both `ownerId` and `ownerName`
(`ownerName` is derived server-side from the authoritative user record).
The backend validates that `ownerId` exists before accepting it.
Synchronized to: this ADR, OpenAPI, `frontend/docs/api-contracts.md`,
`frontend/src/features/applications/types.ts`, the mock data source, and
form submission fields (minimal contract sync only; no page rework).

### G2. `rotateClientSecret` signature

The data source interface declares `rotateClientSecret(clientId)` while the
frozen REST path is
`POST /api/v1/admin/applications/{applicationId}/clients/{clientId}/secret-rotations`.
Acting on `clientId` alone would bypass the Application resource boundary.

**Resolution:** the method signature becomes
`rotateClientSecret(applicationId, clientId)`; the backend loads the Client
and asserts `client.application_id == path.applicationId` (404 on mismatch,
consistent with the anti-enumeration policy).

### G3. standalone `createApplication()`

The data source declares `createApplication()`, but the frozen REST
contract only defines `POST /api/v1/admin/applications/with-initial-client`.
A standalone creation endpoint would need a designed Draft-without-Client
state, which is not in the frozen contract.

**Resolution:** the backend implements only `with-initial-client` for
creation. The standalone `createApplication` command is removed from the
data source contract as part of the minimal contract sync (mock object
keeps no unreachable method). No new public endpoint is invented.

### G4. `consentMode` for `server_to_server`

Client Credentials flows have no user consent, but the unified type carries
`consentMode`.

**Resolution:** the field stays present and non-nullable (frontend type
compatibility), but for `server_to_server` the only accepted value is
`always` and it is recorded as not-applicable metadata; it never influences
protocol configuration. `trusted_first_party` remains unsupported (422).

### G5. `grants` and `auditEntries` in Application detail

P3 grants and the full audit UI are not implemented. No fake data.

**Resolution:** `grants` returns a real (initially empty) array backed by
the grants table introduced when P3 lands — in P2 it is always `[]`.
`auditEntries` returns only security events the P2 `SecurityEventRecorder`
actually recorded for that Application.

## Decision

### 1. Application/Client to ZITADEL mapping

- **All United Pass Applications share one ZITADEL Project**, identified by
  `UP_AUTH_PROVIDER_PROJECT_ID` (required for the `zitadel` provisioner;
  verified with `GetProjectByID` at startup — fail closed, surfaced through
  `/readyz`). Alternatives considered below.
- Each United Pass OAuth Client maps to **one ZITADEL OIDC Application**
  (`AddOIDCApp`) inside that project:

| United Pass profile | ZITADEL `AddOIDCApp` mapping |
| --- | --- |
| `web_server` | `AppType=WEB`, `AuthMethodType=BASIC`, grant types `AUTHORIZATION_CODE + REFRESH_TOKEN`, response type `CODE`, redirect URIs required |
| `spa_mobile` | `AppType=USER_AGENT`, `AuthMethodType=NONE`, grant types `AUTHORIZATION_CODE + REFRESH_TOKEN`, response type `CODE`; PKCE (S256) is enforced by ZITADEL for `USER_AGENT` apps |
| `server_to_server` | `AppType=WEB`, `AuthMethodType=BASIC`, no redirect URIs; ZITADEL v2 serves `grant_type=client_credentials` at the token endpoint for confidential apps (the app.v1 grant-type enum has no client_credentials value; verified against the v2.71 endpoints documentation and to be confirmed on the real instance in P2.8 acceptance) |

- `UpdateOIDCAppConfig` updates redirect/logout URIs and name;
  `DeactivateApp` / `ReactivateApp` map to disable/enable; `RemoveApp`
  maps to delete; `RegenerateOIDCClientSecret` maps to rotation.
- **ID separation:** local `application_id` (`app_…`), `client_id`
  (`clt_…`) and secret IDs (`sec_…`) are United Pass generated and stable.
  Provider identifiers are stored only as mapping columns
  (`provider`, `provider_project_id`, `provider_application_id`,
  `provider_client_id`) and are never used as United Pass identities.
  A provider swap leaves local IDs intact.

### 2. Cross-store consistency (PostgreSQL × ZITADEL)

No database transaction may span an external network call. Every
provisioning flow uses an explicit state machine plus recorded operations:

```text
provisioning_status: provisioning → provisioned
                                → provisioning_failed
                     deleting   → delete_failed
```

The public `status` remains `active | disabled`; a resource only becomes
publicly visible (`status` exposed in list/detail) once
`provisioning_status = provisioned`. Internal provisioning rows are never
reported as Active and never appear in ordinary lists.

`with-initial-client` atomic semantics:

1. Validate + authorize + rate-limit.
2. Local transaction: insert Application (`provisioning`), initial Client
   (`provisioning`), and a `provider_operations` row (`pending`) — commit.
   No transaction stays open across the provider call.
3. Provider call (`AddOIDCApp`). The `provider_operations` row carries an
   idempotency key so retries never create duplicate provider clients.
4. Local transaction: store provider IDs + secret metadata, flip to
   `provisioned`, mark the operation `succeeded` — commit.
5. Provider failure → rows marked `provisioning_failed` (hidden from
   lists), operation `failed`, safe 5xx.
6. Provider success + local commit failure → compensating `RemoveApp`; if
   compensation also fails, a `provider_reconciliation_jobs` row records
   the recoverable cleanup and a
   `oauth_client.provider_reconciliation_required` security event.

Deletion follows the same pattern (`deleting` → provider `RemoveApp` →
local delete → or `delete_failed` + reconciliation job).

Tables: `oauth_applications`, `oauth_clients`, `oauth_client_redirect_uris`,
`oauth_client_scopes`, `oauth_client_secret_records`,
`oauth_provider_operations`, `provider_reconciliation_jobs`,
`security_events`. No table exists without a real purpose; no secrets are
stored anywhere.

### 3. Client Profiles (P2 MVP)

Enforced by the backend domain layer (frontend config is advisory only):

| Rule | web_server | spa_mobile | server_to_server |
| --- | --- | --- | --- |
| clientType | confidential | public | confidential |
| grantTypes | authorization_code, refresh_token | authorization_code, refresh_token | client_credentials |
| tokenEndpointAuthMethod | client_secret_basic | none | client_secret_basic |
| redirect URIs | required ≥1 | required ≥1 | forbidden (must be empty) |
| openid | allowed, not required | allowed, not required | forbidden |
| consent | applicable | applicable | not applicable (`always` only) |
| secret | yes (one-time display) | never | yes (one-time display) |
| PKCE | n/a | S256 required (provider-enforced) | n/a |

Unsupported combinations return 422 field errors and never silently mutate
submitted values: `private_key_jwt`, `client_secret_post`, and
`trusted_first_party` are rejected in P2 (no provider support verified /
no security model reviewed). Submitted `grantTypes` /
`tokenEndpointAuthMethod` are validated against the profile; profile is the
stored authority.

### 4. Redirect URI security semantics

Backend is the only security boundary; rules apply identically to logout
URIs:

- Must be an absolute URI with scheme `https` (or `http` loopback
  exception below); parse failure → 422.
- Loopback exception: `http://localhost`, `http://127.0.0.1`,
  `http://[::1]` (any port, per RFC 8252 §7.1 — loopback ports are dynamic
  and not a prefix-matching risk). Plain hostnames other than loopback are
  rejected over `http`.
- No fragment, no userinfo, no wildcards, no embedded credentials.
- **No normalization:** no case folding of path, no port/path/trailing
  slash rewriting; the exact string is stored and, at authorization time
  (P3), matched exactly as registered.
- Duplicates rejected (unique constraint + 422 field error).
- Limits: ≤ 20 URIs per client, ≤ 2048 characters per URI.
- Custom schemes (native apps): **not supported in MVP** for `spa_mobile`;
  only `https` + loopback `http` are accepted. The profile bundles SPA and
  native clients today; native custom-scheme support requires its own ADR.

### 5. Scope Catalog

`GET /api/v1/admin/scopes` is the backend-authoritative catalog (mirrors
the frozen frontend catalog):

| scope | label | required | notes |
| --- | --- | --- | --- |
| `openid` | OpenID | false | optional for interactive profiles; forbidden for `server_to_server` |
| `profile` | 基本资料 | false | |
| `email` | 邮箱 | false | |
| `phone` | 手机号 | false | |
| `offline_access` | 离线访问 | false | only with `refresh_token` grant |
| `reporting:read` | 报表读取 | false | example business scope |

Unknown scopes → 422; duplicates are de-duplicated into a field error;
arbitrary unregistered scopes are never accepted. OAuth scopes are
delegated-access descriptors only — they never grant backend management
permissions.

### 6. Secret model

- Public clients never receive secrets (domain rule + provider mapping).
- Confidential secrets are generated by ZITADEL (`AddOIDCApp` /
  `RegenerateOIDCClientSecret`) and returned to United Pass once; United
  Pass forwards them in the creation/rotation response exactly once and
  never persists them.
- No secret-query endpoint exists. PostgreSQL, Redis, logs, tracing, audit
  payloads, and test snapshots store only secret **metadata**
  (`secret_id`, `label`, `created_at`, `rotated_at`, provider linkage).
- Secret responses set `Cache-Control: no-store` and `Pragma: no-cache`.
- **Provider limitation (recorded):** ZITADEL v2.71
  `RegenerateOIDCClientSecret` returns only the new secret — no secret ID,
  no grace period; the previous secret is invalidated immediately. United
  Pass therefore: generates its own `secret_id`; returns
  `previousSecretExpiresAt` = rotation timestamp; keeps
  `UP_SECRET_ROTATION_GRACE_PERIOD` (default `0s`) configurable for
  providers that support overlap, documenting that the effective grace
  period against ZITADEL v2.71 is zero.
- Rotation requires reauthentication, rate limiting, audit, and
  single-winner concurrency control. A failed rotation never revokes a
  still-valid old secret. Provider success + local failure enters
  reconciliation. Secrets never appear in error text.

### 7. Permissions and reauthentication

Permissions are resolved server-side (fail closed): `application.read`,
`application.manage`, `application.secret.rotate`. Frontend-supplied
conclusions and role names are never trusted.

High-risk operations (delete Application, delete Client, rotate secret)
require a completed reauthentication grant. P2 introduces the
reauthentication contract:

- `POST /api/v1/auth/reauthentication` (session + CSRF): body carries
  `action`, optional `applicationId`/`clientId`, and `password`. The
  backend authenticates the **current session user** through the existing
  `Authenticator` (password; TOTP/passkey follow-up when the user has a
  second factor), returning either the grant immediately or a
  `reauthToken` challenge (`202`) with `availableMethods` /
  `passkeyRequestOptions`.
- `POST /api/v1/auth/reauthentication/mfa` completes the challenge
  (same atomic claim/consume pattern as login MFA).
- Challenge: random opaque ID; bound to user + session + action + target
  resource; 5-minute TTL; max 5 attempts; Redis loss only invalidates
  challenges (fail closed, never bypasses).
- Success produces a **single-use reauthentication grant** (random opaque
  token, 5-minute TTL, bound to the exact action + resource), submitted by
  the high-risk request as `X-Reauthentication-Token` and consumed
  atomically before the operation executes. Grants are never reusable,
  never cross-session, never cross-action.
- Provider session tokens never reach the browser; failures are generic
  (no account/MFA-state leakage); all outcomes are security events.

### 8. Audit boundary

`SecurityEventRecorder` persists rows into `security_events` (PostgreSQL)
in the same transaction as the audited mutation where possible:

```text
application.created / updated / enabled / disabled / deleted
oauth_client.created / updated / enabled / disabled / deleted
oauth_client.secret_rotated / secret_rotation_failed
oauth_client.provider_reconciliation_required
reauthentication.requested / succeeded / failed
```

Payload fields: `actor_user_id`, `application_id`, `client_id`,
`request_id`, `operation`, `result`, `occurred_at`, safe failure category.
Never included: secrets, tokens, cookies, passwords, TOTP codes, service
account keys, raw provider errors. This is a real persistence boundary,
not log-based audit; the full audit query/export system is a later phase.

### 9. Cursor pagination

`GET /api/v1/admin/applications` supports `cursor`, `limit` (1–100,
default 20), `query` (server-side name/description search), `sort`
(`-updatedAt` default; `updatedAt`, `-createdAt`, `createdAt`, `name`,
`-name`), `status`, `audience`, `ownerId`.

- Stable ordering always ends with the ID tie-breaker
  (e.g. `updated_at DESC, application_id DESC`).
- Cursors are base64url-encoded JSON **signed with HMAC** using a key
  derived from `UP_SESSION_ENCRYPTION_KEY` (versioned); they bind the sort
  and filter state. Tampered/unknown cursors → 400. No raw offsets.
- Permission filtering happens before response assembly; no fake totals;
  response envelope is `{items, page:{nextCursor, hasMore}}`.

## Alternatives Considered

- **One ZITADEL project per Application:** cleaner console isolation and
  cascading project deletion, but doubles the provider surface per
  application (project + app creation/deletion, two-phase compensation)
  and adds a project lifecycle to reconcile. The shared-project model keeps
  provisioning to a single provider call per client and reuses the existing
  `UP_AUTH_PROVIDER_PROJECT_ID` configuration; ZITADEL-side cleanup is
  per-app via `RemoveApp`. Chosen alternative.
- **ZITADEL as the system of record (thin proxy):** rejected — United Pass
  needs its own stable IDs, business metadata, permissions, and audit that
  survive provider changes; ZITADEL remains the protocol engine only.
- **Holding a SQL transaction open across the provider call:** rejected —
  network latency/failures would pin connections and risk inconsistency;
  explicit state machine + compensation chosen instead.
- **Storing redirect URIs/scopes as unconstrained JSONB:** rejected — not
  queryable or constrainable; normalized tables with unique constraints.
- **Client Credentials via a dedicated grant-type registration:** the
  pinned ZITADEL app.v1 enum has no client_credentials value; the token
  endpoint serves it for confidential apps (verified in docs, to be
  confirmed in acceptance). No unsupported field is guessed.

## Consequences

- New packages: `internal/applications` (domain + use cases),
  `internal/adapters/postgres` repository extensions,
  `internal/adapters/zitadel` provisioner, `internal/adapters/redis`
  reauthentication store, `internal/adapters/httpapi` admin handlers.
- Migration `00002_oauth_applications.sql` (does not touch P1 tables).
- OpenAPI gains the admin application/client/scope and reauthentication
  paths; frontend contract sync limited to G1–G3 fixes.
- ZITADEL requires a provisioned project (`zitadel-init.sh` creates it
  idempotently and records the ID in `.zitadel/init-state.json`).

## Security Considerations

- Fail closed everywhere: missing authorizer, Redis outage during
  reauth/rate limiting, provider errors on high-risk paths.
- Secrets: one-time display, `no-store`, never persisted, never logged,
  never in audit payloads or error text.
- Redirect/logout URIs: exact-match semantics, no normalization, no
  wildcards, loopback-only HTTP exception.
- Resource boundary: `client.application_id == path.applicationId`
  enforced on every nested route; inaccessible resources answer 404.
- Reauthentication grants are single-use, action-bound, session-bound.
- Provider IDs never leak into United Pass identities or API responses.

## Implementation Notes

- P2 regression gate: any change to bootstrap/session middleware/CSRF/
  permission resolver/provider adapter/config validation reruns the full
  P1 suite.
- **Client name uniqueness (decided):** client names are unique per
  application among live (non-deleted) clients — duplicate names confuse
  operators and audit trails. Application names are likewise unique among
  live applications. Enforced with partial unique indexes.
- ZITADEL version stays pinned at v2.71.0; no incidental upgrades.
- Real-provider acceptance (P2.8) runs on the `up-zitadel` container
  machine; volumes preserved; no secrets printed.

## Follow-up

- P2.8 acceptance must confirm `client_credentials` at the token endpoint
  for provisioned `server_to_server` clients; if v2.71 refuses, the
  limitation is recorded and the profile is flagged (never faked).
- Secret rotation grace period becomes effective only with a provider that
  supports overlapping secrets.
- Full audit query/export, grants, and consent execution land in later
  phases (P3/P7).
