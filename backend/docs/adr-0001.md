# ADR-0001: Backend service boundaries, HTTP stack and foundation architecture

- Status: Accepted
- Date: 2026-08-05
- Owners: United Pass backend team

## Context

The United Pass frontend has reached a frozen contract (`../frontend/docs/frontend-freeze-v1.md`) covering authentication, account center, administration, OAuth application/client management, consent, providers, policies and audit. The Go backend must now be built to replace the frontend mock data source with real HTTP APIs while preserving every product invariant defined in `AGENTS.md`.

Before any business feature is implemented, the foundation must establish:

1. A correct Go module path and entry point layout.
2. A typed, validated configuration layer so secrets and runtime knobs are never scattered as `os.Getenv` calls.
3. Structured logging that flows request IDs into logs, error responses and future audit records.
4. An HTTP server with production-grade timeouts, panic recovery, access logging, security headers and request-body limits.
5. A unified API error envelope matching the frontend contract.
6. Operational endpoints (`/healthz`, `/readyz`) that do not leak dependency details.
7. Graceful shutdown that drains in-flight requests within a configured timeout.
8. A dependency direction that keeps domain and application logic free of HTTP, database and SDK concerns.

The frontend contract (`api-contracts.md`, `frontend-freeze-v1.md`) and ADRs 0004/0005/0006 fix the error envelope shape, cursor pagination, cookie names (`up_session`, `up_csrf`), the CSRF header (`X-CSRF-Token`), the Application/Client separation, and the server/browser HTTP client split. Phase 0 implements none of these business behaviors, but the foundation must be compatible with all of them.

## Decision

### 1. Module path and entry point

The module path is `github.com/GravelEvolution/united-pass/backend`. The single entry point is `cmd/api/main.go`. `main.go` only loads configuration, constructs the logger, builds the server, starts it and performs graceful shutdown. No business logic lives in `main`.

### 2. HTTP stack: net/http + chi/v5 + slog

- The HTTP server is `net/http`'s `http.Server`, configured with `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout` and a request-body limit.
- Routing and route composition use `github.com/go-chi/chi/v5`. Chi is the only approved initial router dependency.
- All handlers and middleware are standard `net/http` types: `http.Handler`, `http.HandlerFunc`, and `func(http.Handler) http.Handler`. Chi-specific types stay inside `internal/bootstrap` and `internal/adapters/httpapi`.
- Structured logging uses `log/slog`. Production emits JSON; development emits text.
- Domain and application packages must not import Chi, `net/http` handlers, SQL implementations or any external SDK.

### 3. Directory structure

```
backend/
├── cmd/api/main.go              # Entry point: config, logging, server, shutdown
├── internal/
│   ├── bootstrap/               # Wires router, middleware and http.Server (chi lives here)
│   ├── config/                  # Typed, validated configuration
│   ├── adapters/
│   │   └── httpapi/             # HTTP middleware, error envelope, health handlers
│   │       └── request/         # Per-request context helpers (request ID)
│   └── platform/
│       └── observability/       # slog logger construction
├── docs/                        # Backend ADRs
└── .github/workflows/           # CI
```

Packages are added only when they have a real responsibility. No empty placeholder directories exist. Generic dumping-ground packages (`utils`, `helpers`, `common`, `models`) are forbidden.

### 4. Dependency direction

Dependencies point inward:

```
HTTP / PostgreSQL / Feishu / ZITADEL / Cerbos adapters
                        ↓
                 application use cases
                        ↓
                     domain rules
```

- `internal/adapters/httpapi` imports `internal/config` and `internal/platform/observability` types but not domain packages (none exist yet in Phase 0).
- `internal/bootstrap` imports `httpapi`, `config` and `observability` to assemble the server.
- `cmd/api/main.go` imports `bootstrap`, `config` and `observability` only.
- Future domain packages (`identity`, `applications`, `consent`, etc.) will not import HTTP, Chi, SQL or SDK packages.

### 5. Configuration

Configuration is loaded once at startup through `internal/config.Load()`. Every value is typed (string, `time.Duration`, `int64`, typed `Environment`). Production triggers stricter validation (e.g. shutdown timeout capped, body size capped). The rest of the codebase never calls `os.Getenv` directly.

### 6. Request IDs

Every request gets a request ID. The `RequestID` middleware accepts a valid upstream `X-Request-ID` (alphanumeric, dash, underscore, colon; 8–128 chars) or generates a cryptographically random `req_`-prefixed ID. The ID is stored in the request context, echoed on the response header, embedded in every error envelope, and included in access logs. Invalid upstream IDs are rejected and regenerated to prevent log poisoning.

### 7. Unified error envelope

All failures return the frontend-mandated shape:

```json
{
  "error": {
    "code": "internal.unexpected",
    "message": "服务暂时无法处理该请求。",
    "requestId": "req_..."
  }
}
```

`code` is stable and machine-readable; `message` is safe for user display; `requestId` correlates logs and audit; `fieldErrors` is an array. Internal details (SQL, stack traces, hostnames, tokens) are never exposed.

### 8. Operational endpoints

- `GET /healthz` — process is alive. Never depends on downstream services. Returns `{"status":"ok"}`.
- `GET /readyz` — process is ready to serve traffic. Runs registered `ReadinessChecker`s. Phase 0 registers none (no database). Failures return 503 without leaking dependency names or error text.

### 9. Graceful shutdown

`main` listens for `SIGINT`/`SIGTERM`. On signal it stops accepting new requests and waits up to `ShutdownTimeout` for in-flight handlers. Shutdown failures are logged as structured errors. A second signal restores default behavior and forces exit.

## Alternatives Considered

### Gin / Fiber / Echo / Beego / Iris

Rejected. These frameworks impose their own context types, middleware signatures, error handling and often JSON validators, which would violate the requirement that handlers stay compatible with standard `net/http` types and would leak framework types into domain code. They also bundle features (ORM hooks, render engines) that overlap with future deliberate choices. Chi provides routing and route composition while staying on standard `net/http` interfaces, so it is the minimal approved option.

### Wire / Fx (dependency injection frameworks)

Rejected for Phase 0. The wiring is small enough to express explicitly in `bootstrap`. A DI framework would add compile-time or runtime magic, configuration conventions and a learning curve without paying for itself until the dependency graph is much larger. If wiring becomes painful in later phases, an ADR will revisit this.

### ORM (GORM, Ent) / SQL builder (sqlx, squirrel) / database driver / migration tool

Out of scope for Phase 0. No database exists yet. These will be evaluated via ADR before Phase 2 introduces PostgreSQL.

### Custom logger (zap, zerolog)

Rejected. `log/slog` is the standard library structured logger, satisfies the structured-field requirement, and avoids a new dependency. It integrates with the standard `io.Writer` model and can be swapped to a JSON or text handler per environment.

### http.ServeMux instead of Chi

Considered. The standard library `ServeMux` (pre-Go 1.22) lacked method-based routing and route parameters. Go 1.22+ added method and wildcard patterns, but Chi is already explicitly approved in `AGENTS.md`, provides mature middleware composition, and keeps route grouping (`/api/v1`) clean. Chi-specific calls are confined to `bootstrap` so the standard-interface requirement is preserved.

## Consequences

- The foundation is compatible with the frozen frontend contract: error envelope, request IDs, cookie names and API version prefix are all ready for Phase 1.
- Adding a business route in later phases means: define a domain package, implement an HTTP handler in `httpapi`, mount it under `/api/v1` in `bootstrap`. Domain code never sees Chi.
- Production startup fails fast when configuration is invalid, preventing silent misconfiguration.
- Every request is observable end-to-end via request ID in logs, responses and future audit records.
- Panic in any handler is contained and logged, never crashing the process.
- The dependency surface is minimal: only `github.com/go-chi/chi/v5` beyond the standard library.
- Later phases must respect the dependency direction: adapters import use cases, use cases import domain, never the reverse.

## Security Considerations

- Request IDs are generated with `crypto/rand` and validated on input to prevent log poisoning and header injection.
- Request bodies are capped via `http.MaxBytesReader` to mitigate resource-exhaustion attacks.
- Security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Cache-Control: no-store`) are applied to every response.
- Error envelopes never leak internal details (stack traces, SQL, hostnames, tokens, provider responses).
- `/healthz` and `/readyz` expose no dependency internals publicly.
- Production configuration validation prevents unsafe defaults (e.g. oversized body limits, excessive shutdown timeouts).
- No secrets are logged; the access log records only method, path, status, duration and request ID.

## Implementation Notes

- Module: `github.com/GravelEvolution/united-pass/backend`, Go 1.26.5.
- Configuration environment variables are prefixed `UP_` (e.g. `UP_HTTP_ADDR`, `UP_ENVIRONMENT`, `UP_LOG_LEVEL`).
- The `ReadinessChecker` interface in `internal/adapters/httpapi/health.go` is the extension point for future database, Cerbos and Provider health checks.
- The `request` subpackage owns the context key for request IDs, preventing collisions.
- `statusRecorder` tracks `wroteHeader` so only the first `WriteHeader` call is recorded and forwarded, matching `net/http` semantics. It implements `Unwrap()` for `http.ResponseController` compatibility.
- `Recovery` accepts `config.Config` and installs its own `statusRecorder` to detect whether the handler already committed the response before panicking. In production the raw panic value is redacted from logs; the stack trace is logged at debug level.
- `MaxBodyBytes` wraps the request body in `http.MaxBytesReader`. The middleware itself does not return 413 — handlers must map `*http.MaxBytesError` to `WriteRequestBodyTooLarge` in their decode path.
- The CI workflow lives at the repository root `.github/workflows/backend.yml` (not nested under `backend/`) so GitHub Actions can discover it.

## Follow-up

- Phase 1 will add the authentication-provider adapter, session cookie (`up_session`), CSRF validation (`up_csrf` / `X-CSRF-Token`), `GET /api/v1/me`, and permission capabilities.
- The OpenAPI skeleton has been introduced under `backend/openapi/openapi.yaml` covering operational endpoints (`/healthz`, `/readyz`), the error envelope, and the request-ID header. Phase 1 must extend it with session and user endpoints as each is implemented.
- ADR-0002+ will record decisions for PostgreSQL access, migration tooling, ZITADEL integration, Cerbos integration, session architecture and ID generation before the corresponding phases begin.
- Frontend contract reconciliation is complete: `api-contracts.md` is Frozen v1, `frontend-freeze-v1.md` defers to it for API paths, and OpenAPI is declared the machine-readable contract once established.
