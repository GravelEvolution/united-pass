# ADR-0006: Account Security — Sessions, Factors and Step-up Reauthentication (Phase 4)

## Status

**Accepted (P4.0 architecture gate).** No Phase 4 business code may be
written before this ADR lands. This document freezes the session inventory
data model, the session management HTTP contract, the session display
metadata policy, the reauthentication generalization for account actions,
the provider ownership of password/TOTP/passkey factors, and the recovery
code capability decision. All provider capabilities were verified against
the pinned ZITADEL **v2.71.0** live local instance and the pinned
`zitadel-go/v3 v3.29.2` SDK.

Phase 3 frozen surfaces are untouched: the ConsentResolution union, the
decision lifecycle, grant reuse, local-consent revoke semantics, the
`prompt=none` matrix, LoginV2 gateway routing, callback containment and
single-winner/reconciliation are all read-only context for this phase. The
interaction gateway resolves sessions through the same session service
(`OptionalSession`), so session revocation propagates to `prompt=none`
(`login_required`) with zero consent-code changes.

## §1 Session inventory data model

The current `session.Store` is keyed exclusively by `session:{sha256(token)}`
with no user→sessions index. Listing account sessions must never use Redis
`KEYS`/`SCAN`.

Frozen key layout (all under the existing namespace prefix):

```text
{prefix}session:{tokenHash}            JSON SessionRecord          (unchanged)
{prefix}user_sessions:{userId}         SET of SessionIDs           (new)
{prefix}session_locator:{sessionId}    string: tokenHash           (new)
```

Design rules:

1. **Index content is SessionID only.** Neither the raw session token nor
   the token hash of any session other than through the locator is placed
   in the set; the locator is the only SessionID→tokenHash bridge and is
   server-side only. `SessionID` is never a bearer secret (§1.4), but raw
   tokens still never appear in any index.
2. **Create is all-or-nothing.** The session record, the `SADD` into the
   user index and the locator `SET` are written in one Redis transaction
   (MULTI/EXEC). Transaction failure ⇒ no session is created (fail closed).
   All three keys receive the same TTL as the session.
3. **Delete removes all three atomically** (pipeline/transaction: DEL
   record, SREM index, DEL locator). Idempotent.
4. **Token rotation keeps the SessionID stable.** Rotation writes the new
   record, points the locator at the new token hash and deletes the old
   record in one transaction; the user index is untouched. The brief
   dual-validity window documented for `Rotate` in ADR-0002 §7 is unchanged.
5. **Touch keeps index and locator alive.** `Touch` refreshes the record
   and, in the same round-trip, re-expires the locator and the user index
   to the same TTL (remember policy included).
6. **Self-healing on read.** `List` reads the set, resolves each SessionID
   through the locator and then the record; a member whose locator or
   record is gone (TTL expiry, crash between writes) is removed from the
   set lazily (best-effort `SREM`) and skipped. No full Redis scan exists
   anywhere in this path.
7. **Revoke-all-others** iterates exactly the user index of the calling
   user, never deleting the entry whose SessionID equals the current
   session, then applies rule 3 to each victim.

### 1.4 SessionID becomes a browser-visible revoke identifier

`SessionID` is returned to the browser as the `sessionId` of list entries
and accepted in the revoke path. Therefore:

- the `crypto/rand` **timestamp fallback in `generateSessionID` is
  removed**; a random-read failure fails session creation closed
  (`errors.New`, no ID, no session);
- entropy stays at 128 bits (16 random bytes, hex-encoded);
- a SessionID that is not in the current user's index, belongs to another
  user, or resolves to nothing yields the same stable **404
  `session.not_found`** outcome (non-enumerating; never 403, never a
  different error for "exists but not yours").

## §2 Session management HTTP contract

All routes live under `/api/v1`; mutations require `RequireSession` +
`RequireCSRF` (the existing middleware group pattern).

| Method & path | Semantics | Success | Errors |
| --- | --- | --- | --- |
| `GET /me/sessions` | list the caller's UP sessions | `200` array of SessionView (§3) | 401 unauthenticated |
| `DELETE /me/sessions/{sessionId}` | revoke exactly one *other* session of the caller | `204` | 404 stable (unknown/foreign/already gone); 409 `session.current` when `sessionId` is the caller's current session |
| `DELETE /me/sessions` | revoke **all other** sessions of the caller; the current session is always preserved | `204` with body `{"revoked": N}` | 401/CSRF |
| `DELETE /auth/session` | logout the current session (existing endpoint, unchanged) | `204`, both cookies cleared | unchanged |

Revocation ordering per victim session:

1. delete record + index entry + locator (rule 3);
2. best-effort provider session revocation: decrypt the sealed credential,
   call `RevokeProviderSession`; provider failure **never** fails the local
   revocation and never pretends the provider call happened (audit event
   records the outcome class);
3. security event `session.revoked` (self) / `session.revoked_other`
   (targeted) / `session.revoked_others` (bulk) — payloads carry session
   IDs and outcome only, never tokens, hashes or provider references.

A revoked browser's next request fails session lookup ⇒ `GET /me → 401`,
and the interaction gateway's `OptionalSession` resolves no session ⇒
`prompt=none → login_required` (P3 cross-invariant, re-verified in P4.9).

No reauthentication is required to revoke sessions (session + CSRF is the
gate); the reauth-protected session action is `account.sessions.revoke_others`
only when a product decision demands step-up — frozen here as **not
required** for either revoke route (both are already strictly
current-user-scoped), keeping the reauth surface minimal. The action
constant still exists (§4) so the frontend seam is uniform; the handlers
do not demand it.

## §3 Session display metadata

`SessionRecord` today stores only `UserAgentHash`; the frozen frontend
`UserSession` shape requires display data. **No location or device fact is
fabricated.** Frozen policy:

- At session creation the server normalizes the `User-Agent` header with a
  small built-in allowlist parser into two display strings:
  `DeviceDisplay` (OS family, e.g. `macOS`, `Windows`, `Android`, `iOS`,
  `Linux`) and `ClientDisplay` (browser family, e.g. `Chrome`, `Safari`,
  `Firefox`, `Edge`). Unrecognized/absent UA ⇒ empty strings, rendered as
  `未知设备` / `未知浏览器`. The normalized strings (max 64 bytes each) are
  stored plaintext in the record — they are display-only, non-secret data.
  The raw UA continues to be stored only as `UserAgentHash`.
- At creation the server stores the **masked** client IP only: IPv4 keeps
  the first three octets (`203.0.113.*`), IPv6 keeps the first four groups
  (`2001:db8:1:2:*`). The raw IP is never persisted. Missing/untrusted
  remote address ⇒ empty ⇒ rendered `未知 IP`. No proxy-header trust is
  added in P4.
- `approximateLocation` is **optional/null** in the API; the server always
  returns null (no GeoIP dependency). UI renders `未知位置`.
- `isCurrent` is computed by comparing the entry's SessionID with the
  caller's principal SessionID; it is never client-supplied.
- `lastActiveAt` is `LastSeenAt` from the record.

Frozen wire type (`GET /me/sessions` entry):

```json
{
  "sessionId": "3f2c…",
  "deviceName": "macOS",
  "clientName": "Chrome",
  "approximateLocation": null,
  "ipAddressMasked": "127.0.0.*",
  "lastActiveAt": "2026-08-08T10:00:00Z",
  "createdAt": "2026-08-08T09:00:00Z",
  "authenticationMethods": ["password", "totp"],
  "isCurrent": true
}
```

The frontend `UserSession` type adapts: `approximateLocation: string |
null`; unknown values render the `未知…` copy. The mock keeps richer fake
data in mock mode only.

## §4 Reauthentication generalization

The P1 reauth domain (opaque challenge/grant tokens, SHA-256-hash-only
Redis keys, user+session+action binding, atomic claim/consume, single-use
grants, short TTL, rate limiting, MFA continuation, expired-challenge
provider-session cleanup, fail-closed Redis semantics) is **extended, not
duplicated**. No second password-confirm token mechanism is introduced.

Frozen action set (additions to the existing three):

```text
account.password.change
account.totp.enroll
account.totp.remove
account.passkey.enroll
account.passkey.remove
account.sessions.revoke_others     (defined for seam uniformity; not demanded by §2 routes)
```

(`account.recovery_codes.rotate` is intentionally absent — §9.)

### Generic target binding

`ReauthChallengeData` and `ReauthGrantData` gain one optional field:

```text
Target string `json:"target,omitempty"`
```

- Existing `application.delete` / `client.delete` / `client.secret.rotate`
  keep their exact semantics: `ApplicationID` (+ `ClientID`) binding,
  `Target` unused. Full backward compatibility is a freeze requirement.
- Account actions bind `UserID` + `SessionID` + `Action`; `ApplicationID`
  and `ClientID` **must be empty** for `account.*` actions (a fake
  applicationId is forbidden); `Target` is empty for all P4 actions (the
  user is their own target) and remains available for future per-resource
  account actions.
- Consume validates every binding: wrong user / wrong session / wrong
  action / non-empty application-client fields on account actions /
  expired / already-consumed ⇒ fail closed.

Password-only accounts receive the immediate single-use grant path;
password+TOTP accounts go `202 challenge → MFA → single-use grant`,
reusing the existing reauth MFA continuation exactly.

## §5 Remember + MFA completion (P3 freeze debt, fixed in P4.1)

Frozen fix: `auth.MFAChallengeData` gains `Remember bool`; the login
handler stores the request's `remember` into the challenge; `CompleteMFA`
passes `challenge.Remember` (instead of the hard-coded `false`) into
session creation, so the session TTL policy and the `Remember` record flag
match the user's choice. In-flight pre-fix challenges decode with
`Remember=false` (safe default). This is a P1/P4 session-semantics fix and
does not reopen Phase 3.

## §6 Password management

The provider is the password authority. United Pass never stores, hashes
or mirrors user passwords.

Frozen flow for `POST /api/v1/me/security/password`
(`{newPassword}` body; **no** `currentPassword` field):

1. `RequireSession` + `RequireCSRF`;
2. consume a valid reauth grant for `account.password.change`
   (`X-Reauthentication-Token`); the reauth ceremony — which already
   proved the current password (and TOTP where enrolled) — is the sole
   proof of identity; the mutation never re-accepts `currentPassword`;
3. provider `SetPassword` for the user's provider identity. Primary mode:
   the service account sets the password **without** `currentPassword`
   (per the v2 API contract this requires the SA's org-level user
   management permission, which the acceptance SA holds — verified live to
   reach provider validation in V-3). If the live instance rejects the
   no-current-password mode for our SA, the frozen fallback is to thread
   the reauth-verified password through in-memory only (never stored,
   never logged, dropped after the call); P4.1 live-probes and records
   which mode the instance actually grants before implementation;
4. frozen session policy after provider success:
   - the **current** UP session is preserved but rotated (new session
     token + new CSRF token; cookies re-issued; SessionID stable);
   - **all other** UP sessions of the user are revoked (§2 rule 3 +
     best-effort provider session revocation);
   - the sealed provider session credential of the current session is
     re-sealed from the provider response when the password call yields a
     fresh session handle; otherwise the existing credential survives
     (the provider session remains valid for the user);
5. security event `account.password_changed` (no password material in the
   payload); provider failure ⇒ no local side effects, stable error
   `provider.password_change_failed` (fail closed, never pretend success).

Acceptance proof (P4.9): old password → login fails; new password → login
succeeds; other session revoked; current session rotated.

## §7 TOTP management

Frozen endpoints (all `RequireSession` + `RequireCSRF`; provider is the
factor authority; no local factor state beyond reauth/enrollment
transients):

| Endpoint | Reauth action | Provider call |
| --- | --- | --- |
| `GET /api/v1/me/security` | — | factor summary from `ListAuthenticationMethodTypes` (+ provider profile readback) |
| `POST /api/v1/me/security/totp/enrollment` | `account.totp.enroll` (consumed here) | `RegisterTOTP` → `{enrollmentToken, secret, otpauthUri}` |
| `POST /api/v1/me/security/totp/enrollment/confirm` | enrollmentToken (below) | `VerifyTOTPRegistration` |
| `DELETE /api/v1/me/security/totp` | `account.totp.remove` | `RemoveTOTP` + readback |

Enrollment secret handling (freeze):

- the secret appears **only** in the begin response; the response carries
  `Cache-Control: no-store`;
- the secret is never logged, never written to audit payloads, analytics
  or PostgreSQL, and never returned again — after the response the only
  authoritative copy is the provider's pending registration;
- the begin step consumes the reauth grant and mints a short-lived,
  single-use `enrollmentToken` (same pattern as MFA tokens: SHA-256 hash
  key in Redis, user+session bound, claim/consume Lua semantics) so the
  confirm step does not require a second reauth ceremony;
- confirm is single-winner via the claim lock; double registration fails
  on the provider side (`already set up`), which maps to a stable 409 —
  the flow is idempotency-safe;
- removal requires reauth and performs a provider readback afterwards;
  the factor list endpoint never infers state from local memory.

## §8 Passkey management

Included in P4 scope (V-4). Frozen endpoints:

| Endpoint | Reauth action | Provider call |
| --- | --- | --- |
| `POST /api/v1/me/security/passkeys/enrollment` | `account.passkey.enroll` | `RegisterPasskey` → `{enrollmentToken, passkeyId, publicKeyCredentialCreationOptions}` |
| `POST /api/v1/me/security/passkeys/enrollment/confirm` | enrollmentToken | `VerifyPasskeyRegistration` with the browser's attestation |
| `DELETE /api/v1/me/security/passkeys/{passkeyId}` | `account.passkey.remove` | `RemovePasskey` + readback |

- `publicKeyCredentialCreationOptions` is passed through verbatim to
  `navigator.credentials.create()`; real mode never runs the mock WebAuthn
  simulator;
- `passkeyId` is returned only to its owner session and accepted in the
  delete path with the same stable-404 non-enumeration rule as sessions;
- attestation payloads are never logged or audited (only sizes/outcomes).

### Factor summary + multiple passkeys

The legacy `SecurityFactor[]` ("one row per kind") cannot represent
multiple passkeys and is not forced to. Frozen real response shape for
`GET /api/v1/me/security`:

```json
{
  "password": { "set": true },
  "totp": { "enabled": true },
  "passkeys": [
    { "passkeyId": "…", "createdAt": "…", "state": "active" }
  ],
  "recoveryCodes": { "available": false, "deferredReason": "provider_unsupported" }
}
```

The frontend adapts its view model: summary rows derived from this
payload, one real row per passkey. Compressing several passkeys into one
fake factor row is forbidden.

## §9 Recovery codes — DEFERRED BY ARCHITECTURE (Option B)

Findings: the pinned SDK proto declares `GenerateRecoveryCodes` /
`RemoveRecoveryCodes` and the session API accepts a `recoveryCode` check
(V-6), but the pinned **server v2.71.0 does not serve** the
generate/remove endpoints (V-7: live 404 on both POST and DELETE). United
Pass can therefore verify codes in a login chain it cannot issue; a
self-built code store could never enter the real login chain safely.

Frozen decision:

- P4.6 is **DEFERRED BY ARCHITECTURE**;
- real mode hides all Recovery Codes UI (the seam returns
  `recoveryCodes.available=false`; the panel does not render);
- mock mode keeps the existing mock behavior;
- the login backend keeps rejecting `recovery_code` MFA methods
  (P3.9 state, unchanged);
- this deferral does not block the Phase 4 freeze. Reopens only when the
  pinned provider gains a verifiable issuance lifecycle.

## §10 Authorization model for provider factor writes

Factor writes run under the backend's service account via the pinned SDK
(gRPC), not under a user token. The acceptance instance already grants the
service account org-level ownership (init script adds `ORG_OWNER`); the
frozen requirement for any environment is: the backend SA must hold an
org-level user-management role for the orgs it serves, verified per
operation by P4.1 live probes before the corresponding handler ships.
Missing permission ⇒ stable `provider.forbidden` error, fail closed, no
local side effects.

## §11 Non-goals and frozen boundaries (Phase 4)

Explicitly out of scope: OAuth grant/consent semantics, provider-issued
token revocation, application/client lifecycle, user/staff admin,
directory sync, ABAC/policy, admin audit explorer, email/phone profile
changes, account deletion, data export, logged-out password-reset email
flows, and P3 historical reconciliation debt.

```text
Account Session revoke ≠ OAuth Grant revoke ≠ provider OAuth token revoke
```

If any implementation appears to require changes under
`backend/internal/consent/*`: STOP, report, evaluate against the Phase 3
reopen criteria, and do not proceed without approval.

## §12 Security hardening contract (binding for P4.8)

- Redis: no `KEYS`/`SCAN` in any session-listing or inventory path;
- browser-visible identifiers (SessionID, passkeyId) are cryptographically
  random; token hashes, provider session references and sealed
  credentials never leave the server;
- reauth matrix all fail closed: wrong user / wrong session / wrong action
  / wrong target / expired / consumed / parallel consume / parallel MFA
  completion / rate limit / provider outage / Redis outage;
- session matrix: cross-user revoke ⇒ 404; random sessionId ⇒ 404;
  expired-index self-healing; concurrent/double revoke idempotent;
  revoke-others preserves current; logout clears both cookies; rotation
  invalidates the old token;
- sensitive-data sweep across logs, slog, HTTP errors, JSON responses,
  DOM, security events, DB and Redis non-secret fields: password, TOTP
  secret, TOTP code, recovery code, WebAuthn assertion, session cookie,
  CSRF raw token, reauth raw token, provider session credential — zero
  persistence, zero log output.
