# ADR-0013: Cerbos policy authority and durable audit export boundary

- Status: Accepted
- Date: 2026-08-11
- Depends on: ADR-0004, ADR-0007, ADR-0011, ADR-0012

## Context

Phase 7 replaces the temporary all-false/development-override permission
resolver and the policy/audit frontend mocks. Authorization must stay
server-authoritative, policy publication must not activate a partial version,
and audit export must not turn operational logs or raw JSON payloads into a
secret-exfiltration surface.

Cerbos is an external PDP and therefore cannot share a database transaction
with United Pass. PostgreSQL remains the authority for stable users,
workforce state, policy working copies, selected published versions, audit
events and export jobs.

## Decision

### 1. Authorization request construction

The browser never supplies authoritative attributes. For every capability
resolution, PostgreSQL loads the stable `userId`, account status, personas,
employee status and department facts. United Pass maps each frozen capability
to an action and resource selector, loads only the current published policy
versions for that pair, and sends one or more `POST /api/check/resources`
requests bounded to 50 resources each.

The existing PostgreSQL workforce guard remains outside the resolver and
denies an `offboarding` employee before Cerbos can grant anything. Missing
policies, missing users, malformed/incomplete PDP replies, timeouts and all
storage errors fail closed.

Each United Pass policy version is a separate Cerbos resource policy. An
allow document's `EFFECT_ALLOW` means its conditions matched. A deny document
contains a conditional deny plus unconditional allow fallback, so
`EFFECT_DENY` unambiguously means an explicit deny matched. Final aggregation
requires at least one matched allow and no matched deny.

### 2. Drafts, immutable versions and publication

`POST /admin/policies` creates version 1. `PATCH` requires
`expectedVersion`; under a row lock it creates a new immutable draft version
or returns 409. Editing after publication does not disable the older
`published_version`.

Publication requires `policy.publish`, CSRF and a single-use reauthentication
grant bound to `policy.publish + policyId`. A durable publication job is
created before the Cerbos Admin API call. The exact version is installed into
Cerbos first and then selected in a PostgreSQL transaction together with the
success audit event. A provider-success/database-failure can be retried
idempotently; an unselected Cerbos version cannot affect decisions.

Cerbos Admin API credentials are typed server-only configuration. Partial
configuration, plaintext production URLs and default Admin credentials are
rejected. Production requires complete Cerbos configuration, and readiness
checks both PDP health and the authenticated Admin API. No new SDK
dependency is introduced; the small REST adapter bounds timeout and response
size and never logs credentials or response bodies.

### 3. Simulation

Simulation evaluates one selected working copy against caller-provided test
attributes without installing it into Cerbos or changing authorization state.
It uses the same validated operators and AND semantics as the compiler and
returns `allow`, `deny` or `no_match`. Simulation is a preview, not an
authorization decision for a real request.

### 4. Audit search and export

The canonical `security_events` table remains the durable audit boundary.
Typed `target_kind`/`target_id` columns are additive indexes; old safe JSONB
payloads are not exposed. Search returns only fixed fields and uses cursor,
actor, type, result, request ID, text and time filters.

Export creation requires `audit.export`, CSRF and a single-use grant bound to
`audit.export + audit`. The transaction creates a durable job and its audit
event. A background worker claims jobs with `SKIP LOCKED`, caps output at
10,000 events, writes a fixed-column UTF-8 CSV and stores the short-lived
artifact in PostgreSQL. Only the requesting user with `audit.export` can poll
or download it; the same-origin URL expires after 15 minutes and the worker
clears expired artifact bytes. CSV never
contains raw payload, provider errors, credentials, tokens, cookies,
passwords or authorization codes.

## Failure semantics

- Cerbos unavailable/malformed: no capability is granted; publication returns
  a stable provider-unavailable response.
- Stale policy version or another active publication: 409, no provider call.
- Publication provider failure: durable job is terminal failed; selected
  published version is unchanged.
- Worker/process interruption: stale processing jobs are reclaimable.
- Export not complete: 409; expired or wrong owner: anti-enumerating 404.
- Audit write failure in publication/export creation: the state transaction
  aborts instead of reporting success without audit.

## Consequences

- `UP_CERBOS_PDP_URL`, `UP_CERBOS_ADMIN_URL`,
  `UP_CERBOS_ADMIN_USERNAME` and `UP_CERBOS_ADMIN_PASSWORD` are an all-or-none
  configuration set; production requires it.
- Local development may keep the explicit, production-forbidden permission
  override. It does not make publication succeed without Cerbos.
- Cerbos live acceptance and real ZITADEL regression are deployment evidence,
  separate from unit/integration proof.
