# ADR-0007: Password Credential Settlement and Security-Generation Invalidation (P4.3 narrow reopen of ADR-0006 §6)

## Status

**Accepted as architecture correction (P4.3 BLOCKED review).** This ADR is
docs-only. It amends ADR-0006 §6 (Password management) and narrowly
reopens exactly two frozen seams that the amendment requires:

- **P4.1 seam (narrow reopen):** session security-generation validation
  and stale-generation settlement cleanup — a shared authoritative
  security-state validator covering **every** session-to-principal
  promotion path (at minimum `RequireSession` and `OptionalSession`),
  plus generation-scoped post-settlement cleanup.
- **P4.2 seam (narrow reopen):** credential-generation binding of reauth
  challenges/grants and factor enrollment tokens.

Nothing else is reopened (§9). No implementation ships with this document;
the P4.3 rework is a separate, review-gated commit.

## Context

P4.3 implementation (`acd35f2`) shipped the frozen ADR-0006 §6 happy path:
reauth-gated `POST /me/security/password`, SA-privileged newPassword-only
`SetPassword`, current-session rotation, revocation of all other sessions,
durable audit. Review found the frozen flow models the provider call but
never models the moment **after the provider has committed**: when local
session/capability settlement fails, no authoritative, recoverable safe
state exists. Five findings (B1–B5) follow from that single missing model:

- **B1** — rotation failure (e.g. an ordinary concurrent logout making the
  current session vanish) returns before account-level invalidation runs;
  every *other* pre-change session stays live while the provider password
  already changed.
- **B2** — the rotate-failure fallback deletes the old token through the
  **same failing Redis** and discards the error (`_ =`). A Redis failure
  with unknown EVAL outcome can leave the old session record resurrecting
  after recovery: `RequireSession` has no credential-generation barrier to
  stop it, and `SessionRecord` carries no security epoch.
- **B3** — reauth grants (`ReauthGrantData`) and enrollment tokens
  (`EnrollmentData`) bind `UserID + SessionID + Action/Kind + Target`;
  none carries a credential generation. Rotation keeps `SessionID` stable
  by design, so pre-change grants and pending enrollments for
  `account.password.change` / `account.totp.*` / `account.passkey.*`
  remain fully redeemable after a password change — a password change is
  not a privilege-reset boundary.
- **B4** — `CreateGrant` mints independent random tokens; nothing fences
  the user-scoped password mutation. Two legitimate grants can drive two
  concurrent `SetPassword` calls; the request that reports `204` may not
  own the final password.
- **B5** — durable `account.password_changed` is written only after
  complete settlement. Provider-success paths whose settlement degraded
  (rotate failed, revoke-others failed) write no durable event, although
  the credential provably changed.

Root cause: the frozen flow has **no authoritative local security
boundary** between "the provider committed a credential change" and "the
local world was cleaned up". This ADR defines that boundary.

## Decision 1 — Security generation (epoch)

A per-user **security generation** counter (`securityEpoch`, monotonic,
starting at 1) is introduced.

- **Authority and durability:** the authoritative value lives in
  PostgreSQL (`users` table, column `security_epoch`, default 1). The
  epoch is never derived from Redis; Redis state can never resurrect a
  generation that PostgreSQL has advanced.
- **Stamping:** every `SessionRecord` is stamped with the user's current
  epoch at creation and on rotation; every `ReauthChallengeData`,
  `ReauthGrantData` and `EnrollmentData` is stamped at mint time. The
  epoch is a binding dimension, not secret material; it may be persisted
  and logged.
- **Advancement:** the epoch advances by exactly one, atomically in the
  same PostgreSQL transaction that settles the mutation intent (Decision
  3), whenever the provider outcome of a password mutation is `success`
  **or** `unknown` (Decision 4). It never decreases. No other operation
  advances it in Phase 4 (factor enroll/removal does **not** advance the
  epoch — those are factor-lifecycle events, not credential-generation
  resets; this may be revisited only through a future ADR).
- **Validation rule:** any session, grant, challenge or enrollment whose
  stamped epoch is lower than the user's current epoch is treated exactly
  as if it did not exist — fail closed, stable non-enumeration semantics
  (§12 of ADR-0006 unchanged).
- **Mutation-intent barrier (F3, refined by F6).** The authoritative
  security state is the pair `(current epoch, mutation-intent phase)`.
  The barrier has two phases:
  - **Pre-outcome (`active`):** every session promotion, reauth grant
    consumption, enrollment confirmation and further password mutation
    fails closed — the pending mutation is itself part of the barrier,
    not only the epoch it will advance (Decision 3).
  - **Post-epoch (`outcome_recorded` / `local_settlement`):** the atomic
    outcome-record + epoch advancement has already established the
    credential boundary, so sessions stamped with the **current** epoch
    are ordinarily promotable; sessions stamped with an older epoch stay
    denied (stale-epoch rule); reauth grant consumption, enrollment
    confirmation and further password mutations remain denied until the
    intent is `settled` (sensitive capabilities minted before or during
    settlement are not trusted until terminalization).
  - **`settled`:** no barrier.

### P4.1 seam — shared security-state validator and stale-generation settlement cleanup

**Shared validator (F1).** All session-to-principal promotion paths MUST
apply authoritative security-state validation. The backend has two
independent promotion paths — `RequireSession` and `OptionalSession` — and
both call `ValidateSession` and inject the principal directly; neither
passes through the other. Frozen rule: exactly one shared validator (the
epoch read, the active-intent check and their fail-closed semantics) is
implemented once and invoked by every promotion path; no path promotes a
principal without it. This is a middleware seam only — P3 consent
business logic is untouched, and the interaction gateway keeps resolving
sessions through `OptionalSession`.

Stale-epoch behavior is pinned per path:

- `RequireSession`: 401; both the `up_session` and `up_csrf` cookies are
  cleared.
- `OptionalSession`: the request continues **anonymous** — no principal is
  ever injected; both cookies are cleared.

The frozen middleware rule "authentication failure does not clear
cookies" remains frozen for every other failure class; epoch-stale
failure is the single pinned exception, because an epoch-stale token can
never authenticate again (an authoritative, permanent death — not a
transient lookup failure).

- The epoch read is a single indexed point lookup by primary key; it is
  accepted as a per-request cost of the security boundary.
- **Fail-closed ambiguity:** if the authoritative lookup itself fails
  (PostgreSQL outage), promotion fails closed on both paths:
  `RequireSession` answers 401, `OptionalSession` continues anonymous —
  in both cases with **no cookie clearing** (a transient failure must not
  destroy tokens that may still be valid).
- An epoch-stale session is indistinguishable from a revoked session to
  the caller; the distinction exists only in structured logs/audit.

**Generation-scoped settlement cleanup (F4).** After the epoch advances,
physical cleanup MUST target only sessions whose stamped epoch is lower
than the new epoch (an internal settlement seam, conceptually
`RevokeSessionsBeforeEpoch(userID, newEpoch, …)`). It must never revoke a
session already stamped with the new epoch or any later one — a fresh
new-generation login racing the settlement must survive. The generic
`RevokeAllOtherSessions` API is generation-unaware and MUST NOT be used
for post-password-change cleanup. This seam is internal: the
`/me/sessions` HTTP contract, the ZSET model and the inventory contract
stay frozen.

These seams do not touch the remaining frozen P4.1 surfaces: the ZSET
inventory model, effective-expiry scoring, SessionID randomness,
listing/revocation HTTP contracts and inventory display.

### P4.2 seam — reauth/enrollment credential-generation binding

`ReauthChallengeData`, `ReauthGrantData` and `EnrollmentData` each gain
one field (the stamped epoch). Consume/complete/claim verification adds
one binding dimension — stamped epoch equals current epoch — alongside the
existing checks (user / session / action / target / expiry / consumed /
claim), and applies the active-intent barrier of Decision 1: while a
non-terminal password-mutation intent exists, grant consumption and
enrollment confirmation fail closed. Claim/release/consume mechanics,
TTLs, single-use semantics, the sentinel error family and the HTTP error
mapping stay frozen.

## Decision 2 — Settlement state machine (binding outcome matrix)

Every password-mutation terminal state must resolve to exactly one row:

| Provider outcome | Local settlement | Required result |
| --- | --- | --- |
| confirmed failure | none | lease released; epoch unchanged; all sessions and capabilities survive; stable `provider.password_change_failed`; zero local side effects (frozen §6 semantics preserved) |
| success | full settlement success | current session rotated **and re-stamped to the new epoch**; every other session invalid; capabilities of the old generation invalid; durable audit with settlement `settled` |
| success | current session disappeared (concurrent logout/revoke won) | epoch already advanced ⇒ **every** pre-change session and capability is invalid regardless of Redis state; cookies cleared; 401/re-login; durable audit with settlement `settled_relogin` |
| success | Redis cleanup failure (rotate/delete/revoke-others errored or outcome unknown) | epoch already advanced ⇒ the old generation can never authenticate again even if Redis recovers; response never reports success; durable audit with settlement `degraded` |
| unknown (transport error / crash mid-call) | unknown | epoch advanced (fail closed); intent settled `outcome_unknown`; durable audit with settlement `degraded`; every old-generation artifact invalid; re-login required; crash reconciliation per Decision 3 |
| concurrent second mutation | another mutation active | rejected **before** the provider call (Decision 3): stable `password.change_in_progress`, zero provider calls, zero side effects |

**Ordering invariant:** the epoch advancement is the **first** local
effect after the provider outcome is known; rotation, revocation and audit
are settlement steps that follow it and may degrade without ever undoing
the boundary. Consequently:

- account-level invalidation never depends on the current session's
  rotation succeeding (closes B1);
- Redis ambiguity can never resurrect the old generation (closes B2);
- pre-change grants/enrollments die with their generation (closes B3).

## Decision 3 — Mutation lease and durable intent (single-winner fencing)

Before any provider call, the handler must establish a **durable,
per-user, fail-closed mutation intent**.

**Lifecycle terminology (binding).** An intent has exactly these states,
and the flow performs exactly one authoritative settlement — never two:

1. `active` — lease acquired, provider call pending or in flight;
2. `outcome_recorded` — the provider outcome is recorded and, for
   `success`/`unknown`, the epoch is advanced **in the same transaction**
   (this is the settlement of Decision 1's "advancement");
3. `local_settlement` — rotation and generation-scoped cleanup in
   progress (degradable);
4. `settled` — terminal, carrying the provider outcome and the settlement
   outcome.

- **Ledger:** a PostgreSQL per-user mutation lease/intent record: user,
  intent id (monotonic), the epoch at acquisition, status, provider
  outcome, settlement outcome, timestamps. **No password material ever
  enters the ledger** (the §6 secret lifecycle is unchanged).
- **Single-winner:** acquiring the lease is a transactional, row-level
  fencing step (one writer transitions the user's lease to `active`; a
  concurrent requester fails closed **before** the provider call with
  stable `password.change_in_progress`). This is a user-scoped
  single-winner gate, not per-token single-use; it closes B4.
- **Mutation-intent barrier (F3, 3A; phases per Decision 1):** while an
  intent is `active`, the pending mutation is itself a security barrier:
  every session promotion, reauth grant consumption and enrollment
  confirmation fails closed. Once the intent reaches `outcome_recorded`
  the barrier narrows per Decision 1's post-epoch phase. The request
  executing the mutation is not caught by its own barrier: it completed
  session/reauth validation **before** acquiring the intent and continues
  under the intent's fence. On provider `confirmed_failure` the intent
  settles with the epoch unchanged, and the old generation resumes
  validity — a temporary fail-closed window, never a permanent side
  effect.
- **Deadline and fencing rules (F3, 3B), all binding:**
  1. the provider `SetPassword` call runs under a hard bounded deadline
     `D`;
  2. the lease expiry `L` is strictly later than `D` plus a frozen
     safety margin — a hanging provider call can never outlive its
     fence and resurrect as a stale writer after a new mutation starts;
  3. every intent state transition is CAS-fenced:
     `WHERE user_id = ? AND intent_id = ? AND status = <expected>` — a
     transition that matches no row is a lost fence and fails closed;
  4. epoch advancement is idempotent per intent: one intent advances the
     epoch at most once; a stale worker that lost the intent fence MUST
     NOT advance the epoch or perform authoritative settlement.
- **Detached settlement context:** the `outcome_recorded` transition
  (outcome record + epoch advancement) and everything authoritative that
  follows it run under a detached, bounded context — never the HTTP
  request context. A client disconnect after the provider call can never
  cancel the settlement while `SetPassword` may already have committed.
- **Crash model and takeover/recovery matrix (F6, binding).** Every
  non-terminal state has an exit, and recovery NEVER re-invokes the
  provider:

  | Abandoned state | Takeover rule |
  | --- | --- |
  | `active` past lease expiry | CAS from `active` → record `outcome_unknown` and advance the epoch exactly once → continue settlement |
  | `outcome_recorded` | the recorded `providerOutcome` is NEVER changed and the epoch is NEVER advanced again; local settlement is resumed/claimed idempotently |
  | `local_settlement` | generation-scoped cleanup is retried idempotently; if cleanup still fails after bounded attempts, `settlementOutcome = degraded` and the intent settles |
  | `settled` | immutable; no-op |

  Takeover itself is CAS-fenced by `(user_id, intent_id, expected
  status)` and runs under a detached, bounded context. Takeover is
  triggered opportunistically on access — the shared validator observing
  a non-terminal intent, a sensitive-consumption attempt, or a further
  mutation attempt — and every takeover path is bounded: after bounded
  attempts the intent is settled (`degraded` when settlement could not
  complete), so terminalization can never stall either.
- **Terminalization invariant:** no abandoned intent can block legitimate
  re-login indefinitely — post-epoch intents never block new-generation
  ordinary promotion at all (Decision 1), and a pre-outcome `active`
  intent blocks only until expiry-driven takeover — nor can any abandoned
  intent remain non-terminal indefinitely (bounded takeover attempts),
  nor be mistaken for a healthy state.
- **Ambiguity rule:** the lease may be cached/mirrored in Redis for
  hot-path fencing only; any Redis disagreement resolves in favour of the
  PostgreSQL ledger, and Redis unavailability degrades to the ledger. The
  ledger is the single authority — the distributed gap is closed at the
  durable store, never at the cache.

## Decision 4 — Provider outcome classification

The frozen §6 provider call yields exactly one of three classifications:

- `confirmed_failure` — the provider definitively rejected the change
  (business error). Zero local settlement; the stable failure is returned.
- `success` — the provider confirmed the change.
- `unknown` — transport-level failure, timeout, crash, or an ambiguous
  response: the call may or may not have committed. **Unknown is treated
  as committed for boundary purposes (fail closed).** There is no local
  password readback to disambiguate, and none is introduced.

`success` and `unknown` both record the outcome and advance the epoch in
the same CAS-fenced transaction, then attempt the durable audit; they
differ only in the HTTP outcome reported (`unknown` never reports success
and always forces re-login).

## Decision 5 — Settlement audit (closes B5)

Every provider outcome of `success` or `unknown` must **attempt** a
durable `account.password_changed` event on **every** terminal path —
including vanished-session, infra-failure and outcome-unknown paths. The
event preserves the two orthogonal facts as separate fields (F5):

- `providerOutcome`: `success` | `unknown` — the Decision 4
  classification survives into durable history; "the password definitely
  changed" and "it may have changed" must remain distinguishable in
  incident forensics;
- `settlementOutcome`: `settled` | `settled_relogin` | `degraded`.

`intentId`, `fromEpoch` and `toEpoch` SHOULD be carried as forensic
context; they are valuable but not freeze-blocking. Audit-writer
availability stays best-effort per the frozen precedent (a writer failure
logs and never masks the response), but the attempt is mandatory on every
provider-committed terminal path; a password change may never vanish from
durable history. To keep the frozen P4.1 audit result model untouched,
both fields are **new additive fields**, never an overload of the existing
result/outcome field. Provider `confirmed_failure` writes no durable
event (frozen behavior preserved).

## Decision 6 — Migration and back-compat

- `users.security_epoch` defaults to 1. Existing rows receive 1 via
  migration.
- **Legacy decode rule (F2, executable).** Go JSON decoding yields the
  zero value for a missing field, so "missing ⇒ 1" is pinned as an
  adapter rule, not a wish:
  - `SessionRecord`, `ReauthChallengeData`, `ReauthGrantData` and
    `EnrollmentData` records written before this ADR decode with
    `securityEpoch = 0`; that value is **normalized to epoch 1 at the
    persistence-adapter decode boundary** (Redis adapters for sessions,
    grants, challenges and enrollments). Business code never special-cases
    zero.
  - Newly created records MUST carry `securityEpoch ≥ 1`.
  - An explicit zero **written** by post-migration code is invalid and
    fails closed (it indicates a stamping bug, not legacy data).
  Matching the default user epoch, legacy artifacts stay valid until the
  first password change advances the generation, at which point the
  validation rules retire them.
- The HTTP wire shape is unchanged: `{newPassword}` only; `currentPassword`
  remains rejected (§6 and the frozen non-goals are untouched).

## Decision 7 — HTTP outcomes

| Terminal state | HTTP | Stable code |
| --- | --- | --- |
| confirmed provider failure | 502 | `provider.password_change_failed` (frozen) |
| lease already held | 409 | `password.change_in_progress` (new) |
| full settlement | 204 + rotated cookies | — |
| epoch settled but current session gone / outcome unknown | 401 + cleared cookies | stable re-login code (implementation pins it) |
| epoch settled, settlement degraded (Redis cleanup failure) | 500; rotated credentials issued when available so the caller is not stranded | stable settlement-degraded code (implementation pins it) |

## Preserved from the frozen ADR-0006 §6 (not reopened)

- wire shape `{newPassword}` only; no `currentPassword` field, ever;
- `SecretPassword` redaction seam; the password never enters logs, audit,
  Redis, PostgreSQL or error details;
- the single SA-privileged newPassword-only provider mode (V-3(a)); no
  fallback exists;
- stable `provider.password_change_failed` on confirmed provider failure
  with zero local side effects;
- rotation semantics: SessionID stable, fresh token + CSRF, absolute
  deadline never extended;
- non-enumeration contracts (§12);
- the provider session re-seal clause.

## Consequences

- Every authenticated request performs one additional indexed PostgreSQL
  point lookup (epoch validation). Accepted: correctness of the security
  boundary outweighs the cost at this scale; the lookup may later be
  cached only under an explicitly frozen fail-closed staleness policy
  (future ADR, not now).
- Settlement correctness now depends on PostgreSQL availability for the
  epoch read and the lease transaction. Failure modes fail closed (401 /
  rejected mutation); the ambiguous-Redis gap is deliberately moved to a
  transactional durable store with a defined crash model, instead of
  leaving it undefined in Redis.
- The P4.3 rework replaces the current post-provider control flow
  (rotate → revoke → audit) with the Decision 3 lifecycle: acquire intent
  → provider call under deadline `D` → `outcome_recorded` (outcome record
  + epoch advancement in one CAS-fenced transaction, detached context) →
  `local_settlement` (rotate and re-stamp current, then
  generation-scoped cleanup of pre-epoch sessions only) → `settled` +
  audit attempt, with every branch resolving to exactly one matrix row.
- Review evidence for the rework must include: the vanished-session race
  (B1) now asserting **no** pre-change session survives; a Redis-ambiguity
  simulation (B2); pre-change grant/enrollment invalidation after a
  password change (B3); a concurrent-mutation fencing test with a
  deterministic single winner (B4); durable audit attempts on every
  provider-committed terminal path (B5); stale-epoch behavior pinned on
  **both** promotion paths (F1); legacy-decode normalization of a
  zero-epoch record (F2); the active-intent barrier failing closed during
  a pending mutation, with old-generation validity resuming on provider
  `confirmed_failure` (F3); a stale-worker CAS-fence test proving a lost
  intent can neither advance the epoch nor settle (F3); a cleanup test
  proving a fresh new-generation session survives post-change cleanup
  (F4); an audit-payload test asserting `providerOutcome` and
  `settlementOutcome` are preserved (F5); a crash-after-`outcome_recorded`
  test asserting the epoch advances exactly once, recovery never calls
  `SetPassword` again and the intent eventually settles (F6); a
  crash-during-`local_settlement` test asserting cleanup resumes
  idempotently, the new-generation session survives and the intent
  eventually settles or settles `degraded` (F6); a stale-takeover test
  asserting the old `intentId`/status CAS fails and the stale worker can
  neither advance the epoch, overwrite `providerOutcome` nor settle
  another worker's intent (F6); and a barrier-phase test asserting
  current-epoch ordinary promotion is allowed while an intent is
  post-epoch, while sensitive consumption and further mutations stay
  denied until `settled` (F6).
