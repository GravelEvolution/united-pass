# ADR-0005: OAuth Authorization, Consent and Grant Orchestration (Phase 3)

## Status

**Accepted (P3.0 architecture gate).** No Phase 3 business code may be
written before this ADR lands. This document fixes the endpoint topology,
the auth-request lifecycle, the provider session credential model, the
consent/grant source of truth, the allow/deny ordering across systems,
grant revocation semantics, and consent reuse rules. All provider
capabilities below were verified against the pinned ZITADEL **v2.71.0**
sources (git tag, not current docs) and the live local instance.

> **Revision 2026-08-06 (architecture review).** Resolves five gate
> findings without changing the commit history: (1) exact LoginV2
> redirect semantics (`<base_uri>/login?authRequest=…`) and LoginVersion
> preservation across all provisioner paths; (2) global single-winner key
> `(provider, provider_tenant_id, auth_request_id)`; (3) the
> `provider_succeeded` proof state and fail-closed reconciliation; (4)
> full `prompt`/`max_age` semantics; (5) exact protocol endpoint paths,
> Discovery/issuer consistency and proxy trust. Plus: audit-safe
> `attemptedRedirect` recording, opaque-ID input limits, and
> `redirectUrl`/cache-header mapping.

> **Revision 2026-08-06 (second review).** Adds the Authorization
> Interaction Gateway (§12): the server-side execution entry for the
> `prompt=none` branches (silent completion, `login_required`,
> `consent_required` error callbacks) that the side-effect-free browser
> contract cannot carry. The provider entry moves to a controlled
> Interaction Base URI (`…/_interaction/login?authRequest=…`); Next.js
> `/login` now receives `requestId` from the gateway. `select_account`
> fails via the provider callback with `account_selection_required`

> **Revision 2026-08-06 (P3.1 seam review).** Defines the unsupported
> `prompt=create` behavior: account registration is a Phase 3 non-goal,
> so the gateway fails such requests through the provider error callback
> with `request_not_supported` (§9, §12) — never silently ignored,
> never treated as plain consent, never routed to a registration flow.

## Context

Phase 3 implements the OAuth/OIDC authorization loop on top of the frozen
Phase 1/2 baseline (P2 freeze `0d18547`):

```
RP redirects browser → Authorization Endpoint → user login (or resume) →
verified consent screen → Allow/Deny → provider completes the auth request
→ provider-generated callback URL → local grant view → list/revoke grants.
```

United Pass never implements the OAuth protocol core: ZITADEL owns protocol
parsing, client authentication, code/PKCE/token issuance, JWKS and
discovery. The Go backend orchestrates; the Next.js frontend renders the
consent UI. The frozen frontend contract (`frontend/docs/api-contracts.md`,
`frontend/src/features/authorization/types.ts`) defines the four HTTP
operations this ADR must serve.

Two Phase 2 artifacts are reused, not reinvented: the
`provider_operations` + `provider_reconciliation_jobs` pattern (ADR-0004
§8) for cross-system outcomes, and the AES-256-GCM session crypto
(ADR-0002 §13) for credential-at-rest encryption.

## Verified provider capabilities (ZITADEL v2.71.0)

Sources: git tag `v2.71.0` (`proto/zitadel/oidc/v2/*`,
`internal/api/grpc/oidc/v2/*`, `internal/api/oidc/*`, `proto/zitadel/
auth.proto`, `proto/zitadel/app.proto`, `proto/zitadel/project.proto`,
`cmd/defaults.yaml`) plus a live read-only probe of the local instance on
2026-08-06 (project `384994263844257795`; no secrets recorded).

1. **Auth request retrieval.** `zitadel.oidc.v2.OIDCService.GetAuthRequest`
   (REST `GET /v2/oidc/auth_requests/{id}`) returns `id`, `creationDate`,
   `clientId`, `scope`, `redirectUri`, `prompt`, `uiLocales`,
   `loginHint`, `maxAge`, `hintUserId`. It does **not** expose `state` or
   `nonce` (both are echoed back by ZITADEL in the callback URL, so United
   Pass never needs to store them). Permission: `authenticated`. The
   pinned SDK `zitadel-go/v3 v3.29.2` already contains this gRPC client
   (`pkg/client/zitadel/oidc/v2`); no bespoke REST wrapper is needed. The
   earlier assumption that this service only exists on ZITADEL v3 was
   disproved by the v2.71.0 tag sources.
2. **Auth request completion.** `CreateCallback` with
   `Session{session_id, session_token}` links a verified session and
   returns `callback_url` (with `code` for code flow). Both session fields
   are `validate.required min_len=1` — **a session token is mandatory**.
   ZITADEL documents and enforces that this method can only be called
   **once** per auth request; a second call fails and is classified by our
   adapter as `already_completed`.
3. **Deny.** `CreateCallback` with `AuthorizationError{error:
   ERROR_REASON_ACCESS_DENIED}` fails the request and returns a verified
   client redirect URI carrying `error=access_denied&state=…`. The error
   path performs no project permission check (verified in
   `failAuthRequest`; only the session path calls `checkPermission`).
   The same one-shot error callback supports the full OIDC Core
   interaction errors — `ERROR_REASON_LOGIN_REQUIRED`/`_CONSENT_REQUIRED`/
   `_ACCOUNT_SELECTION_REQUIRED`/`_REQUEST_NOT_SUPPORTED` map verbatim to
   `login_required`/`consent_required`/`account_selection_required`/
   `request_not_supported` callback URLs (verified in `errorReasonToOIDC`)
   — which the gateway (§12) uses.
4. **callback_url is credential-grade.** The proto annotation states the
   URL "must be treated as credentials, as the contained code can be used
   to obtain tokens on behalf of the user". Handling rules in §3.
5. **Conditional project check on Allow.** `LinkSessionToAuthRequest`
   invokes `CheckProjectPermissionByClientID` for the **session's user**:
   - `has_project_check=true` ⇒ the user's org must be the project's
     resource owner or hold a valid project grant;
   - `project_role_check=true` ⇒ the user must hold a valid project user
     grant (role);
   - either flag false ⇒ the corresponding requirement does not apply.
   A failure surfaces as gRPC `PermissionDenied` (`OIDC-foSyH49RvL`).
6. **Live probe results (2026-08-06, read-only, IAM_OWNER JWT profile):**
   - shared project `384994263844257795` "United Pass":
     `project_role_check=false`, `has_project_check=false` (fields absent
     in the JSON ⇒ proto3 default `false`); resource owner is the
     `UnitedPassDev` org;
   - instance features: no `loginV2` feature set (login-V2-not-required;
     unset app login version therefore falls back to the built-in v1
     login); `loginDefaultOrg=true`;
   - the project currently has **no apps** (P2.8 acceptance removed its
     test apps), so no legacy `loginVersion` needs reconciling.
   Conclusion: the shared project matches the product intent (open to
   ordinary external users, no project-role admission). No roles or user
   grants are added in `zitadel-init.sh`; doing so unconditionally would
   mask project misconfiguration. If product later requires project-level
   admission, the flag is turned on deliberately and only then are roles
   and grants provisioned.
7. **Login UI steering (exact construction).** Verified in
   `internal/api/oidc/client_converter.go` (`Client.LoginURL`) and
   `client.go` constants: for an app with `LoginVersion.login_v2.base_uri`
   set, the redirect is exactly
   `base_uri.JoinPath("/login") + "?authRequest=<provider-auth-request-id>"`
   (`LoginPath = "/login"`, `LoginAuthRequestParam = "authRequest"`).
   `base_uri` is therefore an **origin/base URI**, never a page path.
   Auth requests created for LoginV2 clients carry the provider v2 ID
   prefix; auth request IDs **without** that prefix fall back to the
   built-in v1 login (`/login?authRequestID=`) regardless of other
   configuration — so a client missing LoginVersion can never enter the
   United Pass consent loop. The instance default is
   `DefaultLoginURLV2=/login?authRequest=` (`cmd/defaults.yaml`,
   overridable via `ZITADEL_OIDC_DEFAULTLOGINURLV2`); an instance feature
   `LoginV2.BaseURI` also exists.
8. **Grant/token revocation limits.** v2.71 offers only:
   - `zitadel.auth.v1` `RevokeMyRefreshToken` / `RevokeAllMyRefreshTokens`
     — caller must be the end user themselves;
   - RFC 7009 `POST /oauth/v2/revoke` — requires the literal token value,
     which United Pass never holds.
   There is **no** service-account RPC to revoke refresh tokens by
   (user × client). Revocation semantics in §6 are defined accordingly.
9. **Caller requirements.** Both `OIDCService` methods require only the
   `authenticated` permission; the existing machine-user JWT profile is
   sufficient. No new ZITADEL roles are introduced in P3.

## Decision

### 1. Endpoint topology (contract §6.1)

The three divergent paths (frontend contract `GET /oauth/authorize`,
frontend ADR-0006 `/oauth2/*` proxy, ZITADEL canonical `/oauth/v2/*`) are
resolved explicitly, not silently:

| Path | Owner | Behavior |
| --- | --- | --- |
| `GET /oauth/v2/authorize` | reverse proxy → ZITADEL | **The sole public authorization endpoint.** Proxied verbatim with query string; never touched by Go or Next.js. |
| `GET /oauth/authorize` | reverse proxy | Compatibility redirect (302, query preserved) to `/oauth/v2/authorize`, satisfying the frontend contract's initiation path without a second implementation. |
| `POST /oauth/v2/token`, `POST /oauth/v2/revoke`, `POST /oauth/v2/introspect`, `POST /oauth/v2/device_authorization`, `GET /oauth/v2/keys`, `GET /oidc/v1/userinfo`, `GET|POST /oidc/v1/end_session`, `GET /.well-known/openid-configuration` | reverse proxy → ZITADEL | Exact protocol endpoint set of ZITADEL v2.71 (verified in `internal/api/oidc/server.go endpoints()`); proxied verbatim, no root-path variants exist. |
| `GET /_interaction/login` (Go backend) | **Authorization Interaction Gateway** | The sole entry point ZITADEL generates for LoginV2 clients: `<interaction-base>/login?authRequest=<provider-auth-request-id>` (§Verified-7, §12). Server-side prompt/max_age/session/grant routing; for `prompt=none` it completes the request (session or error callback) and answers 302 directly; otherwise it 302s into Next.js. Never renders UI; always `Cache-Control: no-store` + `Referrer-Policy: no-referrer`. |
| `GET /login` (Next.js) | Interactive login page | Reached **only** via the gateway 302, with a single `requestId` parameter (the `authRequest`→`requestId` rename happens at the gateway edge); no arbitrary `returnTo`. After successful authentication it navigates to `/authorize?requestId=…`. |
| `/authorize` (Next.js) | Consent UI | Reads `?requestId=` (opaque), renders resolution via the Go API. Never redirects back to `/oauth/v2/authorize` for the same request (no loops). |
| `GET /api/v1/authorization/requests/{requestId}`, `POST …/decision`, `GET /api/v1/me/authorized-applications`, `DELETE /api/v1/me/authorized-applications/{grantId}` | Go backend | Frozen contract endpoints (contract §7). |

The `/oauth2/*` mapping in frontend ADR-0006 is superseded for protocol
endpoints by the canonical paths above; no frontend code depends on the
proxy path, only on the two `authorization` REST endpoints.

Login UI steering:

- `base_uri` is the **Interaction Base URI**: the trusted public origin
  with a controlled path prefix, e.g.
  `https://id.example.com/_interaction` — never a page path. ZITADEL
  constructs `<base_uri>.JoinPath("/login") + "?authRequest=…"`, i.e.
  `https://id.example.com/_interaction/login?authRequest=…`. The reverse
  proxy routes `/_interaction/*` to the Go backend and everything else
  of that origin to the frontend, so the gateway runs on the same origin
  as the United Pass session cookie.
- The Next.js `/login` page receives its `requestId` from the gateway,
  never directly from ZITADEL; the `authRequest`→`requestId` rename is
  the gateway's boundary decision, not an equivalence discovered at
  runtime.
- **P3.6 must empirically verify path-prefix preservation** with a live
  app against v2.71: Go's `url.URL.JoinPath` appends to the existing
  path, so the prefix should survive — but if the probe shows the prefix
  dropped or re-encoded, the deployment falls back to a dedicated
  interaction host (separate origin) instead; the gateway design is
  unaffected either way.
- The provisioner sets `LoginVersion{login_v2{base_uri: …}}` on **every
  path that writes an OIDC app**: creation, UpdateClient, and any
  read-modify-write or reconciliation/backfill flow — it must preserve an
  existing value and repair a missing one. A client whose app lacks
  LoginVersion falls back to the built-in v1 login (§Verified-7) and can
  never enter the United Pass consent loop, so preservation is a
  correctness requirement, not a cosmetic one.
- **Migration of pre-existing apps.** The local project currently having
  no apps does not stand in for production: any production instance with
  pre-P3 apps needs an explicit one-time backfill job (list apps in the
  shared project → set LoginVersion where missing → verify) before the
  consent loop is enabled there. This job ships with the P3 rollout
  runbook and is idempotent.
- The instance `LoginV2` feature stays unset. With both project checks
  off (§Verified-6), an authenticated ordinary user can complete requests.

Discovery, issuer and proxy trust:

- The public **issuer** is the reverse proxy's public origin; ZITADEL's
  external domain/secure settings are configured so that
  `/.well-known/openid-configuration` advertises exactly that origin, and
  every advertised endpoint (authorize, token, introspection, revocation,
  userinfo, jwks, end_session, device_authorization) is reachable through
  the same public address via the proxy table above. A discovery document
  pointing at a host the public cannot reach is a deployment failure, not
  a runtime surprise.
- The proxy **overwrites** `X-Forwarded-Host`/`X-Forwarded-Proto` with
  the values it controls and ZITADEL trusts only that controlled hop;
  client-supplied forwarded values are never accepted (no issuer or
  redirect hijack via header forgery).
- **Device Authorization Endpoint** (`/oauth/v2/device_authorization`)
  is proxied so Discovery stays truthful, but United Pass-provisioned
  clients never enable the `device_code` grant type, so the flow cannot
  complete against them; the consent domain treats device requests as out
  of scope (contract §4), and no UI or API path serves them.

### 2. Auth request lifecycle (contract §6.2)

The provider auth request ID is an **opaque** string end to end: it is
passed through URLs and APIs but never structurally parsed or mutated by
the frontend. "Opaque" does not mean "unchecked": every entry point
(the gateway `/login` `authRequest` parameter, the Next.js `/login` and
`/authorize` `requestId` parameters, the `{requestId}` path segment)
enforces input limits — exactly one query
parameter occurrence, decoded length **1..200** bytes (matching the
provider's own field limits), decoded exactly once (no double-decoding),
rejected otherwise — and the value is standard percent-encoded when
composed into API paths. Internal lifecycle states:

```
received           auth request known to the consent flow (resolution GET)
resolved           local client mapped, validity + scope subset checks ran
awaiting_login     no valid United Pass session for this user agent
awaiting_consent   session valid; consent must be displayed
allowed            decision=allow recorded locally, provider pending
denied             decision=deny recorded locally, provider pending
provider_succeeded CreateCallback returned; proof persisted, local commit pending
provider_completed local grant + audit committed
failed             terminal provider/local failure
expired            provider request no longer retrievable / TTL exceeded
```

Persistence model: resolution states are **derived on read** (no request
table); decisions and their cross-system outcomes are persisted through
the existing `provider_operations` pattern. The decision operation's
unique key is **global per auth request**:
`(provider, provider_tenant_id, auth_request_id)` — or, while United Pass
runs a single provider, `(provider, auth_request_id)`. `local_user_id` is
a **binding field set by the winner**, never part of the unique key: two
user agents resolving the same auth request with different users produce
one operation row, and the decision serializes globally (§5). Grants live
in `oauth_authorization_grants` (+ `oauth_authorization_grant_scopes`),
migration `00005_oauth_authorization_grants.sql`. Raw provider request
payloads, `state`, `nonce`, PKCE material and tokens are never written to
PostgreSQL.

### 3. Provider session credential (contract §6.3; amends ADR-0003)

ZITADEL `CreateCallback` requires `session_id` **and** `session_token`.
ADR-0003's "token discarded" stance is amended (see ADR-0003 revision,
same commit):

```go
// ProviderSessionCredential is the versioned, strongly typed wrapper
// around the provider-side session handle. It is never serialized to
// HTTP, PostgreSQL, logs, audit or error values.
type ProviderSessionCredential struct {
    Version      int    // 1 = legacy session-ID-only; 2 = ID + token
    Provider     string
    SessionID    string
    SessionToken string // empty for Version 1
}
```

Rules:

- The plaintext token is never retained long-term. After authentication
  completes, `session_id` + `session_token` are sealed immediately into
  the versioned credential; the whole credential is encrypted with the
  existing AES-256-GCM session crypto; only the ciphertext is stored, in
  the United Pass session record in **Redis**. Plaintext is dropped as
  soon as encryption succeeds.
- No string-delimiter concatenation: the credential is a typed struct,
  serialized (canonical JSON) before encryption, and the encrypted blob is
  a distinct storage type
  (`EncryptedProviderSessionCredential`), not the old plain
  "provider session reference" name — the content now contains bearer
  material.
- The credential never enters PostgreSQL, the HTTP `Principal`, browser
  responses, logs, audit events or error messages.
- Decryption happens only server-side through the narrow interface, keyed
  by the **currently valid** session of the request, released after use:

  ```go
  type ProviderSessionCredentialReader interface {
      ReadProviderSessionCredential(
          ctx context.Context,
          sessionID session.SessionID,
      ) (ProviderSessionCredential, error)
  }
  ```

  Only consent orchestration receives an implementation.
- **Legacy compatibility.** Sessions created before this change carry a
  Version-1 credential (session ID only). They cannot finalize an auth
  request; the consent flow fails closed and routes the user agent back
  into interactive re-login (gateway → `/login?requestId=…`, §12), which
  upgrades the credential to Version 2. No background migration of live
  credentials is performed.
- **Callback URL handling.** The provider-generated `callback_url` is
  treated as a credential and exposed to the browser **only** as the
  frozen contract field `redirectUrl` in the decision response, consumed
  via same-window navigation (`window.location.assign`); never persisted;
  never written to logs, audit, exception reporting or analytics; United
  Pass never parses or rebuilds its `code`/`state` components. Header
  policy in §11.

### 4. Consent and grant source of truth (contract §6.4)

- The **provider auth request** is authoritative for protocol facts
  (client_id, requested scopes, redirect_uri, prompt).
- The **local application/client** records are authoritative for display
  data and business validity (effective status = application × client;
  redirect exact match; scope-catalog subset).
- The **local grant** (`oauth_authorization_grants`) is the United Pass
  user-consent view. It is not token state and is never presented as such:
  a grant row implies consent, not live tokens.
- With a custom login UI, ZITADEL keeps **no** independent consent record
  for these requests: `CreateCallback` does not consult provider-side
  consent. United Pass grants are therefore the only consent ledger.
- **Reconciliation is fail-closed.** A provider `NotFound` on re-read can
  mean either "expired before we ever called the provider" **or**
  "consumed by our successful CreateCallback"; the two are externally
  indistinguishable. Therefore `NotFound` (and a lone `already_completed`
  on retry) is evidence only for **terminating** the request as
  expired/failed — it is never evidence of a successful Allow, and the
  reconciler never backfills a grant on that basis alone. Grant repair is
  permitted **only** when the operation row carries the explicit
  `provider_succeeded` proof (§5): the reconciler then completes the
  grant + audit exactly once. `pending`/`outcome_unknown` without that
  proof fail closed: the operation is marked failed, no grant is created,
  and the user must start a fresh authorization request from the
  application. The background reconciler never attempts to re-complete an
  auth request whose provider call is unconfirmed — there is no waiting
  browser to deliver a callback URL to. Duplicate grants remain
  impossible because grant upserts are conditional on (`user`,
  `client_id`) under the single-winner transition (§5).

### 5. Allow/deny ordering and cross-system consistency (contract §6.5)

No provider call ever runs inside a SQL transaction.

```
1. validate decision (session, CSRF, request state)
2. claim the operation row globally (insert-or-CAS on the auth-request key; pending)
3. call provider CreateCallback (Session for allow, AuthorizationError for deny)
4. persist the provider_succeeded proof (no callback URL stored)
5. single local transaction: grant upsert (allow) + audit + operation terminal
6. respond with the callback URL as redirectUrl (allow or deny)
```

- **Primary concurrency control is local and global per auth request.**
  The operation row is keyed `(provider, provider_tenant_id,
  auth_request_id)` (§2) and claimed with a compare-and-set transition
  (`INSERT … ON CONFLICT` + `UPDATE … WHERE status = expected`), so
  concurrent decisions — including the *same* auth request open in two
  browsers logged in as *different* users — resolve to exactly one local
  winner before any provider call is made. The losing side receives a
  stable conflict result instead of racing the provider; `local_user_id`
  is written by the winner as a binding, not used as a partition key.
  ZITADEL's one-shot `CreateCallback` is the **second line of defense**,
  catching provider-side replays only; United Pass never depends on
  provider conflicts to serialize local decisions.
- **Crash-window policy.** Two windows exist: between steps 3→4 (provider
  succeeded, proof not persisted) and 4→5 (proof persisted, local commit
  lost). The first cannot be closed; the correct outcome there is a lost
  local grant and a fresh authorization from the application — **never**
  guessing success. The second is repaired by reconciliation, but only
  because the `provider_succeeded` proof exists (§4). The proof row
  records the auth request, decision kind and time; it never stores the
  callback URL. The callback URL itself is unrecoverable after a lost
  response (one-shot API), so even a repaired grant ends with the stable
  user-facing instruction to retry from the application.
- **Retries** detect a completed provider request through the adapter's
  `already_completed` classification and never create a second grant.
- Deny creates no grant row; it records the decision operation and audit
  event and returns the provider's `access_denied` callback URL.

### 6. Grant revocation semantics (contract §6.6)

Verified truth (§Verified-8): United Pass **cannot** revoke provider
refresh tokens for a (user × client) pair from a service account on
v2.71. Therefore:

- `DELETE /api/v1/me/authorized-applications/{grantId}` sets the local
  grant to `revoked` (idempotent; repeat calls return the same stable
  outcome), writes the audit event, and returns 204.
- Effects, stated honestly in both API docs and frontend copy:
  - future authorization requests for this client **never** skip consent;
  - the user must consent again to re-authorize;
  - already-issued access tokens remain valid until their own expiry, and
    already-issued refresh tokens remain usable at the provider token
    endpoint until provider-side expiry — United Pass does not overstate
    the effect ("tokens invalidated immediately" is forbidden wording);
  - `lastUsedAt` has no true signal on v2.71 and is always `null`.
- If ZITADEL is later upgraded to a version exposing per-(user × client)
  revocation, a reconciliation-driven token cleanup can be added without
  changing the API contract.

### 7. Consent reuse (contract §6.7)

- Grants are aggregated **per OAuth client**, not per application; a
  multi-client application shows one grant line per client.
- Reuse (resolution returns `already_authorized`) requires **all** of:
  an `active` grant for the same (user, client); requested scopes ⊆
  granted scopes; client **and** parent application effective; client
  `consent_mode` permits reuse; no `prompt=consent`; `offline_access`
  present in the grant only if it was explicitly consented before.
- `prompt=consent` always forces the consent screen. Scope expansion
  always forces the consent screen (the grant is upserted with the new
  scope set after Allow). A revoked grant never enables reuse. A disabled
  client/application can never be completed and resolves to
  `client_not_found` (audit records the precise reason; no validity
  leakage).
- On `already_authorized`, the frontend proceeds to the decision endpoint
  without displaying the consent form; the backend still enforces every
  reuse condition server-side (the GET is advisory, the decision is
  authoritative).

### 8. Error classification

Adapter error classes (contract §8): `not_found`, `expired`,
`already_completed`, `invalid_redirect`, `invalid_scope`,
`provider_conflict`, `provider_unavailable`, `rate_limited`, `internal` —
plus the deterministic user-admission failure:

- Missing project grant / user grant on the Allow path (gRPC
  `PermissionDenied`, `OIDC-foSyH49RvL`) maps to the stable business error
  `authorization.user_not_eligible`. It is **never** mapped to
  `provider_unavailable` (it will not heal by retry), and audit events
  record only the stable reason code, never the raw provider error text.
- Deny is never rejected for missing project roles (verified: the error
  callback path skips `checkPermission`).

P3.9 real acceptance covers at minimum: (a) checks off ⇒ ordinary
authenticated user completes Allow; (b) `project_role_check` on + no grant
⇒ Allow fails with the stable error; (c) valid user grant added ⇒ Allow
succeeds; (d) Deny still produces the standard `access_denied` callback.

### 9. `prompt` and `max_age` semantics (OIDC Core)

Resolution must honor the full interaction semantics, not only
`prompt=consent` (§7 keeps that rule). These rules bind the Resolution
domain, the Authorization Interaction Gateway (§12 — the execution entry
for every non-interactive branch) and the fake provider in P3.1:

- **`prompt=none`** never renders login or consent UI; it is executed
  entirely at the gateway before any page is served.
  - valid United Pass session **and** grant reusable (§7) ⇒ silent
    completion through the provider (no interaction);
  - no valid session ⇒ provider error callback with `login_required`;
  - session present but consent cannot be silently reused ⇒ error
    callback with `consent_required`.
- **`prompt=login`** forces re-authentication; the current authentication
  time is never reused. After re-login the flow resumes at
  `/authorize?requestId=…`.
- **`max_age`** is evaluated against the United Pass session's
  authentication time (which the session store already records); elapsed
  time above `max_age` — or `max_age=0` — requires re-authentication via
  the same login-continuation path.
- **`prompt=select_account`** is not supported in P3 (single account per
  session): the gateway fails the request through the provider error
  callback with `account_selection_required` (§Verified-3); the flow
  never stalls on a United Pass error page, and the value is never
  silently ignored.
- **`prompt=create`** is not supported in P3 (account registration is a
  non-goal, contract §4): the gateway fails the request through the
  provider error callback with `request_not_supported` (§Verified-3),
  regardless of the session state. It is never silently ignored, never
  treated as plain consent, and never routed to a registration page that
  does not exist.
- **Invalid combinations** (e.g. `none` combined with any other prompt
  value) are neither downgraded nor reinterpreted by United Pass: the
  outcome is the provider's own validated result for the request, or a
  stable error when the request cannot proceed.

### 10. `attemptedRedirect` on redirect mismatch

The frontend union requires `attemptedRedirect` on `redirect_mismatch`,
but the value is attacker-controlled. The backend returns **only the
parsed host** of the attempted URI (`net/url`; unparseable values yield a
fixed placeholder) — never the raw string — and the frontend renders it
as plain text, never as a link. Server-side, the audit record stores
only: `parsed_scheme`, `parsed_host`, `raw_length`, and
`HMAC-SHA256(raw_value)` keyed by the audit HMAC key (correlatable, not
reversible). The raw value is recorded nowhere — audit is not a safe
sink for attacker input.

### 11. HTTP response mapping and cache policy

- The provider's `callback_url` is exposed to clients exclusively as
  `redirectUrl` (frozen contract field) in the decision response; the
  frontend navigates with `window.location.assign(redirectUrl)`.
- `Cache-Control: no-store` is set on the decision API response **and**
  on the resolution GET (`no-store` was already required there).
- `Referrer-Policy: no-referrer` is set on the decision API response,
  on the gateway responses (§12) and on the `/login` and `/authorize`
  HTML documents themselves, not only on API responses.

### 12. Authorization Interaction Gateway (non-interactive execution entry)

The browser contract cannot execute `prompt=none`: `ConsentResolution`
has no silent-completion or provider-error-callback outcome and no
`redirectUrl`; the Decision POST requires a session and CSRF, which a
sessionless `prompt=none` request lacks; and making the Resolution GET
perform `CreateCallback` would turn a read endpoint into a one-shot,
side-effecting operation that browser prefetch, retries or duplicate
GETs could consume prematurely. The semantics of §9 therefore get a
dedicated server entry point: the **Authorization Interaction Gateway**.

- **Ownership.** The gateway is Go-backend orchestration, served at
  `GET /_interaction/login` (§1). It alone sees the provider auth
  request, the United Pass session and the encrypted provider session
  credential (§3); provider credentials are never handed to Next.js.
- **Routing.** On arrival it validates the opaque `authRequest`
  parameter (§2), reads the auth request (`GetAuthRequest`: prompt,
  max_age, client, scopes) and routes:
  - `prompt=none`, no valid session ⇒
    `CreateCallback(AuthorizationError{LOGIN_REQUIRED})` and 302 to the
    returned error callback URL;
  - `prompt=none`, session present but consent not reusable (§7) ⇒
    `CreateCallback(AuthorizationError{CONSENT_REQUIRED})` and 302;
  - `prompt=none`, session present and grant reusable ⇒ silent Allow:
    decrypt the credential, run the §5 sequence (claim → CreateCallback
    with Session → `provider_succeeded` proof → grant + audit +
    terminal), then 302 to the code callback URL;
  - `prompt=create` (any session state) ⇒
    `CreateCallback(AuthorizationError{REQUEST_NOT_SUPPORTED})` and 302
    (registration is a Phase 3 non-goal; §9);
  - interactive cases (`max_age` exceeded, `prompt=login`, consent
    needed, no session) ⇒ 302 into Next.js: `/login?requestId=…` when
    (re-)authentication is required, otherwise `/authorize?requestId=…`.
    The gateway renders no UI itself; on its own failures it returns a
    stable local error page (no provider callback exists yet).
- **Same ordering rules.** The silent Allow is an ordinary decision
  under §5: single-winner operation row, `provider_succeeded` before the
  local commit, crash-window policy unchanged. The gateway introduces no
  second consistency model; a silent Allow has exactly the same audit
  trail and effects as a consent-screen Allow.
- **Contract stability.** The `ConsentResolution` union gains no member,
  the Decision POST remains the interactive decision entry (session +
  CSRF), and the Resolution GET stays side-effect free **always** — the
  gateway, not the GET, is the one-shot execution entry. No new frontend
  union members are introduced.
- **Prefetch note.** The gateway 302s for every outcome, and its URL is
  only ever reached through the provider redirect chain (browsers do not
  speculatively prefetch redirect targets), so one-shot consumption
  inside the single-winner claim is acceptable.
- **Headers and logging.** Every gateway response carries
  `Cache-Control: no-store` and `Referrer-Policy: no-referrer`
  (§11). The 302 target is the callback URL — credential-grade (§3):
  it appears only in the `Location` header and is never written to
  logs, audit, exception reporting or analytics.

## Consequences

- P3.1 builds the provider authorization adapter on the pinned SDK's
  `oidc/v2` client with the §8 classification (including the
  gateway's error-callback completions) and a fake covering all
  documented scenarios.
- P3.2 introduces `internal/consent` + migration 00005 as specified.
- The gateway (§12) is delivered with the P3.6 topology work, together
  with the interaction base-URI path-prefix probe; P3.1's fake provider
  covers its error-callback branches.
- ADR-0003 is amended in the same commit: the session token is no longer
  "absolutely discarded"; it is sealed into the encrypted Version-2
  credential described in §3.
- The provisioner gains `login_version` handling for OIDC apps (P3.6):
  set on creation, preserved on every update/read-modify-write, repaired
  by reconciliation, plus the one-time production backfill job (§1).
  Existing behavior for non-consent flows is unchanged.
- Frontend contract types are unchanged; no new frontend union members are
  introduced by this ADR.
