# ADR-0012: Feishu Provider Login and Directory Reconciliation (Phase 6)

- Status: **Accepted / Phase 6 implementation frozen**
- Date: 2026-08-11
- Depends on: ADR-0002, ADR-0004, ADR-0006, ADR-0007, ADR-0011
- Scope: Feishu OAuth login, directory staging, durable sync jobs, history, conflicts and explicit identity linking

## 1. Context and invariants

Phase 6 makes Feishu the first external identity Provider beyond the primary
ZITADEL authenticator. Login federation and directory synchronization share a
server-side adapter but are separate product capabilities:

- a Feishu `open_id` is never a United Pass `userId`;
- login succeeds only through an existing exact
  `(provider_id, provider_tenant_id, provider_subject)` identity link;
- email, phone, name, employee number, domain and department may suggest a
  conflict candidate but never create or select an identity link;
- directory observations never create a user, employee profile, persona,
  department membership, role, capability or OAuth grant;
- Provider secrets, authorization codes and access/refresh tokens never enter
  PostgreSQL, Redis payloads, browser responses, audit payloads or logs.

The Phase 6 machine-readable HTTP contract is
`openapi/openapi.yaml`; the matching frontend seam is documented in
`frontend/docs/adr-0008.md` and `frontend/docs/api-contracts.md`.

## 2. Feishu protocol boundary

The outer adapter uses Feishu OAuth v2 code exchange and user-info endpoints
for login, and tenant access token plus Contact v3 department/user reads for
directory synchronization. All calls have bounded response bodies, timeouts,
pagination budgets and bounded retry for transport/429/5xx failures.

`UP_FEISHU_APP_SECRET` is typed server configuration only. Tenant access tokens
are cached in process memory until shortly before expiry. The user access token
is scoped to one callback exchange and discarded after user-info lookup. A
Feishu login creates a local United Pass session without persisting a remote
session/token reference; logout therefore revokes the local session and relies
on Feishu token expiry for that discarded credential.

Startup rejects partial Feishu configuration. Production requires HTTPS and
the redirect URI path is fixed to
`/api/v1/auth/providers/feishu/callback`. Enabling login performs a live tenant
credential validation before the metadata state is committed.

## 3. OAuth login state and identity resolution

Login initiation creates a cryptographically random state value. Redis stores
only its SHA-256 locator, an opaque optional authorization-request continuation,
the remember choice and creation time. `SET NX` plus a GET-and-delete Lua
operation makes state creation collision-safe and consumption single-use.

The callback validates and consumes state before exchanging the one-time code.
The returned Feishu `tenant_key` must exactly equal the configured tenant and
the `open_id` must match an explicit active identity link. An unlinked identity
is recorded as a pending manual conflict and receives a generic login failure;
candidate email/name data never authenticates it. Disabled United Pass users
cannot establish a session.

The continuation is an opaque internal request ID. Arbitrary return URLs are
not accepted, so Provider login cannot become an open redirect.

## 4. Durable directory synchronization

`POST .../{providerId}/directory-syncs` returns `202` with a durable job. A
partial unique index permits at most one `pending` or `running` job per Provider;
concurrent requests return the same active job. A background reconciler claims
jobs with `FOR UPDATE SKIP LOCKED`, reclaims stale running jobs and retries
stable failures up to three attempts.

The adapter produces a bounded normalized snapshot. PostgreSQL stages it in
`provider_directory_departments` and `provider_directory_users`, separate from
the authority-plane `departments` and `employee_profiles`. Checksums make
repeated snapshots idempotent. A complete snapshot may mark missing staging
rows inactive; a partial Provider response never retires unseen rows. No sync
path mutates workforce or authorization state.

Only stable failure classes and counters are stored. Raw Provider bodies,
URLs containing credentials, tokens and raw errors are forbidden. Terminal
success/partial/failure and request events are durably audited.

## 5. Conflicts and explicit manual links

An unlinked external subject creates one durable conflict per Provider tenant.
An exact unique active user email is offered first as a suggestion, then an
exact unique display name; ambiguous or absent matches remain manual. These
facts are presentation hints only.

Resolution requires `provider.manage`, CSRF and a single-use reauthentication
grant bound to `provider.identity.link` and the exact `conflictId`. In one
PostgreSQL transaction it validates the active target `userId`, creates the
exact identity link, marks the conflict resolved and records the success audit.
The schema also prevents one user from receiving multiple Feishu subjects in
the same tenant. Ignoring a conflict creates no link.

## 6. Authorization, metadata and audit

Reads require `provider.read`; mutations require `provider.manage`. Frontend
capability checks are presentation only. Enabling/disabling use target-bound
`provider.enable` / `provider.disable` reauthentication. Sync enqueue and
ignore remain capability + CSRF mutations without step-up under this phase.

Provider API responses contain only display metadata, non-secret App ID,
callback URL, configured-scope label, boolean `secretConfigured`, validation
time, job summaries and conflict hints. Audit payloads contain stable IDs,
operation/result and bounded counters only.

## 7. Failure semantics

- a Provider outage cannot partially enable login because validation precedes
  the state transaction;
- an invalid/replayed OAuth state cannot exchange a code or create a session;
- a wrong tenant cannot stage a directory or resolve a login;
- a failed/partial sync cannot mutate authority-plane workforce state;
- a process crash leaves a claimable durable job rather than a false success;
- PostgreSQL and Feishu are not presented as one distributed transaction.

## 8. Acceptance matrix

| ID | Required proof |
| --- | --- |
| P6-1 | partial credentials and drifting callback URI fail startup validation |
| P6-2 | OAuth state is random, hash-keyed, TTL-bound and single-use |
| P6-3 | OAuth code exchange uses server-only credentials and leaks no token |
| P6-4 | login requires exact Provider/tenant/subject link and active local user |
| P6-5 | email/name/phone/department never auto-link or authenticate |
| P6-6 | sync enqueue is durable, idempotent and single-active-job |
| P6-7 | full snapshots are checksum-idempotent; partial snapshots never retire unseen rows |
| P6-8 | directory staging cannot grant employee/persona/capability state |
| P6-9 | conflict resolution links explicit `userId` atomically with audit |
| P6-10 | one Feishu subject per user/tenant is concurrency constrained |
| P6-11 | frontend parsers and commands enforce the frozen response/reauth seam |
| P6-12 | local static, unit, race, integration and build gates pass |
| P6-13 | real Feishu tenant login/directory acceptance is recorded separately |

## 9. Non-goals

- no SCIM, LDAP, SAML, CAS or generic Provider-creation UI;
- no automatic user provisioning, employee linking or workforce permissions;
- no email/phone/name/domain auto-merge;
- no scheduled policy-based employee offboarding from Feishu observations;
- no persisted Feishu user access/refresh token or remote logout claim;
- no Phase 7 Cerbos policy authoring or audit export.
