# ADR-0008: Passkey Browser Ceremony and Enrollment Abandonment Settlement (Phase 4.5)

- Status: Proposed — implementation requires review approval
- Date: 2026-08-09
- Owners: United Pass backend and frontend teams
- Predecessors: ADR-0006 (P4.0), P4.2 frozen head `562950e`, P4.3 frozen head `1e4a742`

## Context

P4.2 implemented and froze the provider-facing passkey lifecycle:

```text
GET    /api/v1/me/security
POST   /api/v1/me/security/passkeys/enrollment
POST   /api/v1/me/security/passkeys/enrollment/confirm
DELETE /api/v1/me/security/passkeys/{passkeyId}
```

The backend already binds reauthentication grants and enrollment tokens to
the current user, session, action, security epoch and passkey target. It also
passes the provider's creation options through as a JSON object and accepts a
browser credential JSON object for confirmation.

The frontend has not implemented that protocol. Its current real-mode gaps
are material rather than cosmetic:

- `getSecurityFactors()` still returns the Mock-only flat
  `SecurityFactor[]`, which cannot represent multiple passkeys;
- passkey begin/confirm/remove still call the Mock data source;
- enrollment forwards a Mock string instead of invoking WebAuthn;
- there is no account-action reauthentication UI;
- `browserFetch` cannot attach `X-Reauthentication-Token`;
- local optimistic factor changes can pretend provider success;
- Recovery Codes UI remains visible although the real backend freezes it as
  unavailable.

P4.5 also exposes an abandonment window that could not occur before a real
browser ceremony existed:

```text
provider RegisterPasskey succeeds
→ browser receives passkeyId + creation options
→ user cancels / browser rejects / tab closes / local conversion fails
→ provider pending registration remains
→ enrollment token eventually expires
```

The frozen P4.2 contract compensates when Redis creation fails, but it has no
browser-visible cancellation operation and no cleanup index for an enrollment
that was successfully returned and then abandoned. Invalid attestation is
also terminal for the enrollment token while the provider registration may
remain pending. P4.0 live probing established that a pending registration may
not appear in ordinary passkey listing, so list-based UI inference cannot
repair this safely.

This ADR defines the narrow P4.5 browser ceremony and abandonment settlement.
It does not reopen password, TOTP, session, recovery-code, OAuth or consent
semantics.

## Decision

### 1. Scope and frozen boundaries

P4.5 migrates only the following real seams:

```text
GET  /api/v1/me/security                         supporting read seam
POST /api/v1/auth/reauthentication               passkey actions only in this UI
POST /api/v1/auth/reauthentication/mfa           challenge completion

POST /api/v1/me/security/passkeys/enrollment
POST /api/v1/me/security/passkeys/enrollment/confirm
POST /api/v1/me/security/passkeys/enrollment/cancel   new P4.5 settlement seam
DELETE /api/v1/me/security/passkeys/{passkeyId}
```

The password, TOTP and session mutation seams remain Mock-backed until P4.7.
Their status may be displayed from the real security summary, but P4.5 does
not enable their real mutation controls. Recovery Codes remain hidden in real
mode and unchanged in Mock mode.

P4.2's successful-confirmation, transient-provider-error, target-binding and
error-classification invariants remain unchanged. The only narrow amendment
is settlement for passkey enrollments abandoned after begin or terminally
rejected during confirmation.

### 2. Real security summary replaces the flat factor model

The real query model is:

```ts
type SecuritySummary = {
  password: { set: boolean };
  totp: { enabled: boolean };
  passkeys: Array<{
    passkeyId: string;
    createdAt: string | null;
    state: "active" | "pending";
  }>;
  recoveryCodes: {
    available: false;
    deferredReason: "provider_unsupported";
  };
};
```

`UnitedPassQueries.getSecurityFactors()` is replaced by the accurately named
`getSecuritySummary()`. There are no other production consumers, so a
parallel legacy method is not retained. The Mock adapter derives an equivalent
summary while `NEXT_PUBLIC_USE_MOCK=true`.

Every passkey is rendered as its own row keyed by `passkeyId`. `createdAt:
null` renders as "未知"; it is never replaced with the browser clock. Pending
and active states remain distinct. Multiple credentials must never be
compressed into a single synthetic factor.

### 3. Runtime narrowing is fail closed

Every P4.5 HTTP response is received as `unknown` and narrowed before use.
The frontend rejects:

- unknown security-summary states or a non-array `passkeys` field;
- recovery-code payloads that claim availability in real mode;
- missing/empty `enrollmentToken` or `passkeyId`;
- creation/request options without required base64url challenge fields;
- reauthentication statuses other than `granted` / `mfa_required`;
- unknown MFA methods;
- confirmation responses whose status or returned `passkeyId` does not match
  the frozen contract.

A malformed success response is a contract error, never a successful empty
result and never a locally fabricated fallback.

### 4. WebAuthn JSON conversion lives in a pure adapter

Provider JSON is not cast directly to DOM WebAuthn types. A dedicated,
unit-tested browser adapter performs the conversion.

For creation options it base64url-decodes at least:

```text
challenge
user.id
excludeCredentials[*].id
```

and preserves the remaining validated WebAuthn fields. The converted value is
passed only as:

```ts
navigator.credentials.create({ publicKey: options, signal })
```

For assertion request options it decodes:

```text
challenge
allowCredentials[*].id
```

and calls `navigator.credentials.get()` when passkey MFA is selected.

The returned `PublicKeyCredential` is serialized immediately into the
standard JSON representation. Binary fields are base64url without padding:

```text
rawId
response.clientDataJSON
response.attestationObject                  creation
response.authenticatorData/signature/userHandle  assertion
```

`clientExtensionResults`, `authenticatorAttachment` and transports are
included when available. The credential object and binary buffers are kept in
function scope only; they are not written to React state, storage, URLs,
telemetry or logs.

Before any reauthentication or provider begin call, real mode checks that the
required WebAuthn APIs are available. Unsupported browsers fail locally and
therefore cannot create provider-side pending state.

### 5. Reauthentication is an explicit action-bound state machine

Enrollment uses action `account.passkey.enroll` with no target. Removal uses
`account.passkey.remove` with `target = passkeyId`. Account actions always
send empty `applicationId` and `clientId`.

```text
password input
→ POST /auth/reauthentication
→ 200 granted
     → hold reauthToken in component memory
     → immediately submit the exact target mutation

→ 202 mfa_required
     → hold challenge token in component memory
     → TOTP code or navigator.credentials.get()
     → POST /auth/reauthentication/mfa
     → granted token
     → immediately submit the exact target mutation
```

The password proves reauthentication only. It is never repeated in the
passkey mutation body. Raw password, challenge token and grant token are
cleared when the modal closes and are never persisted. A grant is not retried
after the target mutation has consumed it; the user must start a fresh
reauthentication ceremony.

`browserFetch` gains a constrained `reauthToken` option that maps only to
`X-Reauthentication-Token`. Callers do not receive a generic arbitrary-header
escape hatch.

### 6. Enrollment and browser ceremony state machine

After reauthentication grants enrollment:

```text
POST passkeys/enrollment + X-Reauthentication-Token
→ narrow envelope {enrollmentToken, passkeyId}
→ narrow/convert creationOptions without discarding the envelope
→ navigator.credentials.create()
→ serialize credential immediately
→ POST passkeys/enrollment/confirm
   {enrollmentToken, publicKeyCredential, passkeyName}
→ narrow {status:"confirmed", passkeyId}
→ clear transient values
→ router.refresh()
→ render provider-derived summary
```

The enrollment token, provider options and passkey ID are held only for the
open ceremony. Closing the modal aborts the WebAuthn request. There is no
optimistic insertion or generated local passkey ID. Confirmation success does
not update a fake factor row; the Server Component refresh is authoritative.
The envelope is narrowed before creation-option conversion so a structurally
valid token can still drive cancellation when the provider options themselves
are unusable; no field is accepted without its own runtime check.

### 7. Explicit cancellation and expiry settlement

P4.5 adds:

```text
POST /api/v1/me/security/passkeys/enrollment/cancel
Content-Type: application/json

{"enrollmentToken":"opaque value"}
```

The raw token remains in the body, never a URL or log field. The endpoint
requires Session + CSRF but not a second reauthentication grant: possession
of the user/session/epoch-bound enrollment capability is the authorization
created by the already completed step-up ceremony.

Cancellation follows the frozen sensitive-consumer rule exactly:

```text
claim enrollment credential
→ validate user/session/kind binding
→ validate authoritative security epoch
→ check mutation barrier
→ RemovePasskey(server-stored Target)
→ terminally finalize enrollment
```

The client calls cancellation after every local terminal failure occurring
after begin, including user cancellation, unsupported returned options,
WebAuthn exceptions and local serialization failures. A transient provider
failure releases the claim for retry. Provider success or stable not-found
resolves cleanup and returns `204`.

An absent, expired, consumed, concurrently claimed or binding-mismatched
enrollment returns the existing `403 enrollment.invalid` envelope. Store
failure and provider failure keep the existing generic/provider error
classification; they are never rewritten as a successful cancellation.

Client cleanup is not sufficient for tab/process loss, so passkey enrollment
creation also atomically writes a Redis cleanup record and expiry index. The
index contains only the token hash and non-secret enrollment metadata; raw
tokens and credentials never enter it.

The cleanup worker follows these rules:

1. it considers only expired passkey enrollment entries;
2. it never takes an entry while the challenge or its claim lock is live;
3. it lists provider passkeys before deletion;
4. if the target is `active`, it removes only the cleanup marker and **never
   deletes the credential** — this is the provider-success / Redis-finalize
   ambiguity guard;
5. if the target is pending or absent from listing, it calls idempotent
   `RemovePasskey(target)` (P4.0 proved pending registrations may be absent
   from listing);
6. provider unavailability requeues the cleanup entry with capped backoff;
7. outcomes are recorded without token, options or credential material.

Provider confirm and cancellation calls use bounded deadlines strictly
shorter than the enrollment claim-lock TTL. The cleanup worker never acts
while that claim exists. These two constraints are one concurrency invariant:
the worker cannot take over a provider mutation that is still in flight.

Enrollment finalization is disposition-aware:

```text
confirmed
→ atomically delete challenge + claim + cleanup record + cleanup index member

abandoned / terminal invalid attestation
→ delete challenge + claim
→ retain or immediately schedule cleanup record

transient provider failure
→ release claim; preserve challenge and cleanup record
```

The worker's "active means preserve" readback is mandatory. Adding an expiry
index without this guard would allow a Redis finalization failure to delete a
successfully registered passkey later and is forbidden.

### 8. Removal uses target binding and provider readback

Each passkey row removes only its own `passkeyId`:

```text
reauth action=account.passkey.remove target=P
→ DELETE /me/security/passkeys/P
   X-Reauthentication-Token: grant bound to P
→ narrow fresh SecuritySummary returned by backend
→ router.refresh()
```

The UI may render the validated mutation response while refresh completes,
but it must not remove the row before the server reports success. A 404 is
presented as an already-gone/stale-view result and followed by refresh; a 409,
429 or provider failure is not converted into success.

### 9. Mock/real boundary

`NEXT_PUBLIC_USE_MOCK=true` preserves the existing Mock preview behavior and
does not invoke WebAuthn. Real mode:

- hides all Mock badges and explanatory text;
- hides Recovery Codes controls (`available=false`);
- never calls the Mock WebAuthn simulator;
- disables duplicate submits while a reauth, browser ceremony, confirm,
  cancel or remove request is in flight;
- displays safe user-facing errors without raw DOMException/provider text.

### 10. Contract synchronization

The P4.5 implementation commit must keep these three surfaces synchronized:

1. `backend/openapi/openapi.yaml` — machine-readable security summary,
   passkey, cancellation and generalized reauthentication contract;
2. `frontend/docs/api-contracts.md` — human-readable lifecycle;
3. frontend runtime types and validators.

Until P4.5 implementation is accepted, this ADR remains Proposed and the new
cancellation endpoint is not represented as shipped behavior.

## Acceptance gates

P4.5 implementation is reviewable only with executable evidence for:

| Gate | Required evidence |
| --- | --- |
| A1 summary model | zero/one/multiple passkeys, active/pending, `createdAt:null`, real recovery hidden |
| A2 runtime narrowing | malformed summary, reauth union, options and confirm responses all fail closed |
| A3 WebAuthn conversion | base64url round-trip and binary-field conversion for create/get |
| A4 credential serialization | exact attestation/assertion JSON; no ArrayBuffer silently becomes `{}` |
| A5 reauth binding | enroll has no target; remove grant for A cannot remove B; app/client IDs absent |
| A6 token handling | CSRF + reauth headers correct; raw tokens absent from storage/logs/URLs |
| A7 browser cancellation | post-begin `NotAllowedError`/Abort invokes cancel and never confirms |
| A8 invalid attestation | terminal rejection schedules/removes provider pending registration |
| A9 expiry cleanup | abandoned entry is cleaned; live challenge/claim is skipped; transient outage requeues |
| A10 active preservation | provider-confirmed key survives Redis finalization ambiguity and worker sweep |
| A11 provider readback | confirm/remove refresh server state; no optimistic authority |
| A12 Mock regression | Mock preview stays functional and never invokes real WebAuthn |
| A13 sensitive sweep | password, raw tokens, options, attestation/assertion and provider detail absent from logs/persistence |
| A14 live ceremony | real browser registration → provider active readback → removal; evidence recorded honestly |

The implementation must run the full backend and frontend local gates from
the repository `AGENTS.md`. Redis integration must cover the cleanup index,
claim race, confirmed disposition and requeue behavior. The live ceremony is
Pending rather than Passed until actually performed against the pinned
ZITADEL v2.71.18 environment.

## Consequences

- P4.5 is a cross-stack implementation, not a frontend-only Mock replacement.
- The existing P4.2 success paths remain frozen; only passkey abandonment
  settlement is narrowly extended.
- The cleanup index gives abandoned provider state an eventual settlement
  path without making Redis authoritative for passkey state.
- Provider readback remains the authority; Redis records only transient work.
- P4.7 can reuse the reauthentication and WebAuthn adapters for the remaining
  Account Security seams without redefining their security model.

## Alternatives considered

### Ignore browser cancellation and rely on enrollment TTL

Rejected. Redis expiry removes only the local capability; it does not remove
the provider pending registration.

### Use the ordinary passkey DELETE endpoint after cancellation

Rejected. That endpoint requires a fresh `account.passkey.remove` grant bound
to the passkey ID. The enrollment grant was already consumed, and silently
bypassing removal reauthentication would weaken the frozen target contract.

### Put the enrollment token in a DELETE URL

Rejected. URLs are routinely recorded in access logs, history and monitoring.
Opaque capabilities belong in a body or constrained header.

### Let the cleanup worker always call RemovePasskey

Rejected. Provider confirmation may succeed while Redis finalization fails.
Blind deletion would later remove a valid active credential.

### Keep `SecurityFactor[]` and synthesize one passkey row

Rejected. It loses credential identity and makes safe target-bound removal
impossible for users with more than one passkey.
