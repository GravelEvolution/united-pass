# ADR-0003: Authentication Provider Selection (Phase 1.2)

## Status

**Accepted.** The ZITADEL adapter is implemented in
`internal/adapters/zitadel` (Phase 1.2). Remaining work is operational: run
the E2E integration tests against a provisioned instance
(`docker-compose.zitadel.yml` + `scripts/zitadel-init.sh`) and roll out
production secrets. This ADR documents the selection and the mapping between
United Pass's `auth.Authenticator` interface and the ZITADEL LoginV2 API.
Feishu remains a separate directory/synchronization provider and is NOT part
of this decision.

## Context

Phase 1 ships the authentication provider **adapter interface** and a
development-only fake. The service refuses to start in production without an
implemented provider. The frontend contract requires: identifier + password
login, MFA (TOTP primary), provider session reference for logout revocation,
and generic login errors.

## Decision

**ZITADEL** (self-hosted OIDC/OAuth2 platform) is the primary identity
provider for Phase 1.2. It satisfies all criteria: standards-based password
and TOTP flows, server-side session with revocation, self-hostable,
production-grade SDK.

## Implementation mapping

The adapter uses the ZITADEL **LoginV2** API (`zitadel.session.v2`) and user
API (`zitadel.user.v2`) via `github.com/zitadel/zitadel-go/v3`:

| United Pass interface | ZITADEL API |
| --- | --- |
| `BeginPasswordAuthentication` | `SessionService.CreateSession` with `CheckUser{loginName}` + `CheckPassword`, then `ListAuthenticationMethodTypes` (TOTP detection) |
| `CompleteMFA` (TOTP) | `SessionService.SetSession` with `CheckTOTP` |
| `CompleteMFA` (passkey) | `SessionService.SetSession` with `CheckWebAuthN` (JSON assertion) |
| `RevokeProviderSession` | `SessionService.DeleteSession` |
| Readiness | `SessionService.ListSessions` (empty query) |
| Identity mapping | `identity.UserLinker` — `GetOrCreateUserByProviderSubject` on first login |

Key details:

- The adapter authenticates to ZITADEL as a **service account** (OAuth2 JWT
  profile grant, key.json from `UP_AUTH_PROVIDER_SERVICE_ACCOUNT_KEY_FILE`).
  End-user sessions are only referenced by opaque IDs/tokens inside MFA tokens
  and provider session references; no end-user token reaches ZITADEL on behalf
  of our service.
- MFA tokens and provider session references encode `{sessionID}:{sessionToken}`.
- The challenge list drives passkey MFA; TOTP is detected per-user via
  `ListAuthenticationMethodTypes` (no challenge needed for TOTP).
- Credential failures are collapsed into a generic invalid-credentials
  result; transport/auth/quota failures map to provider-unavailable (ADR-0002
  section 12 boundary).
- Identity mapping is concurrency safe: the unique constraint on
  (provider, provider_tenant_id, provider_subject) makes concurrent first
  logins resolve to a single local user.
- Provider readiness is exposed via `/readyz` (`auth_provider` check).

## Configuration

- `UP_AUTH_PROVIDER=zitadel`
- `UP_AUTH_PROVIDER_BASE_URL` — HTTPS endpoint (production); local dev may use
  `http://localhost:8080` for the docker instance.
- `UP_AUTH_PROVIDER_SERVICE_ACCOUNT_KEY_FILE` — service account key.json
  (required for zitadel in all environments; production validation enforces it).
- `UP_AUTH_PROVIDER_PROJECT_ID` — tenant scope for identity links (optional).
- `UP_AUTH_PROVIDER_DOMAIN` — WebAuthn relying-party domain for passkey
  challenges (optional; empty disables passkey challenges).

## Consequences

- Production deployments now start with the ZITADEL adapter; the fake remains
  development-only.
- Real ZITADEL instance provisioning and E2E validation are required before
  the deployment can be signed off.
- Passkey and recovery-code factor flows are partially supported (passkey
  via WebAuthn assertion; recovery codes are not implemented for ZITADEL yet).
- TOTP is the primary MFA method in Phase 1.2; passkey challenges are
  requested only when `UP_AUTH_PROVIDER_DOMAIN` is configured.
