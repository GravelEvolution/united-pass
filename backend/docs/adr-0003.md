# ADR-0003: Authentication Provider Selection (Phase 1.2)

## Status

**Accepted.** The ZITADEL adapter is implemented in
`internal/adapters/zitadel` (Phase 1.2) and has passed local real-instance
acceptance against ZITADEL v2.71.0 (see Operational Sign-off). Remaining work
is operational: passkey browser ceremony, production HTTPS instance and
production secret rollout. This ADR documents the selection and the mapping
between United Pass's `auth.Authenticator` interface and the ZITADEL LoginV2
API. Feishu remains a separate directory/synchronization provider and is NOT
part of this decision.

## Context

Phase 1 ships the authentication provider **adapter interface** and a
development-only fake. The service refuses to start in production without an
implemented provider. The frontend contract requires: identifier + password
login, MFA (TOTP primary), provider session reference for logout revocation,
and generic login errors.

## Decision

**ZITADEL** (self-hosted OIDC/OAuth2 platform) is the primary identity
provider for Phase 1.2. It satisfies all criteria: standards-based password
and TOTP flows, server-side session with revocation, self-hostable,
production-grade SDK.

## Implementation mapping

The adapter uses the ZITADEL **LoginV2** API (`zitadel.session.v2`) and user
API (`zitadel.user.v2`) via `github.com/zitadel/zitadel-go/v3`:

| United Pass interface | ZITADEL API |
| --- | --- |
| `BeginPasswordAuthentication` | `SessionService.CreateSession` with `CheckUser{loginName}` + `CheckPassword`, then `ListAuthenticationMethodTypes` (TOTP detection) |
| `CompleteMFA` (TOTP) | `SessionService.SetSession` with `CheckTOTP` |
| `CompleteMFA` (passkey) | `SessionService.SetSession` with `CheckWebAuthN` (JSON assertion) |
| `RevokeProviderSession` | `SessionService.DeleteSession` |
| Readiness | `SessionService.ListSessions` (empty query) |
| Identity mapping | `identity.UserLinker` — `GetOrCreateUserByProviderSubject` on first login |

Key details:

- The adapter authenticates to ZITADEL as a **service account** (OAuth2 JWT
  profile grant, key.json from `UP_AUTH_PROVIDER_SERVICE_ACCOUNT_KEY_FILE`).
  End-user sessions are only referenced by opaque session IDs; no end-user
  token reaches ZITADEL on behalf of our service.
- **Provider credentials never reach the browser or the database.** The
  browser-visible MFA token is a random United Pass token generated by the
  HTTP layer (`session.GenerateMFAToken`); the ZITADEL session ID is stored
  server-side in the MFA challenge. The session token returned by
  `CreateSession` is treated as a provider bearer credential and discarded
  immediately (`SetSession` ignores it; `DeleteSession` works with the ID
  alone for the calling service account). The persisted provider session
  reference stores the session ID only, encrypted at rest (ADR-0002 §13).
- Passkey MFA: the WebAuthn `PublicKeyCredentialRequestOptions` from ZITADEL
  is passed through to the browser as the `passkeyRequestOptions` JSON object
  in the 202 response; the assertion is submitted back as `passkeyAssertion`
  and forwarded to `CheckWebAuthN`. The HTTP layer validates the payload per
  method (totp → `code`, passkey → `passkeyAssertion`) before any provider
  call.
- TOTP is detected per-user via `ListAuthenticationMethodTypes` (no challenge
  needed for TOTP). Recovery codes are not implemented for ZITADEL and are
  never advertised in `availableMethods`.
- The first-login identity mapping synchronizes the provider profile
  (`GetUserByID`: display name, email + verified, phone) into the local user,
  so `/api/v1/me` satisfies the frontend contract.
- Credential failures are collapsed into a generic invalid-credentials
  result; transport/auth/quota failures map to provider-unavailable (ADR-0002
  section 12 boundary). The exact gRPC code mapping is calibrated in E2E.
- Identity mapping is transactional and concurrency safe: user, identity
  link and persona are created in one transaction; the unique constraint on
  (provider, provider_tenant_id, provider_subject) makes concurrent first
  logins resolve to a single local user.
- Provider readiness is exposed via `/readyz` (`auth_provider` check).
- Production configuration requires an HTTPS provider base URL (scheme, host,
  no userinfo/query/fragment) and the service account key file.

## Configuration

- `UP_AUTH_PROVIDER=zitadel`
- `UP_AUTH_PROVIDER_BASE_URL` — HTTPS endpoint (production); local dev may use
  `http://localhost:8080` for the docker instance.
- `UP_AUTH_PROVIDER_SERVICE_ACCOUNT_KEY_FILE` — service account key.json
  (required for zitadel in all environments; production validation enforces it).
- `UP_AUTH_PROVIDER_PROJECT_ID` — tenant scope for identity links (optional).
- `UP_AUTH_PROVIDER_DOMAIN` — WebAuthn relying-party domain for passkey
  challenges (optional; empty disables passkey challenges).

## Consequences

- Production deployments now start with the ZITADEL adapter; the fake remains
  development-only.
- Real ZITADEL instance provisioning and E2E validation are required before
  the deployment can be signed off.
- Passkey and recovery-code factor flows are partially supported (passkey
  via WebAuthn assertion; recovery codes are not implemented for ZITADEL yet).
- TOTP is the primary MFA method in Phase 1.2; passkey challenges are
  requested only when `UP_AUTH_PROVIDER_DOMAIN` is configured.

- Container runtime: Apple `container` CLI 1.0.0 + container machine

Observed real gRPC codes (ZITADEL v2.71.0, no secrets recorded):
unknown login name → `NotFound` (QUERY-Dfbg2); wrong password →
`InvalidArgument` (COMMAND-3M0fs); wrong TOTP → `InvalidArgument`
(EVENT-8isk2); missing session → `InvalidArgument` (COMMAND-8N9ds) on
SetSession / `NotFound` (QUERY-SFeaa) on GetSession; insufficient service
account permission → `NotFound` (AUTHZ-*); invalid SA key / unreachable
provider → non-gRPC (client construction / OIDC discovery). All map to the
generic invalid_credentials or provider_unavailable statuses; no mapping
change was required.

Compatibility fixes applied during acceptance (real code/config issues):
- `docker-compose.zitadel.yml`: image tag `v2.76.1` → `v2.71.0`; added
  `--masterkeyFromEnv` + 32-byte `ZITADEL_MASTERKEY`; superuser changed to
  `postgres` (ZITADEL init requires the `postgres` admin role);
  pre-provisioned an IAM_OWNER machine user whose JSON key is written to
  `./.zitadel/init-sa.json` (v2.71+ rejects the password grant).
- `scripts/zitadel-init.sh`: admin token via JWT profile
  (`grant_type=jwt-bearer`) instead of the removed password grant; user
  lookup by `preferredLoginName` (instance-level tokens ignore
  `userNameQuery`); machine user + key via management v1 API
  (`/management/v1/users/machine`, `/management/v1/users/{id}/keys`);
  org member authorization targets the test user's org via
  `X-Zitadel-Orgid`.
- `internal/adapters/zitadel`: passkey challenge issuance failures fall back
  to a challenge-less retry so TOTP-only users are not blocked;
  `errors.go` calibration comment updated with the observed codes;
  zitadel integration tests re-apply migrations (the postgres suite drops
  the test schema tables in its cleanup).

Open items:
- **Passkey browser ceremony: not completed.** WebAuthn begin login fails in
  the local instance (`WEBAU-4G8sw`, RP/origin configuration) and no
  browser with a virtual authenticator is available inside the container
  machine; left as a manual real-instance acceptance item. Adapter unit
  tests cover passkey request/assertion handling.
- Production HTTPS instance and production Secret Manager rollout must be
  accepted in pre-production/production environments (not covered here).

**Phase 1 local real-instance acceptance: passed** (all locally runnable
items; passkey ceremony outstanding). This is NOT a production operational
sign-off.
