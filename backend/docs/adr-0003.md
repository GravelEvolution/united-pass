# ADR-0003: Authentication Provider Selection (Phase 1.2)

## Status

Proposed. Phase 1 (session, current user) is implemented and the production
safety boundary is in place; a real authentication provider adapter has not
been built yet. This ADR defines the scope and selection criteria for
**Phase 1.2 — Production Authentication Provider**, which is deliberately kept
separate from the Feishu directory provider (originally mislabeled "Phase 6").
Feishu is a directory/enterprise synchronization provider, not a password
identity provider.

## Context

Phase 1 ships the authentication provider **adapter interface** and a
development-only fake. The service refuses to start in production without an
implemented provider (see `bootstrap.buildAuthenticator`), so production
deployment is blocked until a provider adapter exists.

The frontend contract requires:

- Login with identifier + password.
- MFA verification (TOTP; passkey and recovery codes in later phases).
- Provider session reference for logout revocation (encrypted at rest with
  AES-256-GCM per ADR-0002 section 13).
- Generic login errors that never reveal whether an account exists.

## Decision

Select a single primary identity provider for Phase 1.2. Candidate: **ZITADEL**
(self-hosted OIDC/OAuth2 platform with password, TOTP, and passkey support,
suitable for the United Pass multi-tenant model).

Selection criteria (in priority order):

1. Supports password + TOTP flows over a standards-based protocol (OIDC/OAuth2).
2. Supports server-side session reference and revocation (logout).
3. Can be self-hosted and provisioned per deployment environment.
4. SDK is stable, well documented, and does not leak provider types into the
   domain layer (ADR-0002 section 12 boundary).
5. License and operations cost are acceptable for the product.

## Phase 1.2 Scope

- Implement `auth.Authenticator` adapter for the selected provider
  (`BeginPasswordAuthentication`, `CompleteMFA`, `RevokeProviderSession`).
- Provider adapter selection in `bootstrap.buildAuthenticator` driven by
  `UP_AUTH_PROVIDER` (e.g. `zitadel`).
- Provider connectivity in `/readyz`.
- E2E integration tests against a provider test instance; the development
  fake remains for local development only.
- Deployment documentation: TLS-only endpoints, client credentials via
  secrets manager, session encryption key rotation.

## Not in Phase 1.2

- Passkey / recovery code factor management (Phase 4).
- Feishu directory and organization synchronization (Feishu provider phase).
- User registration, password reset, email verification (later phases).

## Consequences

- Production deployments stay blocked until the Phase 1.2 adapter is built,
  which is intentional: the fake must never serve production traffic.
- The `UP_AUTH_PROVIDER` value becomes authoritative for adapter selection;
  an unknown value fails startup in all environments.
