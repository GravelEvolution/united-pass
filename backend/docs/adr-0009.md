# ADR-0009: Remaining Account Security Real-Seam Migration (Phase 4.7)

- Status: **Accepted — architecture gate for P4.7 implementation**
- Date: 2026-08-09
- Depends on: ADR-0006, ADR-0007, ADR-0008
- Scope: frontend migration of the already-frozen password, TOTP and own-session contracts

## 1. Context and boundary

P4.1–P4.3 implemented and froze the account-session, TOTP and password
backend contracts. P4.5 migrated the security summary, reauthentication and
passkey browser ceremony, while deliberately leaving password, TOTP and
session commands on the Mock data source. P4.7 closes only those remaining
real seams.

Included:

```text
GET    /api/v1/me/sessions
DELETE /api/v1/me/sessions/{sessionId}
DELETE /api/v1/me/sessions
DELETE /api/v1/auth/session

POST   /api/v1/me/security/password
POST   /api/v1/me/security/totp/enrollment
POST   /api/v1/me/security/totp/enrollment/confirm
DELETE /api/v1/me/security/totp
```

The existing `POST /auth/reauthentication` and `/mfa` seams are reused for
password and TOTP actions. No backend business behavior is reopened.

Excluded:

- recovery-code generation/removal remains DEFERRED BY ARCHITECTURE;
- profile, avatar, email and phone mutation seams remain Mock-backed;
- admin session mutation is a distinct authorization surface and is not
  redirected to the current-user session routes;
- no geolocation, device fingerprinting, optimistic authority or client-side
  secret persistence is introduced.

## 2. Contract adaptation

### 2.1 Reauthentication becomes account-action generic

The frontend action union expands from passkey-only to the complete accepted
account action set:

```ts
type AccountReauthenticationAction =
  | "account.password.change"
  | "account.totp.enroll"
  | "account.totp.remove"
  | "account.passkey.enroll"
  | "account.passkey.remove";
```

`target` is required by the frontend input type but is the empty string for
password and TOTP. It is non-empty only for passkey removal. The request still
sends empty `applicationId` and `clientId`. Password-only accounts receive an
immediate grant; MFA accounts continue through the existing TOTP/passkey
challenge adapter.

The reusable UI is renamed from a passkey-specific form to an account
reauthentication form. It receives the operation-specific failure copy, but
does not inspect, store or reuse grant tokens. Every grant is handed directly
to exactly one mutation attempt.

### 2.2 Password

The frontend command is frozen as:

```ts
changePassword(newPassword: string, reauthToken: string): Promise<void>
```

The current password is sent only to `/auth/reauthentication`. The mutation
body is exactly `{newPassword}` and the grant is sent only in
`X-Reauthentication-Token`. The two password values never coexist in the
mutation command or request body.

After a successful response, the browser does not synthesize a security state.
The current UP session may have been rotated by ADR-0007, so the UI closes the
modal and performs `router.refresh()` to read provider/session-authoritative
state and refreshed cookies. Any failure reports a generic operation error and
requires a completely new reauthentication ceremony; the grant is never
retried.

Client-side length and confirmation checks are usability checks, not a
security policy substitute. Provider/backend validation remains authoritative.

### 2.3 TOTP enrollment and removal

The frontend commands are frozen as:

```ts
type TotpEnrollment = {
  enrollmentToken: string;
  secret: string;
  otpauthUri: string;
};

beginTotpEnrollment(reauthToken: string): Promise<TotpEnrollment>
confirmTotpEnrollment(input: {
  enrollmentToken: string;
  code: string;
}): Promise<void>
removeTotp(reauthToken: string): Promise<SecuritySummary>
```

The begin response is runtime-validated. `secret`, `otpauthUri` and
`enrollmentToken` exist only in the mounted enrollment modal's React state.
They are never placed in URL state, DOM attributes other than the visible
secret text / QR presentation, browser storage, logs, analytics, error text or
server-rendered props. Closing the modal clears the only frontend references.

P4.7 does not add a QR-code dependency. The UI shows the manual secret and an
`otpauth:` link suitable for a registered authenticator application; it never
opens that secret-bearing URI in a new web tab and never labels it as a Mock
link. Confirmation sends the one-time token and code together. Success closes
the modal and refreshes the provider summary. A wrong code consumes the
enrollment per ADR-0006, so the UI returns to the initial enrollment step and
does not retry the same token.

Removal obtains a fresh action-bound grant, sends no body, and validates the
returned `SecuritySummary`. The command result is used only as contract proof;
the page refresh remains the rendered authority.

### 2.4 Session inventory and mutations

`GET /me/sessions` is narrowed at runtime onto the full frozen wire type:

```ts
type UserSession = {
  sessionId: string;
  deviceName: string;
  clientName: string;
  approximateLocation: string | null;
  ipAddressMasked: string;
  lastActiveAt: string;
  createdAt: string;
  authenticationMethods: string[];
  isCurrent: boolean;
};
```

Empty display values and null location are rendered as `未知设备`,
`未知浏览器`, `未知位置` and `未知 IP`; the frontend never fabricates facts.

Targeted and bulk revoke commands return only after the backend succeeds.
The UI performs `router.refresh()` after success and does not optimistically
delete list entries. The targeted route is never offered for the current
session. Stable 404 is treated as already absent and still refreshes; other
errors preserve the visible inventory.

The bulk response `{revoked: number}` is runtime-validated and used in the
success message. No reauthentication is added: session + CSRF is the frozen
gate.

`DELETE /auth/session` is invoked by the logout route. Redirect to `/login`
occurs only after the backend response cleared both cookies. An unauthorized
response is treated as an already-ended browser session and also redirects;
other failures remain visible with an explicit retry control. Mock mode keeps
its preview delay and copy.

## 3. Runtime validation and error behavior

New response validators reject malformed session arrays, revoke counts, TOTP
enrollment payloads and TOTP confirmation payloads before they reach UI state.
Successful `204` responses require no parser. All writes use the existing
same-origin browser client, CSRF cookie/header adapter and constrained
reauthentication header option.

No component renders backend/provider error detail. Error messages are scoped
to the operation and do not distinguish foreign/unknown session IDs or expose
credential state beyond the already-authorized summary.

## 4. Mock compatibility

The data-source interface changes to the real wire semantics. The Mock
implementation adapts to the same method signatures and maintains only its
existing in-memory preview state. Real components may branch only for:

- authoritative refresh versus local Mock summary updates;
- Mock logout delay/copy;
- Mock TOTP fixture values.

Real mode must never call a Mock command for any endpoint listed in §1. Mock
recovery/profile/admin seams remain intentionally untouched.

## 5. UI state and cancellation

- Mutation controls are disabled for the entire reauthentication + operation
  chain, preventing accidental double submission.
- Closing a reauthentication modal aborts an in-flight WebAuthn assertion.
  Ordinary HTTP requests are not claimed cancellable unless their command
  explicitly receives an AbortSignal; a late result may not reopen a closed
  modal.
- A TOTP enrollment capability is single-use and never reused after any
  terminal confirmation response.
- Password and TOTP success paths refresh only after the mutation has
  succeeded. Failures never mutate the displayed provider summary.
- Session list refreshes after successful/already-absent revoke; failures
  preserve the list.

## 6. Acceptance matrix

| ID | Required proof |
| --- | --- |
| A1 | Real mode calls no Mock seam for password, TOTP, own-session list/revoke or logout |
| A2 | Reauth actions/targets are exact; password/TOTP use empty target and empty application/client IDs |
| A3 | Password reauth request contains current password; mutation contains only new password + constrained grant header |
| A4 | Password success refreshes authoritative state; every failure requires a new grant and preserves displayed state |
| A5 | TOTP begin payload is strictly validated and delivered with no frontend persistence/logging |
| A6 | TOTP confirm sends enrollment token + code; wrong-code terminal state cannot reuse the token |
| A7 | TOTP remove consumes the correct grant and validates provider readback before refresh |
| A8 | Session response parser covers every frozen field, nullable location and unknown-display fallback |
| A9 | Targeted revoke cannot target current session; 204 and stable 404 refresh, other failures preserve state |
| A10 | Bulk revoke validates `{revoked}` and preserves the current session without reauthentication |
| A11 | Logout calls the real DELETE route before redirect; retry is available for non-auth failures |
| A12 | CSRF is attached to every write; reauth header appears only on password/TOTP/passkey grant consumers |
| A13 | Real mutation UIs are available; recovery/profile/admin Mock surfaces remain isolated |
| A14 | Unit/component tests cover parsers, exact requests, reauth immediate/MFA branches and failure-state behavior |
| A15 | P4.9 live proof: password settlement, TOTP enroll/remove, two-session targeted/bulk/logout semantics and secret-leak sweep |

## 7. Implementation and freeze sequence

1. Freeze this ADR before frontend business-code changes.
2. Add the missing OpenAPI path/schema descriptions without changing backend
   handler semantics.
3. Migrate types, validators, server query and browser commands.
4. Refactor the account-security and session/logout components.
5. Add focused tests and run the complete local frontend/backend gates.
6. Perform review closure, then create a docs-only P4.7 freeze record. A15 may
   remain honestly Pending only until the Phase 4 final live-acceptance stage.
