# ADR-0011: Identity and Workforce Management Plane (Phase 5)

- Status: **Accepted / Phase 5 frozen**
- Date: 2026-08-11
- Depends on: ADR-0002, ADR-0004, ADR-0006, ADR-0007
- Scope: Phase 5 user administration, employee profiles, departments, linking, offboarding and access revocation

## 1. Context and invariants

Phase 5 turns the frozen frontend administration seam into an authoritative
backend management plane. It must preserve the identity model established in
Phase 1:

- a United Pass `userId` is the stable identity primary key;
- an employee is an optional profile on that user, never a second account;
- linking an existing consumer to an employee profile preserves the consumer
  persona and every existing OAuth grant;
- email, phone, display name and domain are search/display facts only and can
  never select or merge identities;
- external provider subjects remain explicit `identity_links` and are never
  copied into employee identity keys.

The frontend contracts in `frontend/docs/api-contracts.md` and
`frontend/src/lib/api/united-pass-data-source.ts` are the product source for
the Phase 5 HTTP surface. `openapi/openapi.yaml` is the machine-readable source
once this ADR is implemented.

## 2. Local data authority

PostgreSQL is authoritative for users, personas, employee profiles,
departments and workforce access state. ZITADEL remains the credential and
provider-session authority; Redis remains the United Pass browser-session
store.

### 2.1 Employee profiles

`employee_profiles` has exactly one row per stable `user_id` and contains:

```text
employee_number, department_id, title, supervisor_user_id,
status = active | offboarding, onboarded_at, offboarded_at, version
```

The current deployment is one organization scope, so `employee_number` is
unique deployment-wide. Numbers are server-generated from a PostgreSQL
sequence and are never inferred from user attributes. A future multi-org model
must add an explicit organization key before weakening this uniqueness rule.

`supervisor_user_id`, when present, must resolve to a different active employee.
The employee persona is inserted in the same transaction as the profile. The
consumer persona is never removed by linking or offboarding.

User disable and employee offboarding atomically clear every department-owner
and subordinate-supervisor reference to the affected user. This preserves the
active-assignee invariant without blocking the security transition; cleared
counts are included in the lifecycle audit payload.

### 2.2 Departments

`departments` is an adjacency-list tree. Names are unique among siblings,
including root departments. The owner is optional and, when present, must be
an active employee. Hierarchy mutations take a transaction-scoped advisory
lock and run serializably; a recursive ancestor check rejects self-parenting
and cycles. A department can be deleted only when it has no child departments
and no employee profiles.

### 2.3 Workforce access state

An `active` profile may participate in internal authorization. An
`offboarding` profile is a durable, immediate deny fact. The Phase 5 permission
resolver wraps the existing resolver and returns no administration
capabilities for an offboarding user. Phase 7 Cerbos integration must preserve
this mandatory deny before evaluating any allow policy.

The historical employee profile and employee persona remain attached for
audit and display. Offboarding does not disable the consumer account, remove
OAuth grants or change the stable `userId`.

## 3. Authorization and anti-enumeration

Every route authenticates the session and authorizes independently. The
frozen capability object remains unchanged:

| Operation | Required capability |
| --- | --- |
| user, employee and department reads | `user.read` |
| enable/disable user, revoke a user's sessions | `user.disable` |
| link or update employee profile | `employee.manage` |
| offboard employee | `employee.offboard` |
| create, update or delete department | `department.manage` |

Malformed, foreign and unauthorized resource identifiers use the common
non-enumerating not-found/forbidden behavior. The API never accepts email,
phone or provider subject in place of a `userId`.

The following high-risk operations consume a single-use reauthentication
grant bound to the actor session, exact action and target `userId`:

```text
user.disable
user.sessions.revoke
employee.offboard
```

Enabling a user, linking/updating a profile, department changes and one
targeted session revoke still require CSRF and their management capability,
but do not consume a step-up grant. Reauthentication never grants the
underlying business permission.

## 4. Transaction and cross-store convergence

Employee linking commits the profile, employee persona and success audit in
one PostgreSQL transaction. Department and user lifecycle mutations likewise
commit their authoritative state and audit atomically.

Offboarding commits all of the following in one transaction:

1. lock the target user and employee profile;
2. change the profile from `active` to `offboarding`;
3. persist the success audit event;
4. enqueue an `employee_offboarded` access-revocation job.

User disable with `revokeSessions=true` enqueues the same kind of durable job
for reason `user_disabled`. An explicit administrator bulk session revoke
enqueues reason `admin_session_revoke` before attempting Redis cleanup.

The service tries each job synchronously, removing every target user's United
Pass session and then best-effort revoking the corresponding provider
sessions while their encrypted references are still available. A bounded
background reconciler retries unresolved United Pass/Redis cleanup jobs. Only
stable error classes and attempt counts are stored; tokens, provider session
handles, passwords and raw errors are forbidden.

A provider failure after the authoritative Redis record was removed is
recorded as a degraded provider outcome and the job is resolved: the system
cannot safely retain or reconstruct a provider handle merely to retry it.
Provider expiry is therefore the final fallback for that remote session. This
is an explicit best-effort boundary, not durable provider-side convergence.

This ordering provides the following failure semantics:

- offboarding access is denied immediately from PostgreSQL even when Redis is
  unavailable;
- an offboarding response means the process was durably started, not that
  every provider session is already gone;
- explicit bulk session revocation returns failure when the synchronous Redis
  walk is incomplete, while the durable job continues local convergence;
- retries are idempotent because deleting an absent session is success and a
  job has one terminal `resolved_at` marker.

No distributed transaction is claimed.

## 5. Pagination, search and disclosure

User and employee lists use server-side search/filtering and signed opaque
cursors bound to the complete query state. Limits are 1–100, default 20.
Production never sends a complete directory to the browser for local
filtering. Department search is also server-side; the Phase 5 department list
is bounded to 100 rows per response until a cursor UI is introduced.

Responses contain only the fields required by the frozen UI. Raw phone
numbers, provider credentials, session tokens, CSRF material and private
employee attributes are never returned. `lastActiveAt` is derived from the
latest explicit provider identity-link observation, with user creation time as
the safe fallback.

## 6. Durable audit

The canonical `security_events` table records, at minimum:

```text
user.enabled, user.disabled,
user.session_revoked, user.sessions_revoked,
employee.linked, employee.updated, employee.offboarded,
department.created, department.updated, department.deleted
```

Success events for PostgreSQL mutations share their state transaction. Denied
authorization and failed cross-store attempts are recorded best-effort without
changing a result that already committed. Payload vocabulary is fixed to
stable target IDs, status transitions, affected counts and safe failure
classes.

## 7. HTTP surface

Phase 5 implements the frozen paths plus the targeted session seam already
used by the user-detail UI:

```text
GET    /api/v1/admin/users
GET    /api/v1/admin/users/{userId}
POST   /api/v1/admin/users/{userId}/enable
POST   /api/v1/admin/users/{userId}/disable
DELETE /api/v1/admin/users/{userId}/sessions
DELETE /api/v1/admin/users/{userId}/sessions/{sessionId}

GET    /api/v1/admin/employees
POST   /api/v1/admin/employees/link
GET    /api/v1/admin/users/{userId}/employee-profile
PUT    /api/v1/admin/users/{userId}/employee-profile
POST   /api/v1/admin/users/{userId}/offboarding

GET    /api/v1/admin/departments
POST   /api/v1/admin/departments
GET    /api/v1/admin/departments/{departmentId}
PATCH  /api/v1/admin/departments/{departmentId}
DELETE /api/v1/admin/departments/{departmentId}
```

The frontend may continue to name the employee detail query
`getEmployeeDetail`; its real seam maps to the user-scoped employee-profile
path. Department commands are added to the data-source abstraction before the
Mock implementation can be removed.

## 8. Acceptance matrix

| ID | Required proof |
| --- | --- |
| W1 | linking preserves one `userId`, the consumer persona and existing grants |
| W2 | concurrent linking creates at most one profile and employee number |
| W3 | email/phone/name/domain never select an identity for mutation |
| W4 | sibling department uniqueness and cycle prevention are database/service enforced |
| W5 | non-empty department deletion fails without partial mutation |
| W6 | every protected route denies absent capability server-side |
| W7 | high-risk grants are action/session/target bound and single-use |
| W8 | offboarding status, audit and cleanup job commit atomically |
| W9 | offboarding user loses admin capability before session cleanup converges |
| W10 | session cleanup retry leaks no credential/provider handle/raw error |
| W11 | user/employee search and pagination are server-side with tamper-proof cursors |
| W12 | frontend runtime parsers reject malformed Phase 5 responses |
| W13 | backend unit, race and PostgreSQL/Redis integration gates pass |
| W14 | real HTTP admin flow passes against the configured ZITADEL-backed runtime |

## 9. Non-goals

- no separate employee account, email-domain auto-link or implicit merge;
- no SCIM, LDAP, SAML, CAS or directory synchronization;
- no employee invitation or creation of a user from the workforce surface;
- no restoration/re-hiring workflow after offboarding;
- no revocation of consumer OAuth grants during employee offboarding;
- no Phase 7 policy authoring or Cerbos rollout;
- no claim that Redis and PostgreSQL commit atomically.
