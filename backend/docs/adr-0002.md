# ADR-0002: Session, PostgreSQL, Redis and Authentication Provider architecture

- Status: Accepted
- Date: 2026-08-05
- Owners: United Pass backend team

## Context

Phase 0 established the HTTP foundation (ADR-0001). Phase 1 must implement real session management, authentication, and current-user APIs. Key decisions are needed for:

1. How browser sessions work (opaque token vs JWT).
2. How PostgreSQL and Redis divide responsibilities.
3. How CSRF is bound to sessions.
4. How the authentication provider is integrated without leaking its types into domain code.
5. How migrations are managed.
6. How tests isolate PostgreSQL schemas and Redis key prefixes.

The frontend contract (ADR-0006, api-contracts.md) fixes cookie names (`up_session`, `up_csrf`), the CSRF header (`X-CSRF-Token`), and the API paths for login, MFA, logout, `/me`, and `/me/permissions`.

## Decision

### 1. Opaque server-side session (not browser JWT)

United Pass uses an opaque, cryptographically random session token stored in a Cookie. The token is never used as a database key — its SHA-256 hash is the Redis key. The server holds the full session record in Redis.

**Why not browser JWT:**
- JWT in a Cookie cannot be revoked without server-side state, which defeats the purpose of stateless tokens.
- JWT payload size grows with claims, increasing Cookie overhead.
- JWT cannot enforce idle timeout independently of absolute expiry.
- Storing provider tokens in a JWT requires encryption and exposes them to potential decode attacks.
- Opaque tokens give the server full control over session lifecycle: revocation, rotation, idle expiry, and attribute updates without re-issuing tokens.

### 2. PostgreSQL and Redis responsibilities

| Store | Role | Data loss impact |
|---|---|---|
| PostgreSQL | Persistent source of truth: users, identity_links, user_personas | Users lose their account — must not happen |
| Redis | Ephemeral: sessions, MFA challenges, rate limit counters | Users lose sessions — must re-login; no user data lost |

Redis is NOT a persistent store. Redis data loss only invalidates sessions and forces re-authentication. No user identity, identity links, or personas are stored in Redis.

### 3. Session token generation and storage

- Token: 32 bytes (256 bits) from `crypto/rand`, base64url-encoded.
- Redis key: `up:{environment}:session:{sha256(token)}`
- Redis value: JSON-encoded session record with TTL.
- Token is never logged, never stored in Redis, never used as a key directly.
- The Cookie contains the raw token; only the hash reaches Redis.

### 4. Session record structure

```json
{
  "version": 1,
  "sessionId": "internal-uuid",
  "userId": "stable-user-id",
  "provider": "provider-name",
  "providerSessionReference": "encrypted-reference",
  "createdAt": "2026-08-05T00:00:00Z",
  "lastSeenAt": "2026-08-05T12:00:00Z",
  "expiresAt": "2026-08-06T00:00:00Z",
  "authenticationTime": "2026-08-05T00:00:00Z",
  "authenticationMethods": ["password", "totp"],
  "reauthenticatedUntil": null,
  "csrfTokenHash": "sha256-of-csrf-token",
  "userAgentHash": "sha256-of-user-agent"
}
```

### 5. Cookie attributes

| Cookie | HttpOnly | Secure | SameSite | Path | Domain |
|---|---|---|---|---|---|
| `up_session` | true | true (prod), false (dev) | Lax | / | not set (host-only) |
| `up_csrf` | false (JS readable) | true (prod), false (dev) | Lax | / | not set (host-only) |

Domain is intentionally not set to keep cookies host-only, preventing subdomain leakage.

### 6. CSRF binding

1. On session creation, a random CSRF token is generated.
2. The raw token is set in the `up_csrf` Cookie (JS readable).
3. The SHA-256 hash is stored in the Redis session record.
4. On non-safe requests (POST, PUT, PATCH, DELETE), the middleware:
   - Reads `up_csrf` Cookie value.
   - Reads `X-CSRF-Token` header value.
   - Compares them using `subtle.ConstantTimeCompare`.
   - Verifies the hash matches the session record's `csrfTokenHash`.
5. Session rotation generates a new CSRF token.
6. Logout clears both cookies.

Login endpoint (no session yet) is protected by:
- SameSite=Lax on the response cookies
- Origin/Sec-Fetch-Site validation
- JSON Content-Type requirement
- Login rate limiting

### 7. Session fixation protection

- Login always generates a brand-new session token.
- MFA completion creates a new session (does not reuse the MFA challenge token).
- Session rotation on privilege elevation or reauthentication.
- The MFA challenge token is single-use and deleted on success.

### 8. Redis key naming and TTL

| Key pattern | TTL |
|---|---|
| `up:{env}:session:{sha256(token)}` | Session TTL (12h default, 720h remember) |
| `up:{env}:mfa:{sha256(mfaToken)}` | MFA challenge TTL (5m) |
| `up:{env}:rl:login:{ip}:{sha256(identifier)}` | Rate limit window (15m) |
| `up:{env}:rl:mfa:{ip}:{sha256(mfaToken)}` | Rate limit window (15m) |

Keys never contain raw identifiers, tokens, emails, or usernames.

### 9. Session touch interval

`lastSeenAt` is not updated on every request. It is updated at most every `UP_SESSION_TOUCH_INTERVAL` (default 5m). This reduces Redis write load while still enforcing idle timeout.

### 10. PostgreSQL connection pool

- Uses `pgxpool` from `pgx/v5`.
- Pool size, min connections, and connect timeout are configurable.
- The pool is created at startup and closed during graceful shutdown.
- Readiness check verifies connectivity with a short timeout.

### 11. Migration tool

Uses `goose/v3` with SQL migrations in `migrations/`.

- Migrations are versioned, ordered, and reviewable.
- Migrations are NOT executed automatically at API server startup.
- A separate `cmd/migrate` command requires explicit arguments (`up`, `status`).
- Down migrations are not automatically executed in production.
- Migrations set the schema search_path to the configured schema.

### 12. Authentication provider adapter boundary

The application layer defines an `Authenticator` interface. The HTTP adapter and domain code depend on this interface, not on any provider SDK.

```go
type Authenticator interface {
    BeginPasswordAuthentication(ctx, PasswordAuthenticationInput) (AuthenticationResult, error)
    CompleteMFA(ctx, MFAChallengeInput) (AuthenticationResult, error)
    RevokeProviderSession(ctx, sessionReference) error
}
```

AuthenticationResult distinguishes: Authenticated, MFARequired, InvalidCredentials, Locked, Expired, ProviderUnavailable.

Provider SDK types do not leak into domain or application packages.

### 13. Provider token storage and encryption

If the provider session reference contains sensitive data (e.g., a refresh token), it is encrypted with AES-GCM before storage in Redis.

- Key: 32 bytes from `UP_SESSION_ENCRYPTION_KEY` (base64-encoded).
- Key ID: stored alongside ciphertext for rotation.
- Plaintext is never logged.
- Ciphertext is never logged.

### 14. TLS requirements

- PostgreSQL: `sslmode=require` (minimum). Connection fails if TLS is unavailable.
- Redis: `rediss://` scheme (TLS). Connection fails if TLS is unavailable.
- No downgrade to plaintext for public network connections.
- If TLS is not available, the service starts but readiness checks fail.

### 15. Readiness strategy

`GET /readyz` checks:
- PostgreSQL connectivity (short timeout, no query details exposed).
- Redis connectivity (short PING, no key details exposed).
- Auth provider connectivity (if configured).

Failures return 503 without leaking dependency addresses, passwords, or error text.

### 16. Test environment isolation

- Integration tests use `UP_TEST_DATABASE_URL`, `UP_TEST_DATABASE_SCHEMA`, `UP_TEST_REDIS_URL`, `UP_TEST_REDIS_KEY_PREFIX`.
- Tests skip (not fail) when these variables are missing.
- Tests never connect to the development schema or development Redis prefix.
- Tests clean up only their own schema tables and Redis prefix keys.
- Tests never execute `FLUSHALL`, `FLUSHDB`, or `DROP DATABASE`.

### 17. Redis failure strategy

- If Redis is unavailable, authentication is not possible (sessions cannot be created or verified).
- Readiness check fails (503).
- The API server does NOT crash — it returns 503 for session-dependent endpoints.
- Health check (`/healthz`) still returns 200 (process is alive).
- Rate limiting fails closed: if Redis is down, login is rejected (not allowed unlimited attempts).

### 18. Temporary permission resolver

Phase 1 does not integrate Cerbos (scheduled for Phase 7). A `PermissionResolver` interface is defined:

```go
type PermissionResolver interface {
    Resolve(ctx, userID) (PermissionCapabilities, error)
}
```

- The default production implementation returns all-false (fail closed).
- A development override can be enabled via explicit configuration.
- Production startup fails if the development override is enabled.
- The API contract does not change when Cerbos is introduced in Phase 7.

## Alternatives Considered

### JWT in Cookie
Rejected — see Decision §1.

### Database-backed sessions (PostgreSQL instead of Redis)
Rejected — session lookup on every request would add latency and load to the primary data store. Redis provides sub-millisecond reads with automatic TTL expiry. PostgreSQL remains the source of truth for user identity.

### Client-side CSRF tokens (double-submit without server state)
Rejected — binding CSRF to the server-side session record provides stronger guarantees. The hash in Redis ensures the token belongs to the current session and cannot be replayed after session rotation.

### GORM/Ent for PostgreSQL access
Rejected — per AGENTS.md §21, ORMs are not approved. `pgx` provides direct, reviewable SQL with full control over queries and connection pooling.

### Auto-migration at startup
Rejected — per AGENTS.md §15, migrations must not execute automatically at API server startup. A separate `cmd/migrate` command with explicit arguments is used.

## Consequences

- Sessions are fully server-controlled: revocation, rotation, idle timeout, and attribute updates work without client cooperation.
- Redis must be available for login and authenticated requests. Redis downtime degrades gracefully (503, not crash).
- PostgreSQL stores only persistent identity data. Redis stores only ephemeral session/challenge/rate-limit data.
- The Authenticator interface allows swapping providers without touching HTTP or domain code.
- Permission resolution is fail-closed until Cerbos is integrated.
- All external connections require TLS. No plaintext fallback for public network connections.

## Security Considerations

- Session tokens are 256-bit cryptographically random, never used as Redis keys directly.
- CSRF tokens are bound to sessions and compared in constant time.
- Provider credentials and session references are encrypted at rest in Redis.
- Rate limit keys use hashes of identifiers, never raw emails or usernames.
- Passwords, TOTP codes, recovery codes, access tokens, and refresh tokens are never logged.
- Login errors are generic — they do not reveal whether an account exists.
- Disabled users' sessions are invalidated (status check on every authenticated request).
