# ADR-0010: Enrollment Finalization and Partial-Revoke Forensics (Phase 4.8)

- Status: **Accepted — architecture gate for P4.8 implementation**
- Date: 2026-08-09
- Depends on: ADR-0006, ADR-0007, ADR-0008, ADR-0009
- Scope: settlement/observability hardening only

## 1. Context and constraints

Two explicitly deferred Phase 4 debts remain after P4.7:

1. after a provider enrollment outcome is terminal, Redis
   `ConsumeEnrollment` / `AbandonEnrollment` can fail under the request
   context; the handler currently logs one warning and relies on capability
   TTL/readback safety;
2. bulk session revocation can delete some victims and then fail while walking
   Redis. Provider cleanup still runs for removed victims, but no durable row
   records that partial mutation.

P4.8 must improve convergence and forensics without changing any frozen HTTP,
provider-authority, session or factor result. No new user-visible feature,
database migration, Redis scan, secret field or retryable raw token is allowed.

## 2. Decision 1 — detached bounded enrollment finalization

Every post-provider enrollment finalization uses one helper with three modes:

```text
consume  — confirmed TOTP/passkey or terminal TOTP result/cancel
abandon  — terminal passkey failure that requires cleanup worker ownership
release  — transient provider failure; browser capability stays retryable
```

Once the provider call has returned, finalization runs under
`context.WithoutCancel(requestContext)` plus a short hard timeout. It retries a
bounded number of times with a small capped delay. `ErrEnrollmentNotHeld` is
idempotent completion: another winner/expiry already settled the claim.

The provider outcome remains the HTTP outcome. A Redis finalization failure
must not turn a confirmed provider success into a false provider failure, nor
turn an invalid factor proof into success. After retries are exhausted the
handler emits one structured `security.enrollment_finalization_degraded` event
containing only:

```text
userId, factorKind, finalizationMode, outcome=degraded, errorClass
```

No raw token/hash, secret, code, credential, provider response or error detail
is logged. The existing challenge/claim TTL and provider-authoritative replay
readback remain the final safety bound when Redis is continuously unavailable.

The helper is used by:

- TOTP confirm (success, invalid terminal, transient release);
- TOTP cancel;
- passkey confirm (success, abandon, transient release);
- passkey cancel.

Pre-provider binding/security-gate rejection keeps its existing semantics but
also finalizes through the detached helper after the claim is owned.

## 3. Decision 2 — durable partial bulk-revoke audit

If `Store.RevokeAllOtherSessions` returns both:

- at least one already-removed victim; and
- a non-nil infrastructure error,

the service continues provider cleanup for every returned victim, then writes
one durable event:

```text
eventType: session.revoked_others
operation: session.revoke_all_others
result: denied
target: current session ID
failure_class: stable class of the store error
revoked_count: number of victims already removed locally
provider_failure_class: first stable provider cleanup failure class, if any
```

`denied` continues to mean the requested bulk operation did not reach its full
success contract; it does not claim that zero side effects occurred.
`revoked_count` makes the partial side effect explicit. The HTTP response stays
the frozen failure with count zero; provider cleanup remains best-effort.

A failure before any victim is removed remains structured-log-only: there is no
partial mutation to preserve durably. A fully successful bulk revoke retains
the existing success row and gains `revoked_count`; provider degradation stays
in the existing `failure_class` field for backward compatibility.

## 4. Decision 3 — detached bounded audit attempt

Session revocation audit writes occur after local invalidation. They therefore
run under a detached bounded context so browser cancellation cannot erase the
forensic attempt. Audit-store failure remains best-effort and never masks or
rewrites the already-completed session result; it produces the existing stable
structured warning.

No outbox or schema migration is introduced. This decision improves the
attempt boundary but does not claim guaranteed delivery during a PostgreSQL
outage.

## 5. Safe additive payload

`session.SecurityAuditEvent` gains two non-secret additive facts:

```go
AffectedCount        int
ProviderFailureClass string
```

The composition root maps positive `AffectedCount` to JSONB
`"revoked_count":"N"` and non-empty provider failure class to
`"provider_failure_class":"..."` through the existing fixed-vocabulary
`SecurityEvent.Extra` seam. Existing columns and result/failure-class meanings
remain unchanged.

## 6. Acceptance matrix

| ID | Required proof |
| --- | --- |
| H1 | provider-terminal consume uses a context that survives request cancellation |
| H2 | transient finalization failure is retried and can converge without changing HTTP outcome |
| H3 | exhausted retries emit exactly one safe degraded event and leak no capability/secret |
| H4 | `ErrEnrollmentNotHeld` is treated as idempotently settled |
| H5 | TOTP confirm/cancel and passkey confirm/cancel all use the shared helper |
| H6 | partial bulk store failure records one durable denied event only when victims were removed |
| H7 | partial event carries exact revoked count, store failure class and optional provider failure class |
| H8 | successful bulk event remains success and carries count; targeted/session semantics unchanged |
| H9 | audit attempt survives caller cancellation but remains timeout-bounded/best-effort |
| H10 | full local gates, Redis/PostgreSQL integration race and sensitive-data sweep pass |

## 7. Non-goals

- no change to enrollment TTL, factor authority, reauth grants or browser API;
- no retry of provider mutation calls after ambiguous outcomes;
- no durable storage of raw enrollment capabilities;
- no guarantee that audit persists through a PostgreSQL outage;
- no reopening of OAuth/consent, recovery codes, profile/admin mutations or
  the frozen password-settlement state machine.
